# [A-12] A user can view anyone's profile and manage their own account from the app

**Lane:** A — Identity & Access
**Task ID:** A-12
**Size:** ~2 days — two screens, and Settings has four sections
**Depends on:** **A-07**, **A-08**, **A-09**, **A-11**. Mounts `<AddFriendButton>`
(**C-08**) — a stub that renders nothing until Lane C ships.
**Blocks:** integration milestone 5 (the friend button's home).

---

## Problem

Every endpoint in this lane is reachable only through `/api/docs`. `/users/:id` and
`/settings` render placeholder boxes, so a user cannot see anyone's profile, change
their own name, set an avatar, or delete their account from inside the app.

## Proposed outcome

Two screens: a public profile with the user's contributions, and a Settings page that
gathers everything a person can do to their own account — including the parts that are
dangerous, clearly marked as such.

## Acceptance criteria

### `ProfilePage` (`/users/:id`)

- [ ] Header: avatar, username, join date, and the three counts from A-06.
- [ ] Anonymized users render the neutral state (no bio, no avatar, no friend button).
- [ ] A tabbed body switching between the user's **Questions** and **Answers** (A-07),
      each paginated.
- [ ] For **another** user (not yourself, not anonymized), mount
      `<AddFriendButton userId>` and pass through the `friendship` object from the
      profile payload. Until C-08 ships the stub renders nothing — **the page must lay
      out correctly with an empty slot**, not with a gap or a broken row.
- [ ] Viewing **your own** profile shows an "Edit profile" affordance linking to Settings.

### `SettingsPage` (`/settings`)

- [ ] **Profile** section: edit username and bio (A-08) with live validation.
- [ ] **Avatar** section: upload and remove (A-09), with a preview of the current one.
- [ ] **Password** section: change password (A-05) — **hidden entirely when
      `has_password` is false**. A Google-only user must not see a password form they
      can't use.
- [ ] **Danger zone**: delete account (A-11) behind a confirmation modal —
      a **password field** for password accounts, a **"type DELETE" field** for
      OAuth-only accounts. On success the user is logged out and sent to the landing page.
- [ ] Every form surfaces `fields` errors **inline, under the relevant input**, and
      reports success with a toast.

## Out of scope

* Any backend change. If a screen needs data the API doesn't return, that's an A-06/A-07
  conversation, not a quiet endpoint edit.
* Building the friend button (C-08) — you mount it, Lane C builds it.
* The Questions/Answers **card** design used elsewhere — reuse Lane B's feed card
  component if it exists by the time you get here; coordinate rather than fork it.
* Public "member since / last seen" indicators. Not in this project.

## Technical notes

**Constraints (requirements, not suggestions):**
* `has_password` drives whether the Password section exists **and** which delete
  confirmation you show. One flag, two consequences — read it once and branch.
* Use the `api` wrapper (`lib/api.ts`); read `fields` off the thrown `ApiError`.
* `components/Modal.tsx` already exists with a focus trap and Escape handling. Use it
  for the delete confirmation rather than writing a third modal.
* Deleting your account must go through `logout` in `AuthContext` (or clear the user)
  so the app doesn't keep rendering as a user who no longer exists.

**Files you will probably touch:**
* `frontend/src/pages/ProfilePage.tsx`, `frontend/src/pages/SettingsPage.tsx` —
  replace the `<Placeholder>`s.
* `frontend/src/components/Avatar.tsx` (from A-09), `contexts/ToastContext.tsx`.

**Suggested approach:**
1. ProfilePage read-only first: header + counts. Then the two tabs with pagination.
2. Mount `<AddFriendButton>` early, even though it renders nothing — that way you find
   the layout problem now rather than on the day Lane C ships.
3. SettingsPage one section at a time, in this order: Profile, Avatar, Password, Danger
   zone. Each is a small form over one endpoint you already have.
4. The delete modal last. Branch on `has_password`, and don't enable the submit button
   until the confirmation input is valid.

**Words you'll meet in this ticket:**
* **Danger zone** — the conventional name for a section holding irreversible actions,
  visually separated so nobody clicks one by accident.
* **Inline field error** — an error rendered next to the input that caused it, rather
  than as a banner. The envelope's `fields` map exists to make this possible.
* **Affordance** — a visible cue that something is clickable.

## Verify it yourself

1. Visit another user's profile → header, counts, both tabs work and paginate.
2. Visit your **own** profile → "Edit profile" links to Settings; **no friend button**.
3. Visit an **anonymized** user's profile → neutral state, no bio, no avatar, no button,
   and the layout doesn't break.
4. Settings → change your username → the header updates and a toast confirms.
5. Set a bio over 500 characters → the error appears **under the bio field**.
6. Upload an avatar → preview updates; it appears in the header bell area and on your
   profile. Remove it → back to initials.
7. Change your password → success toast; a second logged-in window is logged out (A-05).
8. **Log in as a Google-only account** (no password): the Password section is **absent**,
   and the delete modal asks you to type `DELETE` rather than for a password.
9. Delete an account → the modal blocks submission until the confirmation is right; on
   success you're logged out and on the landing page. Their old question still renders
   with the deleted-user stub.
