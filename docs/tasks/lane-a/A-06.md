# [A-06] Anyone can view a user's public profile with their contribution counts

**Lane:** A — Identity & Access

**Size:** ~1 day
**Depends on:** **A-01**. Reads two seams you don't own — `content.visible_filter`

**Blocks:** A-07, A-12.

## Problem

Every author name in the app links to `/users/{id}`, and there is nothing behind it.
There's no way to see who wrote something, what else they've contributed, or whether
you're already friends with them.

## Proposed outcome

`GET /api/users/{id}` returns a public profile card — username, bio, avatar, join date,
three contribution counts, and the viewer's friendship state — while leaking none of
the account's private fields.

## Acceptance criteria

- [ ] Unknown id → **404 `not_found`**. Works for **anonymous** viewers (use
      `get_optional_user`, not `get_current_user`).
- [ ] Returns `UserProfileOut` = `{ id, username, bio, avatar_url, created_at,
      question_count, answer_count, accepted_answer_count, is_anonymized, friendship }`.
- [ ] **Never** includes `email`, `role`, `password_hash`, or any oauth field. This is a
      public endpoint; anyone on the internet can call it.
- [ ] Counts use **visibility semantics**: a stranger counts only the target's
      `approved` questions and answers; the target themselves — or an admin — also counts
      their own `pending` and `rejected` ones.
- [ ] `accepted_answer_count` = the target's answers that some question points at via
      `accepted_answer_id`.
- [ ] An **anonymized** target returns `bio: null` and `avatar_url: null` (counts are
      still computed), so the frontend can render the neutral stub.
- [ ] `friendship` is populated **only** when all three hold: a viewer is logged in,
      viewer ≠ target, and the target isn't anonymized. Shape `{ state, id }` with
      `state ∈ none | request_sent | incoming_pending | friends | rejected`. Otherwise
      it is `null`.

## Technical notes

**Constraints (requirements, not suggestions):**
* Two schemas, deliberately. `UserMeOut` is what you send to the account owner;
  `UserProfileOut` is what you send to the world. Sharing one class is how private
  fields leak.
* Counts respect visibility, which is why they go through B's filter rather than a
  plain `count(*)`.

**Files you will probably touch:**
* `backend/app/routers/users.py`, `backend/app/schemas/user.py`.

**Suggested approach:**
1. Fetch the user, 404 if missing.
2. Three count queries, each with `visible_filter(Model, viewer)` applied. Combining
   them into one query is possible and not worth it yet.
3. Anonymized blanking last, as a post-step on the response object.
4. `friendship` guarded by the three conditions before you call the seam at all.

**Words you'll meet in this ticket:**
* **Visibility semantics** — "who is allowed to see this row", centralised in B-01 so
  four people can't disagree about it.
* **Anonymized user** — a deleted account. The row survives (their posts must keep an
  author) with the personal fields wiped. See A-11.

## Verify it yourself

```bash
docker-compose exec backend pytest tests/lane_a/test_a06_public_profile.py -v
```

By hand:
1. `GET /api/users/{id}` **logged out** → 200, `friendship` is `null`, and there is no
   `email` or `role` anywhere in the JSON.
2. Same call logged in as someone else → `friendship.state == "none"`.
3. Your own profile while logged in → `friendship` is `null`.
4. Insert a pending question for the target in `psql` → a stranger's `question_count`
   doesn't move. (Once B-01 lands, the owner's does.)
5. Set `is_anonymized = true` on a user with a bio and avatar → both come back `null`,
   counts unchanged.
