# [A-13] A user can sign in with their Google account

**Lane:** A — Identity & Access
**Task ID:** A-13
**Size:** ~1.5–2 days
**Depends on:** **A-01**, **A-02**.
**Blocks:** A-14 (the linking flow this hands off to).

---

## Problem

Signing up means inventing another password. The `users` table has `oauth_provider` and
`oauth_subject` columns that nothing writes, and the login page has no third-party
option.

## Proposed outcome

`GET /api/auth/google` and `GET /api/auth/google/callback` — a complete OAuth
authorization-code flow that signs returning users in, provisions new ones, and hands
the awkward case (this email already has a password account) over to A-14 instead of
silently merging two identities.

## Acceptance criteria

### Start — `GET /api/auth/google`

- [ ] If OAuth isn't configured (`GOOGLE_OAUTH_CLIENT_ID` or `..._SECRET` empty),
      **302 redirect** to `/login?oauth_error=unconfigured`. **Never a 500** — an
      unconfigured deployment must still boot and behave.
- [ ] Otherwise mint a signed, expiring **state** token: HMAC-SHA256 with `SECRET_KEY`,
      10-minute expiry, random nonce.
- [ ] Put it in a short-lived `HttpOnly` cookie and **302** to Google's authorize URL
      with scope `openid email profile`.

### Callback — `GET /api/auth/google/callback`

- [ ] Redirect to `/login?oauth_error=state` unless **all** of these hold: `code` and
      `state` are present; `state` matches the cookie under a **constant-time**
      comparison; and its signature and expiry both verify.
- [ ] Exchange the code and fetch userinfo. Any provider failure →
      `?oauth_error=provider`.
- [ ] Require `sub`, `email`, and `email_verified === true` — otherwise
      `?oauth_error=unverified`. An unverified Google email is not proof of ownership.
- [ ] **Returning user** (matched on `oauth_provider = "google"` **and**
      `oauth_subject = sub`): create a session, **302** to `/home`.
- [ ] **First login** (no oauth match, no email collision): provision a user — derive a
      unique username from the email's local part (strip to `[A-Za-z0-9_-]`, pad to at
      least 3 characters, add a numeric suffix on collision), `password_hash = null`,
      and apply the same admin-email rule as A-02. Create a session, **302** to `/home`.
- [ ] **Email collision with an existing password account** → hand off to A-14: **302**
      to `/auth/link` with the link cookie set. If the colliding account is **already**
      Google-linked or otherwise unusable → `?oauth_error=conflict`. **Never silently
      merge or overwrite.**
- [ ] The state cookie is cleared on **every** exit path, success or failure.

## Out of scope

* The linking page and its endpoints — **A-14**. You set the cookie and redirect; they
  handle the rest.
* The `<GoogleButton>` on the login/register pages — also A-14.
* Rendering the `?oauth_error=` notices — A-04 already does that.
* Any provider other than Google.
* Unlinking Google from an account. Not in this project.

## The tests that grade this task

```bash
docker-compose exec backend pytest tests/lane_a/test_a13_oauth_signin.py -v
```

Three tests. The file's docstring explains the shape of them: OAuth is **unconfigured**
in the test environment, so the suite asserts the safe redirect behaviour rather than a
live round-trip to Google.

| Test | What it pins down | AC |
|---|---|---|
| `test_start_unconfigured_bounces_to_login` | `GET /api/auth/google` with no credentials configured → **302** with `/login?oauth_error=unconfigured` in the `Location` header | never 500 |
| `test_callback_without_code_or_state_is_rejected` | a bare callback → **302** with `oauth_error=state` | required params |
| `test_callback_with_mismatched_state_is_rejected` | `?code=abc&state=forged` → **302** with `oauth_error=state` | forged state |

All three use `follow_redirects=False` and read `r.headers["location"]`, so your
redirects must be real 302s with a `Location` header — not a 200 with a JSON error.

**Not graded here, but still required:** essentially the entire happy path. Nothing here
tests the token exchange, userinfo, the `email_verified` requirement, returning-user
matching, username derivation, the collision hand-off, or the constant-time compare.
The tests are guardrails against the failure modes that don't need Google; the real flow
you verify by hand with actual credentials.

## Technical notes

**Constraints (requirements, not suggestions):**
* Compare the state with `hmac.compare_digest`, not `==`. String equality returns early
  on the first differing byte, which leaks information through timing.
* `email_verified` must be exactly `true`. Google will happily report an unverified
  address; treating it as proof of ownership is an account-takeover path.
* Never merge accounts silently. If an email matches a password account, the human must
  prove they own it (that's A-14). Auto-linking means anyone who can create a Google
  account with your email address owns your Knowly account.
* Redirect with the error in the query string; don't render error JSON. The browser is
  mid-navigation and the user needs to land somewhere.

**Files you will probably touch:**
* `backend/app/routers/auth.py`, `backend/app/services/oauth.py` (new).
* `GOOGLE_OAUTH_CLIENT_ID` / `_SECRET` / `_REDIRECT_URI` are already in `config.py`.

**Suggested approach:**
1. The unconfigured path first — it's one `if` and it makes a test green immediately.
2. State minting and verification next (sign `nonce|expiry` with `SECRET_KEY`), which
   makes the other two tests green. That's the whole graded surface; everything after
   this is manual.
3. Then the exchange and userinfo calls with `httpx`.
4. Then the three user branches. Write them as an explicit if/elif chain — returning
   user, collision, new user — rather than one clever query.
5. Username derivation last; it's fiddly but self-contained (`bo.b+tag@x.com` → `bob`,
   then `bob2`, `bob3`).

**Words you'll meet in this ticket:**
* **OAuth authorization code flow** — you send the user to Google; Google sends them
  back with a short-lived `code`; your **server** trades that code for tokens. The
  browser never sees the client secret.
* **State parameter** — a random value you send out and check on the way back. It proves
  the callback belongs to a flow *you* started, defeating cross-site request forgery.
* **`sub`** — Google's permanent, unique id for a user. Match on this, not on email;
  emails can change hands.
* **Constant-time comparison** — comparing two secrets in a way that takes the same time
  regardless of where they differ.
* **Provisioning** — creating a local account from an external identity on first login.

## Verify it yourself

```bash
docker-compose exec backend pytest tests/lane_a/test_a13_oauth_signin.py -v
```

With credentials configured in `.env`:
1. Click through the full flow with a real Google account → you land on `/home`, logged
   in, and a new user row exists with `oauth_provider = "google"`, `oauth_subject` set,
   and `password_hash` NULL.
2. Sign out and repeat → you land on `/home` as the **same** user; no second row.
3. Register a password account with `x@gmail.com`, then Google-sign-in with the same
   address → you land on `/auth/link`, **not** on `/home`, and no account was modified.
4. Tamper with the state cookie mid-flow → `/login?oauth_error=state`.
5. Blank the client ID in `.env`, restart, click the flow →
   `/login?oauth_error=unconfigured`, and the app is otherwise fine.
6. Check the derived username of a fresh sign-in for an address like
   `some.body+spam@gmail.com` → something clean and valid, and a second such user gets a
   numeric suffix rather than a 500.
