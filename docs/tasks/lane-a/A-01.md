# [A-01] A user's login survives page reloads, and every protected route knows who is calling

**Lane:** A — Identity & Access
**Task ID:** A-01
**Size:** ~1.5–2 days
**Depends on:** nothing. Start here on day 1.
**Blocks:** everything you build after it — **and all three other lanes.** Every
protected route in the app currently runs on a fake user; yours is the code that makes
them real.

---

## Problem

The Launch Pad hands every request the same hardcoded dev user, so the app cannot tell
two people apart, nobody can log out, and no endpoint can refuse an anonymous caller.
Three other people are building features on top of that fake user right now — none of
their permission rules can be tested until sessions are real.

## Proposed outcome

Real server-side sessions: a random opaque token in a cookie, only its hash in the
database, and the three dependency functions (`get_current_user`, `get_optional_user`,
`require_admin`) that every protected route in every lane imports.

## Acceptance criteria

- [ ] A session token is 256 bits of randomness (`secrets.token_urlsafe(32)`), returned
      to the client **only** in the `knowly_session` cookie.
- [ ] The database stores **only the SHA-256 hash** of the token. The raw token is never
      logged and never appears in any response body.
- [ ] `create_session(user_id)` inserts a `sessions` row with
      `expires_at = now + 14 days`, **flushes but does not commit** (the caller owns the
      transaction), and returns the raw token.
- [ ] The cookie is set with `HttpOnly`, `Secure`, `SameSite=Lax`, `path=/`, and
      `max_age` of 14 days.
- [ ] `get_optional_user` reads the cookie, resolves the session by token hash, and
      returns the `User` or `None`.
- [ ] An expired session (`expires_at <= now`) is treated as absent **and deleted
      lazily** during that lookup.
- [ ] `get_current_user` does the same but returns **401 `unauthenticated`** when there
      is no valid session.
- [ ] `require_admin` builds on `get_current_user` and returns **403 `forbidden`**
      ("Admin access required") when `user.role != "admin"`.
- [ ] `delete_session(session)` removes one row; `delete_other_sessions(user_id, keep_id)`
      removes all of a user's sessions except the one passed in.
- [ ] All timestamps are **naive UTC** (`datetime.utcnow()`), matching the schema.

## Technical notes

**Constraints (requirements, not suggestions):**
* Store the hash, never the token. If your database leaks, hashes are useless to an
  attacker; raw tokens are working keys to every account.
* `create_session` flushes, never commits — register and login need to create a user
  and a session in one transaction.
* Naive UTC everywhere. Mixing naive and timezone-aware datetimes raises `TypeError`
  the first time you compare them, usually in the expiry check.

**Files you will probably touch:**
* `backend/app/services/auth.py` — replace the fixed-dev-user stub.
* `backend/app/services/session.py` — session creation/lookup/deletion helpers.
* `backend/app/models/session.py` — read only.
* `backend/app/routers/users.py` — a minimal `GET /me` so the tests can run.

**Suggested approach:**
1. `hash_token(raw) -> sha256 hex` and `create_session(db, user_id)` first.
2. Then `get_optional_user`: read cookie → hash → `SELECT ... WHERE token_hash = :h`
   → check expiry → return user. Delete the row when it's expired.
3. `get_current_user` = `get_optional_user` + raise 401. `require_admin` =
   `get_current_user` + role check.
4. The cookie-setting helper last, so login/logout in A-03 just call it.

**Words you'll meet in this ticket:**
* **Opaque token** — a random string that means nothing by itself; the server looks it
  up. The opposite of a JWT, which carries its own readable payload.
* **Dependency (FastAPI)** — a function you declare in a route's signature that runs
  before the handler. `get_current_user` is one; that's how a route "requires login".
* **Lazy deletion** — cleaning up an expired row when you happen to touch it, instead
  of running a scheduled sweep.
* **Flush vs commit** — flush sends the INSERT so the row gets an id; commit makes it
  permanent. Callers commit.

## Verify it yourself

```bash
docker-compose exec backend pytest tests/lane_a/test_a01_sessions.py -v
```

Then by hand:
1. Create a session for a user, and look at the `sessions` table in `psql` — the value
   there must **not** be the token you hold. It should be 64 hex characters.
2. `curl -k https://localhost/api/users/me` with no cookie → 401 and the error envelope.
3. Same call with a valid cookie → 200.
4. Set `expires_at` to yesterday in `psql`, call again → 401, **and the row is gone**.
5. Check the `Set-Cookie` header in the browser devtools: `HttpOnly`, `Secure`,
   `SameSite=Lax`, `Max-Age` around 1209600.
