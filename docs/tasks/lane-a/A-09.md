# [A-09] A user can upload a profile picture, and everyone else sees it

**Lane:** A — Identity & Access
**Task ID:** A-09
**Size:** ~1–1.5 days
**Depends on:** **A-05**.
**Blocks:** A-12 (Settings' avatar section). `<Avatar>` is used by **every lane** — Lane
C's friends list and notification dropdown, Lane B's post headers, Lane D's AI pages.

---

## Problem

Every user in the app looks the same. The Launch Pad's `<Avatar>` renders initials and
ignores `avatar_url` entirely, and there is no way to set one — so the field exists,
unused, in every payload the app sends.

## Proposed outcome

Upload and remove endpoints that accept only real images, normalise them to a single
size and format, and a real `<Avatar>` component that shows the picture when there is
one and a stable initials tile when there isn't.

## Acceptance criteria

### `POST /api/users/me/avatar` (multipart)

- [ ] **Validate by content, not by filename.** Reject → **400 `validation_error`** with
      `fields: { avatar: ... }` when the file is: larger than 2 MB; empty; not PNG /
      JPEG / WebP **by magic bytes**; or fails a real image decode.
- [ ] Normalise every accepted image to a **256×256 PNG** (centre-crop or fit), store it
      under a UUID filename in the public avatars volume, and set `avatar_path` so
      `avatar_url` reads `/avatars/<uuid>.png`.
- [ ] Returns `UserMeOut`.
- [ ] **Replacing** an avatar deletes the previous file **after** the database commit
      succeeds. If the commit fails, delete the file you just wrote (no orphans). A
      failure to delete the *old* file must never fail the request.

### `DELETE /api/users/me/avatar`

- [ ] Sets `avatar_path` to `null`, returns `UserMeOut`, and best-effort removes the file.

### `<Avatar user size>`

- [ ] When `avatar_url` is set, render the image.
- [ ] When it's `null`, render a **deterministic** initials tile derived from the
      username with a stable colour — the same user always gets the same colour, on
      every screen, on every reload.
- [ ] Anonymized users get a neutral placeholder.

## Out of scope

* Post attachments — that's Lane D's file system (D-09/D-10), a different volume with
  different rules. Yours is public; theirs is auth-gated.
* Cropping UI, filters, or drag-to-reposition. Server-side normalisation only.
* The Settings page that mounts the upload control — A-12.
* Gravatar or any external avatar service.

Three tests. They build real PNG bytes with Pillow (`Image.new(...).save(buf, "PNG")`),

| Test | What it pins down | AC |

**Not graded here, but still required:** the 2 MB limit, the 256×256 normalisation, the
declared-MIME-vs-magic-bytes distinction (the test's fake is text through and through —
try a `.png` filename over text bytes yourself), old-file cleanup ordering, and the
entire `<Avatar>` component (no pytest surface).

## Technical notes

**Constraints (requirements, not suggestions):**
* Never trust the filename or the client's `Content-Type`. Both are attacker-controlled.
  Sniff the magic bytes and then actually decode the image — a file that claims to be a
  PNG and isn't should fail at decode, not at serve time.
* Order of operations on replace: write new file → update row → **commit** → delete old
  file. Deleting before the commit means a rollback leaves the user with a broken image.
* Pillow is already a dependency (the tests import it).

**Files you will probably touch:**
* `backend/app/routers/users.py`, `backend/app/services/avatar.py`,
  `frontend/src/components/Avatar.tsx` (replace the initials-only stub).
* `AVATAR_DIR` and `AVATAR_MAX_BYTES` are already in `config.py`.

**Suggested approach:**
1. Size check → magic-byte sniff → `Image.open()` inside a `try` (a decode failure is a
   400, not a 500).
2. Convert to RGB, centre-crop to a square, resize to 256×256, save as PNG under
   `uuid4().hex + ".png"`.
3. Then the ordering dance for replacement. Write it as: remember `old_path`, do the
   work, commit, then `try: unlink(old_path) except: log`.
4. `<Avatar>` last. For the stable colour, hash the username and index into a fixed
   palette — same input, same colour, no state.

**Words you'll meet in this ticket:**
* **Magic bytes** — the first few bytes of a file that identify its real format
  (`\x89PNG` for PNG). The only trustworthy signal about what a file is.
* **Normalisation** — forcing everything into one size and format so the rest of the app
  never deals with a 4000×3000 progressive JPEG.
* **Orphan file** — a file on disk with no database row pointing at it. Created by
  committing in the wrong order.
* **Deterministic** — same input, same output, every time. Required for the initials
  colour, or a user's tile changes colour between pages.

## Verify it yourself

```bash
docker-compose exec backend pytest tests/lane_a/test_a09_avatars.py -v
```

By hand:
1. Upload a large JPEG → 200, and the returned URL ends in `.png`. Open it in the
   browser: it's 256×256.
2. Upload a 3 MB image → 400 with `fields.avatar`.
3. Rename a `.txt` file to `.png` and upload it → 400. (Filename lies; bytes don't.)
4. Upload a second avatar → the old file is **gone** from the volume; exactly one remains.
5. `DELETE` the avatar → `avatar_url: null`, and the UI falls back to initials.
6. Load a page with several users → each has a consistent colour; refresh → identical.
7. An anonymized user renders the neutral placeholder, not initials of `[deleted_ab12]`.
