# [A-11] A user can delete their account without destroying the discussions they took part in

**Lane:** A — Identity & Access
**Task ID:** A-11
**Size:** ~1.5 days — the trickiest task in the lane
**Depends on:** **A-05**.
**Blocks:** A-12 (Settings' danger zone).

---

## Problem

There is no way to leave. That's a real problem for a product that stores an email
address — but a naive delete would take every question and answer the user ever wrote
down with it, tearing holes in threads other people are still reading. The schema
already forbids it: `author_id` foreign keys are `ON DELETE RESTRICT`, so the database
will refuse the delete outright.

## Proposed outcome

`DELETE /api/users/me` — the account's personal data is wiped and the row is kept as an
anonymous stub, so authored content survives, re-attributed to `[deleted_xxxx]`. One
transaction: all of it, or none of it.

## Acceptance criteria

### The confirmation gate

- [ ] A **password** account must send `{ password }`. Wrong or missing →
      **401 `invalid_credentials`** with `fields: { password: ... }`.
- [ ] An **OAuth-only** account (no password) must instead send `{ confirm: "DELETE" }`.
      Anything else → **400 `confirmation_required`** with
      `fields: { confirm: "Type DELETE to confirm" }`.

### The anonymization, in one transaction

- [ ] The user row is **UPDATEd, never DELETEd**.
- [ ] Set `username = "[deleted_<hex>]"`, `email = null`, `password_hash = null`,
      `bio = null`, `avatar_path = null`, `oauth_provider = null`,
      `oauth_subject = null`, `is_anonymized = true`.
- [ ] Delete all of the user's `sessions`.
- [ ] Delete all `messages` where they are sender **or** receiver — both copies vanish.
      The deleting user's privacy wins over the other party's history; this is
      deliberate, documented behaviour.
- [ ] `notifications` where they are the **actor**: set `actor_id = null` and
      `actor_count = max(actor_count - 1, 1)` — keep the row, floor the count at 1.
- [ ] `notifications` where they are the **recipient**: delete.
- [ ] Delete their `ai_conversations` (`ai_messages` cascade in the database).
- [ ] Delete their `friendships` from either side.
- [ ] **Any partial failure rolls the whole thing back.** There is no half-deleted state.
- [ ] On success: clear the session cookie and return **204**. The avatar file is
      removed after the commit, best-effort.

## Out of scope

* Deleting the user's questions, answers, or comments. They stay, re-attributed. That's
  the entire point.
* An "undo" or grace period. This is irreversible by design.
* Admin-initiated deletion of another user. Not in this project.
* Data export. Not in this project.

Your route must accept a body.

| Test | What it pins down | AC |

| `test_oauth_only_account_requires_typed_confirmation` | a passwordless account sending `{"confirm": "nope"}` → **400** with `error.code == "confirmation_required"`; sending `{"confirm": "DELETE"}` → **204** | OAuth gate |

## Technical notes

**Constraints (requirements, not suggestions):**
* One transaction. If the notifications step fails, the username must not already be
  wiped.
* `ON DELETE RESTRICT` on `author_id` is the schema telling you this is an UPDATE. Don't
  fight it.
* You are writing to tables Lane C and Lane D own. That's expected here — the models all
  exist in the Launch Pad and the schema is frozen, so no coordination is needed. Read
  their models; don't guess column names.
* `actor_count` floors at 1 because a coalesced notification that says "0 people voted"
  is nonsense.

**Files you will probably touch:**
* `backend/app/routers/users.py`, `backend/app/services/account.py` (new).
* Read-only: `models/{message,notification,ai,friendship,session}.py`.

**Suggested approach:**
1. The gate first — branch on `user.password_hash is None` to decide which confirmation
   applies, and fail closed.
2. Then the six cleanup steps as six bulk statements in one function. Bulk `delete()` /
   `update()` statements, not loops loading objects.
3. Wipe the user row **last**, so if anything above fails you haven't destroyed the
   identity you needed to find the rows.
4. Commit once at the end. Then clear the cookie and best-effort unlink the avatar.

**Words you'll meet in this ticket:**
* **Anonymization** — removing the link between data and a person while keeping the
  data. The alternative to deletion when other people's content depends on the row.
* **`ON DELETE RESTRICT`** — a foreign-key rule that blocks deleting a parent row while
  children reference it. Here it's a design decision expressed in the schema.
* **Atomic / all-or-nothing** — the transaction either fully happens or fully doesn't.
* **Bulk statement** — one `UPDATE`/`DELETE` affecting many rows, instead of a Python
  loop issuing one query per row.

## Verify it yourself

```bash
docker-compose exec backend pytest tests/lane_a/test_a11_account_deletion.py -v
```

By hand — build a user with **everything** attached first: a question, an answer, two
messages (one sent, one received), a notification where they're the actor **and** one
where they're the recipient, an AI conversation, and a friendship.

1. Delete with the wrong password → 401, and **nothing** changed anywhere.
2. Delete correctly → 204, cookie cleared, you're logged out.
3. In `psql`, walk the list:
   - the `users` row exists, `is_anonymized = true`, username `[deleted_...]`, personal
     fields `NULL`;
   - `sessions` for them: none;
   - `messages` involving them (either direction): none;
   - the notification where they were the **actor**: still there, `actor_id` is `NULL`,
     `actor_count` did not drop below 1;
   - the notification where they were the **recipient**: gone;
   - `ai_conversations` and `ai_messages`: gone;
   - `friendships`: gone;
   - their **question and answer**: still there.
4. Load the question in the app → the author renders as the neutral deleted stub.
5. Force a failure mid-way (temporarily raise after step 3) → confirm the username is
   **not** wiped and the messages are **not** gone. Then remove the sabotage.
