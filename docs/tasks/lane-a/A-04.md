# [A-04] A user can sign up and sign in from the app itself, and stays signed in across reloads

**Lane:** A — Identity & Access
**Task ID:** A-04
**Size:** ~1.5 days
**Depends on:** **A-02**, **A-03**.
**Blocks:** every other lane's manual testing — until this ships, testing as a second
user means hand-crafting cookies.

---

## Problem

Registration and login exist as endpoints only. The `/login` and `/register` routes
render placeholder boxes, and `AuthContext` is the Launch Pad's dummy — it resolves a
user on mount but has no real `login`, `register` or `logout`. Nobody can use the app
as themselves.

## Proposed outcome

Working Login and Register pages backed by a real `AuthContext`, so a user signs in
once and the whole app knows who they are — including after a refresh.

## Acceptance criteria

### `AuthContext`

- [ ] Exposes `{ user, isLoading, login, register, logout, refresh }` — the shape the
      dummy already advertises, so no other lane's `useAuth()` call has to change.
- [ ] On mount it resolves the current user via `GET /api/users/me` **once**;
      `isLoading` stays `true` until that settles.
- [ ] `login` and `register` set `user` from their own response — no second round-trip.
- [ ] `logout` calls the endpoint and then clears `user` **even if the call fails**.
      A user who clicked "log out" must end up logged out locally regardless.

### Login page (`/login`)

- [ ] Email + password fields; submit calls `login`.
- [ ] On `invalid_credentials`, show the message, and — because `oauth_hint` is set —
      an inline note like "If you signed up with Google, use the Google button."
- [ ] Field-level errors from the envelope's `fields` render under their inputs.
- [ ] Accepts an `?oauth_error=<reason>` query param (set by A-13) and shows a generic
      notice for `unconfigured | state | provider | unverified | conflict`.

### Register page (`/register`)

- [ ] Email, username, password fields.
- [ ] Client-side validation **mirrors the backend rules** (username 3–30 of
      `[A-Za-z0-9_-]`; password 8–128 with a letter and a digit) for instant feedback.
- [ ] Server `fields` errors still render on submit — the 409 uniqueness case can only
      come from the server, so client validation never replaces it.

### Both

- [ ] A successful login or register redirects to `/home`.
- [ ] `ProtectedRoute` (shell-provided) sends unauthenticated users to `/login`, and
      **waits for `isLoading` to finish** so a logged-in user isn't bounced to the login
      page on first paint.

## Out of scope

* The endpoints themselves (A-02, A-03) — if a page needs a field the API doesn't send,
  that's a backend conversation.
* The Google button and the `/auth/link` page — A-13 / A-14.
* Profile and settings screens — A-12.
* "Forgot password". Not in this project.

## Technical notes

**Constraints (requirements, not suggestions):**
* Keep the `useAuth()` return shape exactly as the dummy advertises. Three other lanes
  already destructure `user.id`, `user.role`, `user.username`, `user.avatar_url`.
* Use the `api` wrapper in `lib/api.ts` — it sends the cookie (`credentials: 'include'`)
  and throws a typed `ApiError { status, code, message, fields? }`. Read `fields` off
  that, don't re-parse the response.
* The session cookie is `HttpOnly`, so **JavaScript cannot read it**. "Am I logged in?"
  is answered only by calling `/api/users/me`. Don't try to inspect the cookie.

**Files you will probably touch:**
* `frontend/src/contexts/AuthContext.tsx` — replace the dummy internals.
* `frontend/src/pages/LoginPage.tsx`, `frontend/src/pages/RegisterPage.tsx`.
* `frontend/src/components/ProtectedRoute.tsx` — check the `isLoading` handling.
* `frontend/src/lib/validation.ts` — check what's already there before writing rules.

**Suggested approach:**
1. `AuthContext` first, with `login`/`register`/`logout` as thin wrappers over `api`.
2. Login page next — it's the simpler form and it's how you'll test everything else.
3. Register page, reusing the same error-rendering component.
4. `?oauth_error=` handling last; it's a `useSearchParams` read and a notice banner.

**Words you'll meet in this ticket:**
* **Context (React)** — app-wide state any component can read without prop-drilling.
* **HttpOnly cookie** — a cookie the browser sends automatically but JavaScript cannot
  read. It's what protects the session from a cross-site scripting bug.
* **First paint** — the very first render, before async work finishes. The classic bug
  here is redirecting to `/login` during it because `user` is still `null`.

## Verify it yourself

1. Register a new account → lands on `/home`, header shows your username.
2. Log out → back to `/login`; visiting `/home` directly bounces you to `/login`.
3. Log in, then **hard-refresh** `/home` → you stay on `/home`. You must not see a
   flash of the login page. (Throttle the network in devtools to make the gap visible.)
4. Log in with a wrong password → the generic message plus the Google note; nothing
   reveals whether the email exists.
5. Register with the username of an existing user → the 409 message appears **under the
   username field**.
6. Register with password `password` → blocked client-side, before any request goes out.
7. Visit `/login?oauth_error=state` → the generic notice shows.
8. Stop the backend and click "log out" → you still end up logged out locally.
