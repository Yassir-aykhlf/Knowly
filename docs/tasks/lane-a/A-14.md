# [A-14] A user whose email already has a password account can link Google to it, by proving it's theirs

**Lane:** A — Identity & Access
**Task ID:** A-14
**Size:** ~1 day
**Depends on:** **A-13** (it sets the pending-link cookie and redirects here).
**Blocks:** nothing — this is the last task in the lane.

---

## Problem

A-13 deliberately refuses to merge a Google identity into an existing password account,
and redirects to `/auth/link` instead. That route currently renders a placeholder, so
anyone in this situation hits a dead end: they can't sign in with Google, and nothing
tells them why.

## Proposed outcome

A link-or-cancel screen. The user proves they own the password account by entering its
password; only then does the Google identity get attached. Cancelling is a first-class
option, not a trap.

## Acceptance criteria

### `POST /api/auth/google/link`

- [ ] Reads the pending-link signed cookie set by A-13 (5-minute expiry, carrying
      `email` and `sub`). Absent or expired → **400 `link_expired`**.
- [ ] Body `{ password }`. Load the password account by that email. Missing, already
      linked, or passwordless → **400 `link_invalid`**.
- [ ] Wrong password → **401 `invalid_credentials`**.
- [ ] If that Google `sub` got linked to **someone else** in the meantime →
      **409 `conflict`**.
- [ ] On success: set `oauth_provider = "google"` and `oauth_subject = sub` on the
      account, create a session, clear the link cookie, and return `UserMeOut`.

### `DELETE /api/auth/google/link`

- [ ] Clears the link cookie and returns **204**. Always succeeds — cancelling something
      that isn't there is not an error.

### `AuthLinkPage` (`/auth/link`)

- [ ] Explains the situation: "An account with this email already exists — confirm your
      password to link Google to it."
- [ ] A password field (submit → link, success → `/home`) and a **Cancel** button
      (→ the cancel endpoint, then back to `/login`).
- [ ] On `link_expired`, prompt the user to start Google sign-in again rather than
      leaving them staring at a dead form.

### `<GoogleButton>`

- [ ] A "Continue with Google" button on both the login and register pages that
      navigates to `GET /api/auth/google`.
- [ ] It's fine for it to show even when OAuth is unconfigured — the start endpoint
      bounces back with the notice (A-13), and A-04 renders it.

## Out of scope

* The sign-in flow itself — A-13.
* Unlinking Google from an account afterwards. Not in this project.
* Linking any provider other than Google.
* Letting a logged-in user add Google from Settings. The only entry point is the
  collision hand-off from A-13.

| Test | What it pins down | AC |
|---|---|---|
| `test_link_without_pending_cookie_is_expired` | posting to link with **no** cookie → **400** and `error.code == "link_expired"` | the cookie gate |

## Technical notes

**Constraints (requirements, not suggestions):**
* The link cookie must be **signed** and short-lived. It carries "this Google identity
  is waiting to be attached to this email" — if a user could forge it, they could attach
  their Google account to someone else's email and then sign in as them.
* Verify the password. That step is the entire security of this feature; without it the
  flow is exactly the silent merge A-13 refused to do.
* Clear the cookie on success **and** on cancel. A leftover pending link is a loaded gun.
* Re-check the `sub` at write time — between A-13's redirect and this POST, that Google
  identity may have been linked elsewhere. That's the 409.

**Files you will probably touch:**
* `backend/app/routers/auth.py`, `backend/app/services/oauth.py` (share A-13's
  cookie-signing helpers — don't write a second signer).
* `frontend/src/pages/AuthLinkPage.tsx`, `frontend/src/components/GoogleButton.tsx`,
  and mounting the button on `LoginPage` / `RegisterPage`.

**Suggested approach:**
1. Reuse A-13's sign/verify helpers for the link cookie; only the payload differs.
2. Endpoint: verify cookie → load account → the three invalid cases → verify password →
   re-check `sub` → write → session → clear cookie → return `UserMeOut`.
3. Cancel is three lines.
4. Then the page: it's a one-field form plus a cancel button. Handle `link_expired` by
   swapping the form for a "start again" link to `/api/auth/google`.
5. `<GoogleButton>` last — a link styled as a button, pointing at the start endpoint.

**Words you'll meet in this ticket:**
* **Account linking** — attaching a second sign-in method to one existing account.
* **Signed cookie** — a cookie carrying a value plus an HMAC of it, so the server can
  detect tampering. It is *not* encrypted; the contents are readable, just not forgeable.
* **Fail closed** — when anything is uncertain, refuse. Every ambiguous branch here ends
  in a 400 or a 409, never in "link it anyway".

## Verify it yourself

```bash
docker-compose exec backend pytest tests/lane_a/test_a14_oauth_linking.py -v
```

With real credentials:
1. Register `you@gmail.com` with a password. Sign out.
2. Click "Continue with Google" as `you@gmail.com` → you land on `/auth/link` with an
   explanation, not on `/home`.
3. Enter the **wrong** password → 401 shown inline, and the account is unchanged in
   `psql` (`oauth_subject` still NULL).
4. Enter the right one → you land on `/home`, logged in, and the row now has
   `oauth_provider = "google"` with `oauth_subject` set. `has_password` is still `true`
   — you can now sign in **both** ways. Check both.
5. Repeat the flow but click **Cancel** → back on `/login`, cookie cleared, account
   untouched.
6. Start the flow, wait six minutes, then submit → `link_expired`, and the page invites
   you to start again.
7. Visit `/auth/link` directly with no cookie → the expired/invalid state, not a crash.
