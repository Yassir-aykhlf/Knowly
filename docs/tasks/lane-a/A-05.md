# [A-05] A user can see their own account and change their password without being logged out

**Lane:** A — Identity & Access
**Task ID:** A-05
**Size:** ~0.5–1 day
**Depends on:** **A-01**.
**Blocks:** A-08, A-09, A-10, A-11 (they all extend `/api/users/me`), and A-12.

---

## Problem

`GET /api/users/me` exists only as whatever stub A-01 needed to run its tests, and
there is no way to change a password. A user who suspects their password is
compromised has no recourse, and no way to kick other devices off their account.

## Proposed outcome

A proper `GET /api/users/me`, and a password change that logs out **every other**
session while keeping the caller signed in on the device they're using.

## Acceptance criteria

### `GET /api/users/me`

- [ ] Requires auth (401 otherwise) and returns the caller's `UserMeOut` —
      `{ id, email, username, bio, avatar_url, role, created_at, is_anonymized, has_password }`.

### `PUT /api/users/me/password`

- [ ] Body `{ current_password, new_password }`.
- [ ] `new_password` is re-validated (8–128, at least one letter and one digit) →
      **400** with `fields.new_password` on failure.
- [ ] If the account has **no password** (Google-only) or `current_password` is wrong →
      **401 `invalid_credentials`** with
      `fields: { current_password: "Incorrect password" }`.
- [ ] On success: store the new bcrypt hash, **invalidate every other session for this
      user while keeping the caller's current one**, and return **204**.

## Out of scope

* Editing username or bio — A-08 (also `PUT /api/users/me`, but a different route).
* Avatars (A-09), heartbeat (A-10), deletion (A-11) — all separate tasks on the same
  `/users/me` prefix.
* The Settings page UI — A-12.
* Password reset by email. Not in this project.

## The tests that grade this task

```bash
docker-compose exec backend pytest tests/lane_a/test_a05_me_and_password.py -v
```

Four tests.

| Test | What it pins down | AC |
|---|---|---|
| `test_get_me_returns_own_record` | **200** and the body contains at least `id, email, username, role, has_password, is_anonymized` | `UserMeOut` |
| `test_password_change_wrong_current_is_401` | **401** and `error.fields["current_password"]` is truthy | wrong password |
| `test_password_change_validates_new_password` | a 5-char new password → **400** with `"new_password"` in `fields` | validation |
| `test_password_change_invalidates_other_sessions_but_keeps_current` | opens a **second** client with a second real session, changes the password on the first, then asserts client 1 still gets **200** from `/me` while client 2 gets **401** | session invalidation |

That last test is the interesting one, and it's why A-01 had to give you
`delete_other_sessions(user_id, keep_id)`. It builds the second session with
`factory.session_token(user)` and sets the `knowly_session` cookie by hand — worth
reading if you ever need two identities in a test of your own.

**Not graded here, but still required:** the Google-only account case (no password set
→ 401, same shape), and the exact `"Incorrect password"` message.

## Technical notes

**Constraints (requirements, not suggestions):**
* Keep the caller's session. Logging someone out of the tab they're actively using,
  right after they did something security-conscious, reads as "it broke".
* Re-validate `new_password` server-side. The client checks it too (A-04), but client
  checks are a convenience, never a control.
* Reuse `UserMeOut` from A-02 rather than declaring a second, slightly different shape.

**Files you will probably touch:**
* `backend/app/routers/users.py`, `backend/app/schemas/user.py`,
  `backend/app/services/security.py`, `backend/app/services/session.py`.

**Suggested approach:**
1. `GET /me` is three lines given A-01's dependency.
2. Password change: validate new → verify current (401 on missing hash **or** mismatch,
   same response) → hash → `delete_other_sessions(user.id, keep_id=current_session.id)`
   → commit → 204.
3. You need the *current session object*, not just the user, to know which one to keep.
   If your A-01 dependency only returns the `User`, add a small dependency that returns
   the session too rather than re-reading the cookie here.

**Words you'll meet in this ticket:**
* **Session invalidation** — deleting stored sessions so their cookies stop working.
  The standard response to "my password may have leaked".
* **Re-validation** — checking on the server what the client already checked. Always.

## Verify it yourself

```bash
docker-compose exec backend pytest tests/lane_a/test_a05_me_and_password.py -v
```

By hand, with the **same account logged in twice** (normal window + private window):
1. `GET /api/users/me` in both → 200.
2. Change the password in window 1 → 204.
3. Reload window 1 → still logged in. Reload window 2 → **logged out**.
4. Check `psql`: exactly one `sessions` row for that user.
5. Log in with the old password → 401. With the new one → 200.
6. Try changing the password on a Google-only account → 401 with
   `fields.current_password`, not a 500.
