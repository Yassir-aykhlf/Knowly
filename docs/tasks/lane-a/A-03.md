# [A-03] A returning user can log in, and log out again, without leaking who is registered

**Lane:** A — Identity & Access
**Task ID:** A-03
**Size:** ~0.5–1 day
**Depends on:** **A-01**.
**Blocks:** A-04 (the login page).

---

## Problem

Accounts can be created but not returned to. Close the tab and the session is
unreachable; there is also no way to end a session deliberately, which means a shared
machine keeps you logged in forever.

## Proposed outcome

`POST /api/auth/login` and `POST /api/auth/logout`. Login is deliberately vague about
*why* it failed, so the API can't be used to discover which email addresses have
accounts.

## Acceptance criteria

### Login

- [ ] Body `{ email, password }`; look up the user by exact email.
- [ ] **Every** failure returns the **same** response — **401 `invalid_credentials`**,
      message "Invalid email or password", with `fields: { oauth_hint: "true" }` — for
      all three cases:
  - [ ] the email isn't registered,
  - [ ] the account is Google-only (`password_hash is null`),
  - [ ] the password is wrong.
- [ ] That identical response is a **hard requirement**: it must be impossible to tell
      from the API whether an email exists or is Google-only.
- [ ] On success: create a session (A-01), set the cookie, return **200** `UserMeOut`.

### Logout

- [ ] Reads the cookie and deletes that session row if it exists.
- [ ] **Idempotent** — a caller with no session still gets a success, never an error.
- [ ] Clears the cookie and returns **204**.

## Out of scope

* The login **page** and the "if you signed up with Google" hint text — A-04 renders
  those; you just supply `oauth_hint`.
* Google sign-in itself — A-13.
* Password change (A-05), account deletion (A-11).
* Rate-limiting login attempts. Not in this project.

## The tests that grade this task

```bash
docker-compose exec backend pytest tests/lane_a/test_a03_login_logout.py -v
```

Five tests.

| Test | What it pins down | AC |
|---|---|---|
| `test_login_success_sets_cookie` | **200**, the right `username` in the body, and `"knowly_session" in r.cookies` | happy path |
| `test_login_wrong_password_is_generic_with_oauth_hint` | **401**, `error.code == "invalid_credentials"`, and `error.fields["oauth_hint"] == "true"` — note it's the **string** `"true"`, not a JSON boolean | generic failure |
| `test_login_unknown_email_is_indistinguishable` | an email that was never registered → the **same** 401 `invalid_credentials` | no enumeration |
| `test_oauth_only_account_cannot_password_login` | a user with `password=None` and `oauth_provider="google"` → the **same** 401 | no enumeration |
| `test_logout_clears_session_and_is_idempotent` | logout → **204**; afterwards `/api/users/me` is 401; **logging out again is still 204** | idempotent logout |

Read the three failure tests together — they exist as three separate tests precisely
because the temptation is to return three different helpful messages. Helpful here
means "tells an attacker which emails are worth attacking".

**Not graded here, but still required:** the exact message string, and that logout
actually deletes the `sessions` row rather than only clearing the cookie (the test
clears cookies client-side, so a server that kept the row would still pass).

## Technical notes

**Constraints (requirements, not suggestions):**
* One failure path, one response. Build the 401 once and `raise` it from every branch —
  that's the easiest way to guarantee they can't drift apart.
* Verify the password **even when the user doesn't exist**, or at least don't return
  early in a way that makes the unknown-email case measurably faster. Timing is a leak
  too, and comparing against a dummy hash costs you nothing.
* Logout never errors. A user clicking "log out" on an expired session should not see
  a red toast.

**Files you will probably touch:**
* `backend/app/routers/auth.py`, `backend/app/schemas/auth.py`,
  `backend/app/services/security.py` (password verify).

**Suggested approach:**
1. Login: fetch by email → if no user, or no `password_hash`, or `verify()` fails →
   raise the one shared 401. Otherwise session + cookie + `UserMeOut`.
2. Logout: `get_optional_user`-style cookie read → delete row if found → clear cookie →
   204. Note it must **not** depend on `get_current_user`, or logging out twice 401s.

**Words you'll meet in this ticket:**
* **User enumeration** — probing an API to discover which accounts exist, usually as
  step one of a targeted attack. The identical-response rule is the defence.
* **Idempotent** — doing it twice has the same effect as once. Logout must be.
* **`oauth_hint`** — a flag the frontend uses to show "if you signed up with Google, use
  the Google button". It is sent on **every** failure, so it hints at a possibility
  without confirming anything about this specific email.

## Verify it yourself

```bash
docker-compose exec backend pytest tests/lane_a/test_a03_login_logout.py -v
```

By hand:
1. Log in correctly → 200 + cookie; `GET /api/users/me` works.
2. Log in with the wrong password, with an unregistered email, and with a Google-only
   account. **Compare the three responses byte for byte** — status, code, message and
   `fields` must be identical.
3. Log out → 204. `GET /api/users/me` → 401. Check `psql`: the `sessions` row is gone.
4. Log out again with no cookie → still 204.
