# [A-02] A visitor can create an account and is logged in immediately

**Lane:** A — Identity & Access
**Task ID:** A-02
**Size:** ~1 day
**Depends on:** **A-01** (sessions). Also uses the admin-role rule owned by **D-06** —
copy the four-line stub below and swap it when D ships.
**Blocks:** A-04 (the register page), and everyone's ability to create a second test
account by hand.

---

## Problem

There is no way to create an account. Every test of every feature in every lane has to
insert users directly into the database with `psql`, and nobody can demonstrate the app
to anyone without that trick.

## Proposed outcome

`POST /api/auth/register` validates the input, refuses duplicates with a precise
message about which field collided, creates the account with a properly hashed
password, and logs the new user straight in.

## Acceptance criteria

- [ ] Body `{ email, username, password }`.
- [ ] Validation → **400 `validation_error`** with a `fields` map:
  - [ ] `email` must be a valid email address.
  - [ ] `username` 3–30 characters of `[A-Za-z0-9_-]`.
  - [ ] `password` 8–128 characters with **at least one letter and one digit**.
- [ ] Uniqueness → **409 `conflict`** with a `fields` map naming exactly which field(s)
      collided: `email: "Email already registered"`,
      `username: "Username already taken"`. **Both can appear at once** when both are
      taken — don't stop at the first.
- [ ] On success: hash the password with **bcrypt, rounds=12**, create the user, create
      a session (A-01), set the cookie, and return **201**.
- [ ] The response body is `UserMeOut` =
      `{ id, email, username, bio, avatar_url, role, created_at, is_anonymized, has_password }`.
      **`password_hash` never appears in any response.**
- [ ] `has_password` is derived (`password_hash is not null`) — it is `true` here.
- [ ] **Admin bootstrap:** if the lowercased email equals `INITIAL_ADMIN_EMAIL`, the new
      user's `role` is `"admin"`, otherwise `"user"`.

## Out of scope

* Login and logout — A-03.
* The registration **page** — A-04. This is the endpoint only.
* Email verification, password-reset flows, CAPTCHA. Not in this project.
* Google sign-up — A-13.
* Owning the admin rule. You use it; **D-06** owns it. Until they ship, use this local
  stub and mark it:

```python
def is_initial_admin(email: str) -> bool:  # STUB: swap for D-06 helper
    admin = settings.INITIAL_ADMIN_EMAIL
    return bool(admin) and email.lower() == admin.lower()
```

## The tests that grade this task

```bash
docker-compose exec backend pytest tests/lane_a/test_a02_registration.py -v
```

Four tests.

| Test | What it pins down | AC |
|---|---|---|
| `test_register_creates_account_and_logs_in` | **201**; body carries `email`, `username`, `role == "user"`, `has_password is True`, `is_anonymized is False`; **neither `password` nor `password_hash` is present**; and `"knowly_session" in r.cookies` | happy path + auto-login |
| `test_register_rejects_bad_username_and_password` | a 2-char username → **400** with `error.code == "validation_error"` and `"username"` in `fields`; a digitless password → **400** with `"password"` in `fields` | validation |
| `test_register_conflict_reports_each_field` | registering with a taken email **and** a taken username → **409** with **both** keys in `fields` | uniqueness |
| `test_register_admin_bootstrap_by_email` | monkeypatches `settings.INITIAL_ADMIN_EMAIL`, registers that email → `role == "admin"` | admin bootstrap |

Two things this file quietly requires:

* The last test **monkeypatches the settings object at runtime**. So read
  `settings.INITIAL_ADMIN_EMAIL` **inside** your function — if you capture it into a
  module-level constant at import time, the patch won't be seen and the test fails.
* The conflict test asserts both keys at once. A `return` after the first collision
  passes neither.

**Not graded here, but still required:** bcrypt rounds=12 specifically, the exact
`fields` message strings, and that the session created here is a real A-01 session
(the test only checks the cookie exists, not that it works).

## Technical notes

**Constraints (requirements, not suggestions):**
* bcrypt with **rounds=12**. Not the library default, not 10.
* The 400-vs-409 split matters: 400 means "you typed something invalid", 409 means
  "what you typed is fine but already belongs to someone".
* `has_password` is computed from the hash — never send the hash to derive it client-side.

**Files you will probably touch:**
* `backend/app/routers/auth.py`, `backend/app/schemas/auth.py`,
  `backend/app/schemas/user.py`, `backend/app/services/security.py` (password hashing).

**Suggested approach:**
1. Write `UserMeOut` first — five other endpoints return it.
2. Validation via Pydantic where it fits; anything Pydantic can't express (the
   letter+digit password rule) as an explicit check that raises the envelope.
3. Do the uniqueness check as **one** query for both fields, then build the `fields`
   map from what came back.
4. Hash, insert, `create_session`, set cookie, commit, return 201.

**Words you'll meet in this ticket:**
* **bcrypt / rounds** — a deliberately slow hash. "Rounds" sets how slow; 12 is the
  project's choice. Slow is the security property.
* **Monkeypatch** — a test temporarily replacing a value at runtime. Relevant because
  it dictates *when* you read settings.
* **User enumeration** — leaking which emails are registered. Registration must say
  "email taken" (there's no way around it), but **login must not** — see A-03.

## Verify it yourself

```bash
docker-compose exec backend pytest tests/lane_a/test_a02_registration.py -v
```

By hand at `https://localhost/api/docs`:
1. Register a fresh account → 201, and a `knowly_session` cookie comes back.
2. Immediately `GET /api/users/me` → 200 with that user. (You are already logged in.)
3. Register the same email **and** username again → 409, `fields` names both.
4. Register with password `password` → 400, `fields.password`.
5. Look at the user row in `psql` — `password_hash` starts with `$2b$12$`.
6. Set `INITIAL_ADMIN_EMAIL` in `.env`, restart, register that email → `role: "admin"`.
