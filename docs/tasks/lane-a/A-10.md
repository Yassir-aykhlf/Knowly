# [A-10] The app knows which users are currently active

**Lane:** A — Identity & Access
**Task ID:** A-10
**Size:** ~0.5 day
**Depends on:** **A-05**.
**Blocks:** **Lane C's friend online dot** (C-07 reads the column you write). Until this
ships, `last_seen` is `NULL` for everyone and every friend reads as offline.

---

## Problem

The `users.last_seen` column exists and nothing ever writes to it. Lane C's friends list
is built to show an online dot and can only ever show everyone as offline.

## Proposed outcome

A heartbeat endpoint plus a hook that calls it while the tab is open, keeping
`last_seen` fresh — cheaply enough that a hundred open tabs don't become a hundred
writes per second.

## Acceptance criteria

- [ ] `POST /api/users/me/heartbeat` performs a **single atomic** statement:
      `UPDATE users SET last_seen = now WHERE id = me AND last_seen < now - 30s`.
- [ ] It **always returns 204**. Inside the 30-second window it updates nothing, and
      that is a success, not an error.
- [ ] Two concurrent beats cannot both win — the throttle is in the `WHERE` clause, not
      in a read-then-write.
- [ ] `useHeartbeat` posts on mount and then on an interval, **only** while the user is
      authenticated **and** the tab is visible.
- [ ] The hook doesn't fire faster than roughly every 30 seconds. Server-side throttling
      is the guarantee, but the client shouldn't lean on it.
- [ ] The hook is mounted somewhere every authenticated page inherits (the app layout),
      not per-page.

## Out of scope

* Deriving and exposing "is online" — that's **Lane C** (C-07), server-side, from the
  column you maintain. You never compute or return an `online` boolean.
* Any UI dot or indicator. Also Lane C.
* "Last active" text on profiles. Not in this project.
* Presence via websockets. Not in this project.

## The tests that grade this task

```bash
docker-compose exec backend pytest tests/lane_a/test_a10_online_status.py -v
```

Two tests, and together they define the whole endpoint.

| Test | What it pins down | AC |
|---|---|---|
| `test_heartbeat_updates_last_seen` | with `last_seen` aged 10 minutes, a beat → **204**, and re-reading the row shows `last_seen` is within the last 30 seconds | the update |
| `test_heartbeat_within_window_is_a_noop_204` | with `last_seen` 5 seconds ago, a beat → **204**, and `last_seen` is **unchanged** (asserted to within 1 second) | the throttle |

The second test is the entire reason the `WHERE last_seen < now - 30s` clause exists.
A naive `UPDATE ... SET last_seen = now()` passes the first test and fails this one.
Both tests call `db.expire_all()` before re-reading — that's the harness dropping its
cached copy of the row so it sees what the endpoint actually committed.

**Not graded here, but still required:** the `useHeartbeat` hook entirely (no pytest
surface) — mounting, the visibility check, and the interval.

## Technical notes

**Constraints (requirements, not suggestions):**
* One statement. Reading `last_seen`, comparing in Python, then writing is two
  round-trips and a race. Put the condition in the `WHERE`.
* Naive UTC (`datetime.utcnow()`), matching the rest of the schema. Lane C compares
  against this column; a timezone mismatch there shows up as everyone being offline.
* Always 204. A throttled beat is not a 429 and not a 304.

**Files you will probably touch:**
* `backend/app/routers/users.py`, `frontend/src/hooks/useHeartbeat.ts` (the file
  already exists — check what's in it), `frontend/src/layouts/AppLayout.tsx`.

**Suggested approach:**
1. The endpoint is one `update()` statement plus `return Response(status_code=204)`.
2. For the hook, look at `hooks/usePolling.ts` first — it already implements
   "run on an interval, pause on a hidden tab, fire once on refocus", which is exactly
   the behaviour you need. Reusing it is likely simpler than writing a second timer.
3. Mount it in `AppLayout` so every authenticated page gets it once.

**Words you'll meet in this ticket:**
* **Heartbeat** — a small periodic "I'm still here" request.
* **Throttle** — an upper bound on how often something may happen. Yours is 30 seconds
  and it lives in the database query.
* **Atomic** — happens as one indivisible step, so two concurrent callers can't
  interleave into a wrong result.
* **No-op** — a call that legitimately does nothing.

## Verify it yourself

```bash
docker-compose exec backend pytest tests/lane_a/test_a10_online_status.py -v
```

By hand:
1. Set your `last_seen` to an hour ago in `psql`, call the endpoint → 204, and the
   column jumps to now.
2. Call it again immediately → 204, and the column **doesn't move**.
3. Open the app and watch the network tab for two minutes → roughly one heartbeat every
   30 seconds, no faster.
4. Switch to another tab for two minutes → **zero** heartbeats while hidden. Come back →
   it resumes.
5. Log out → heartbeats stop entirely.
6. Once C-07 exists: have a friend's tab open and confirm their dot goes green, then
   close their tab and confirm it goes grey within about two minutes.
