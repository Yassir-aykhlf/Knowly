# [B-07] An author can revise or remove their own answer

**Lane:** B — Q&A Core
**Task ID:** B-07
**Size:** ~1 day
**Depends on:** **B-06**.
**Blocks:** B-13's edit and delete controls.

---

## Problem

Answers are write-once. A wrong answer stays wrong and a held answer can never be fixed.
Deleting one is worse than impossible — if it were possible today it would leave its
comments and votes behind as orphans, and could leave a question pointing at an accepted
answer that no longer exists.

## Proposed outcome

`PUT /api/answers/{id}` and `DELETE /api/answers/{id}` — author-only, re-screened on
edit, and cleaning up every dangling reference on delete.

## Acceptance criteria

### Edit

- [ ] Author-only (`load_owned` → 404 / 403). Body 30–30 000.
- [ ] **Re-screen** the new body; the fresh verdict replaces the old status.
- [ ] Newly-added `@mentions` fire on approval; ones already notified are deduplicated by
      C-01 — so adding a name to an existing answer pings **only the new person**.
- [ ] If the answer was **already approved**, an edit **after the grace window**
      (`EDIT_NOTIFICATION_GRACE_SECONDS`, 300 s) also notifies the question author with
      `content_edited`. Fixing your own typo thirty seconds later stays silent.
- [ ] Re-bind attachments. Return the refreshed `AnswerOut`.

### Delete

- [ ] Author-only.
- [ ] If the answer was **approved**, stage a `content_deleted` notification to the
      question author **before** removing the row. Held or rejected content was never
      visible to them, so its removal is not an event.
- [ ] Clear any question's `accepted_answer_id` that points at this answer.
- [ ] Cascade the answer's comments, votes and attachments.
- [ ] Delete the answer, commit, then remove the files. Return **204**.

## Out of scope

* Editing questions (B-05) or comments (B-09).
* An edit history. `updated_at` is the whole feature.
* Admin removal of someone else's answer — moderators reject (D-07), they don't delete.

## The tests that grade this task

```bash
docker-compose exec backend pytest tests/lane_b/test_b07_edit_delete_answer.py -v
```

Three tests.

| Test | What it pins down | AC |
|---|---|---|
| `test_edit_answer_author_only` | a non-author `PUT` → **403**; the author's → **200** with the new body | ownership |
| `test_delete_answer_removes_it` | **204**, and the `Answer` table is empty afterwards | delete |
| `test_deleting_accepted_answer_clears_pointer` | an accepted answer is deleted → re-reading the question shows `accepted_answer_id is None` | the dangling pointer |

The third test is the one worth reading closely. The schema declares that foreign key as
`ON DELETE SET NULL`, so the database will clear it for you — but the same test note in
B-05 says to clear it manually before deleting a *question*. Know which case you're in:
deleting an **answer** lets the database clean up; deleting a **question** requires you to
clear the pointer first, because you're removing the row that holds it.

**Not graded here, but still required:** re-screening, the grace-window `content_edited`
notification, the approved-only `content_deleted` rule, and the comment/vote/attachment
cascade for the answer. **No test here counts comments or votes after an answer delete** —
B-05's test does it for the question path, but nothing does for this one. Check it
yourself.

## Technical notes

**Constraints (requirements, not suggestions):**
* The grace window comes from `settings.EDIT_NOTIFICATION_GRACE_SECONDS` (300). Read it
  from config; don't hardcode 300.
* "Already approved" is the condition for the edit notification — a pending→approved
  transition reads as *new*, not *edited*, and C-01's `notify_content_edited` is where
  the timing rule lives. Call it; don't reimplement the check.
* Stage the `content_deleted` notification **before** the delete — afterwards you no
  longer know who to tell.

**Files you will probably touch:**
* `backend/app/routers/answers.py`, plus B-01's cascade helpers.

**Suggested approach:**
1. Edit is B-06 with `load_owned` in front and no insert. Reuse the serializer.
2. Delete: load owned → if approved, stage the notification → cascade comments, votes,
   attachments → delete → commit → unlink files.
3. Let the database clear `accepted_answer_id` via `ON DELETE SET NULL`, and confirm it
   actually happened (the test does).

**Words you'll meet in this ticket:**
* **Grace window** — a short period after creation during which edits don't notify, so
  typo fixes stay quiet.
* **Dangling pointer** — a reference to a row that no longer exists. Here, a question
  whose accepted answer was deleted.
* **`ON DELETE SET NULL`** — a foreign-key rule that nulls the reference automatically
  when the target row goes.

## Verify it yourself

```bash
docker-compose exec backend pytest tests/lane_b/test_b07_edit_delete_answer.py -v
```

By hand:
1. Edit someone else's answer → 403. Your own → 200.
2. Give an answer two comments and two votes, then delete it → 204, and in `psql`
   **both comments and both votes are gone**.
3. Accept an answer, then delete it → the question's `accepted_answer_id` is `NULL` and
   the detail page renders with nothing accepted.
4. Once C-01 has shipped: edit an approved answer **within** 300 s of creating it → the
   asker gets nothing. Backdate its `created_at` in `psql`, edit again → they get
   `content_edited`.
5. Delete an approved answer → the asker gets `content_deleted`. Delete a **pending** one
   → they get nothing.
