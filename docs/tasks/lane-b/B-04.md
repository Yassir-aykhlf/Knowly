# [B-04] Opening a question shows it with its answers, comments and scores in one request

**Lane:** B — Q&A Core
**Task ID:** B-04
**Size:** ~1.5 days
**Depends on:** **B-01**. Reads `files.attachments_for` (**D-09**, stub).
**Blocks:** B-05, B-06, B-09, B-13 — and Lane D's "use as answer" flow.

---

## Problem

There's no way to read a question. The detail page is the busiest screen in the app — it
needs the question, its answers in the right order, comments nested in two places, each
post's score, the viewer's own votes, and attachments. If the client had to assemble that
from six endpoints, the page would flicker its way into existence.

## Proposed outcome

`GET /api/questions/{id}` — one request that returns everything the question page
renders, already sorted, already filtered to what this particular viewer may see.

## Acceptance criteria

- [ ] Missing **or** not viewable (per `can_view`) → **404 `not_found`**. A held question
      is invisible to non-authors, and 404 rather than 403 so its existence doesn't leak.
- [ ] **View count:** best-effort increment of `view_count` that must **not** bump
      `updated_at` — a view is not an edit. A failure to increment must not fail the
      request.
- [ ] Returns `QuestionOut = { id, title, body, tags, author, view_count, vote_total,
      my_vote, accepted_answer_id, moderation_status, moderation_note, created_at,
      updated_at, answers[], comments[], attachments[] }`.
- [ ] `answers`: only the ones this viewer may see. Each is an `AnswerOut` with its own
      `vote_total`, `my_vote`, its visible `comments[]` and `attachments[]`.
- [ ] **Answer sort: accepted first, then highest `vote_total`, then oldest first.**
- [ ] `comments`: question-level comments (visible only), oldest first. Answer-level
      comments are nested under their answer, not in this array.
- [ ] `my_vote` reflects the viewer's own vote everywhere it appears; `0` for anonymous.
- [ ] `moderation_note` reaches the client only because the viewer is the author or an
      admin — a stranger never receives a non-approved row in the first place.

## Out of scope

* Editing, deleting, answering, commenting, voting — B-05 through B-10.
* The detail **page** — B-13.
* Attachment storage rules — D-09. Until they ship: `attachments_for → {}`, marked
  `# STUB: swap for D-09`.
* A separate "answers" endpoint with its own pagination. Answers come with the question.

Four tests.

| Test | What it pins down | AC |
|---|---|---|
| `test_detail_sorts_accepted_answer_first` | an accepted answer with **zero** votes still comes before an up-voted one — `answers[0]` is the accepted one, `answers[1]` is the popular one with `vote_total == 1` | the sort |
| `test_detail_increments_view_count` | two consecutive GETs → the second reports exactly `first + 1` | view count |
| `test_held_question_is_404_for_strangers_but_visible_to_author` | a stranger gets **404**; the author gets **200** with `moderation_status == "pending"` | visibility |
| `test_missing_question_is_404` | a random UUID → **404** | not found |

The first test is designed to fail a sort that puts votes before acceptance — the
accepted answer deliberately has no votes at all, so any "order by votes, accepted as a
tiebreak" implementation gets it backwards.

**Not graded here, but still required:** the `updated_at` rule (nothing checks that a
view doesn't bump it), the oldest-first tiebreak among answers, comment nesting and
ordering, `my_vote` for a logged-in viewer, and `attachments` (stubbed empty).

## Technical notes

**Constraints (requirements, not suggestions):**
* Increment `view_count` with a targeted `UPDATE ... SET view_count = view_count + 1`,
  not by loading the object and mutating it — ORM flushes will touch `updated_at` via the
  model's `onupdate`, and then every view looks like an edit in the UI.
* 404 for held content, never 403. The point is that strangers can't tell it exists.
* One serializer, shared with B-02 and B-05. Three copies of this payload will drift.

**Files you will probably touch:**
* `backend/app/routers/questions.py`, `backend/app/schemas/{question,answer,comment}.py`.

**Suggested approach:**
1. Load the question, `can_view` check, 404.
2. Load visible answers, then **all** comments for the question and those answers in one
   query, then vote totals and viewer votes for both target types in two more.
3. Assemble in Python: bucket comments by `(parent_type, parent_id)`, attach votes, sort
   answers with a key like `(not is_accepted, -vote_total, created_at)`.
4. The `view_count` bump last, as a separate statement wrapped so a failure is swallowed.

**Words you'll meet in this ticket:**
* **Assembled payload** — one response built from several tables so the client makes one
  request.
* **Best-effort** — try it; if it fails, carry on. The view counter is best-effort;
  the question body is not.
* **Sort key** — the tuple you sort by. `(not accepted, -votes, created_at)` reads as
  "accepted first, then most votes, then oldest".

## Verify it yourself

```bash
docker-compose exec backend pytest tests/lane_b/test_b04_question_detail.py -v
```

By hand:
1. Build a question with three answers: one accepted with 0 votes, one with +5, one with
   0. Fetch → accepted, then +5, then the last. Add a fourth with 0 votes → it sorts
   after the older 0-vote answer.
2. Note `updated_at`, fetch the question five times, check `psql` → `view_count` rose by
   5 and `updated_at` **did not move**.
3. Comment on the question and on an answer → the first is in the top-level `comments`,
   the second is nested inside its answer.
4. Vote on an answer, fetch as that user → `my_vote: 1`. Fetch logged out → `my_vote: 0`.
5. Set the question to `pending` → author sees it with the note; a stranger gets 404.
6. Set one **answer** to `pending` → it vanishes for strangers but the question still
   renders.
