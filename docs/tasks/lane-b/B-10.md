# [B-10] A user can vote content up or down, but not their own

**Lane:** B — Q&A Core
**Task ID:** B-10
**Size:** ~0.5–1 day
**Depends on:** **B-01**. Calls `notify_vote_if_new` (**C-01**, stub).
**Blocks:** B-14's `<VoteArrows>`, and the `votes` sort in B-03.

---

## Problem

Every payload in the app reports a `vote_total` and a `my_vote`, and both are always
zero because nothing can cast a vote. Ranking, the `votes` sort, and the whole signal of
"this answer is the good one" are inert.

## Proposed outcome

`POST /api/questions/{id}/vote` and `POST /api/answers/{id}/vote` — one vote per person
per target, self-voting refused, and the recomputed totals returned so the UI can settle
on the truth.

## Acceptance criteria

- [ ] Auth required. The target must exist **and be viewable** → **404** otherwise.
- [ ] Body `{ value: -1 | 0 | 1 }`, where `0` clears the caller's vote.
- [ ] **Self-voting is blocked**: voting on your own question or answer → **400
      `self_vote`**.
- [ ] Stage the coalesced vote notification for the caller's **first** vote on this
      target — and do it **before** applying the vote, so C-01 can still see the
      pre-vote state and tell "first vote" from "changed my mind".
- [ ] Vote **changes** (`+1 → -1`) and **removals** (`0`) are silent, and the event never
      reveals direction.
- [ ] Apply the vote and return `{ vote_total, my_vote }` **recomputed from the table**.

## Out of scope

* The arrows themselves — B-14.
* Vote-count denormalisation. Totals are aggregated on read, always (B-01).
* Voting on comments. Not in this project.
* Rate-limiting or serial-downvote detection. Not in this project.

## Technical notes

**Constraints (requirements, not suggestions):**
* Order matters: notify first, then apply. `notify_vote_if_new` decides "is this their
  first vote?" by looking for an existing row in `votes` — insert yours first and it will
  always see one and never notify.
* Self-vote is 400 `self_vote`, a custom code. The envelope allows extra codes as long as
  the status is right (foundation §4.1).
* `apply_vote` (B-01) commits. Don't wrap it in another transaction expecting to roll it
  back.

**Files you will probably touch:**
* `backend/app/routers/{questions,answers}.py`, `backend/app/schemas/vote.py`.

**Suggested approach:**
1. One shared handler taking `target_type`, with two thin routes calling it.
2. Load target → `can_view` → 404. Compare `author_id` to the caller → 400 `self_vote`.
3. `notify_vote_if_new(...)` (stub for now) → `apply_vote(...)` → return its two fields.

**Words you'll meet in this ticket:**
* **Coalesced notification** — many votes folding into one "N people voted" row. C-01
  does the folding; you just call it once per vote.
* **Direction-neutral** — the notification never says up or down. Being told someone
  downvoted you is a fight; being told someone voted is information.
* **Recomputed total** — read back from the `votes` table rather than adjusting a
  counter. Slower, always right.

## Verify it yourself

```bash
docker-compose exec backend pytest tests/lane_b/test_b10_voting.py -v
```

By hand:
1. Vote +1 on someone's question → `{vote_total: 1, my_vote: 1}` and **exactly** those
   keys.
2. Vote -1 on the same target → `{-1, -1}`, and `psql` shows **one** row in `votes`.
3. Vote 0 → `{0, 0}` and the row is gone.
4. Vote on your own question and your own answer → 400 `self_vote` both times.
5. Vote on a `pending` answer as a stranger → 404.
6. Have three people vote the same answer up → `vote_total: 3`; each sees their own
   `my_vote: 1`; a logged-out viewer sees `my_vote: 0`.
7. Once C-01 has shipped: one voter voting, changing, and clearing produces **exactly
   one** notification, and it doesn't say which direction.
