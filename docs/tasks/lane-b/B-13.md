# [B-13] A user can read a question and take part in it — answer, comment, vote, accept

**Lane:** B — Q&A Core
**Task ID:** B-13
**Size:** ~2–2.5 days — the busiest screen in the app
**Depends on:** **B-04**, **B-06**, **B-08**, **B-09**, **B-10**, and `<VoteArrows>`
(**B-14** — build that first). Mounts `<AttachmentList>` (**D-10**, stub) and reads the AI
prefill from **D-05**.
**Blocks:** integration milestone 8 (the AI "use as my answer" hand-off lands here).

---

## Problem

`/questions/:id` renders a placeholder. Every endpoint this lane has built — detail,
answers, comments, votes, accept — is unreachable from the app, and there is no screen
where a user can actually participate in a discussion.

## Proposed outcome

The question page: the question, its answers in the server's order, comments in both
places, working vote arrows, an accept control for the asker, composers for answers and
comments, and honest banners for the author when their post is held.

## Acceptance criteria

- [ ] Renders the question, its comments, and its answers **in the server-sorted order**
      (accepted first — don't re-sort on the client).
- [ ] Each post shows author, timestamps, an **"edited" marker** when
      `updated_at > created_at`, and an **AI-assisted badge** where the answer carries it.
- [ ] **Voting** via `<VoteArrows>` (B-14) with optimistic updates, **disabled on the
      viewer's own posts** with a tooltip explaining why.
- [ ] **Accept:** the question's author sees an Accept control on each **approved**
      answer; accepting or clearing updates the UI and floats the accepted answer to the
      top. Everyone else sees the accepted state read-only.
- [ ] **Composers:** an answer composer (self-answering is allowed — don't hide it from
      the asker) and a comment composer per post, each with live length validation.
      Posting reloads the affected part so votes and comments re-sync.
- [ ] **Moderation banners, author-facing only:** when the viewer is the author and a post
      is `pending` show "held for review"; when it's `rejected` show the
      `moderation_note`. Other viewers never receive held or rejected posts at all, so
      they need no handling.
- [ ] **AI prefill:** when navigated to with router state
      `{ prefillBody, fromConversationId, isAiAssisted }` (emitted by D-05's "Use this as
      my answer"), preload the answer composer with that body and submit it with
      `is_ai_assisted: true` and `from_conversation_id`. Until D-05 ships, handle the
      "no state" case — which is every case.
- [ ] Render `<AttachmentList>` under each post (empty until D-10).

## Out of scope

* Any backend change. Every behaviour here already has an endpoint; if something's
  missing, that's a conversation with the owning task.
* Building `<VoteArrows>` or `<MarkdownBody>` — B-14.
* Building `<AttachmentList>` (D-10) or the AI page that emits the prefill (D-05).
* Editing posts inline. Editing a question goes to B-12's page.
* Real-time updates. A reload after your own action is the design.

## The tests that grade this task

**There is no `test_b13_*.py`** — React pages have no pytest surface in this project. Six
backend test files define what this page renders and calls, and must stay green:
`test_b04_question_detail.py` (the payload and its sort), `test_b06_create_answer.py`,
`test_b08_accept_answer.py`, `test_b09_comments.py`, `test_b10_voting.py` — plus
`tests/milestones/test_m8_ai_answer.py`, which asserts that an answer submitted from the

## Technical notes

**Constraints (requirements, not suggestions):**
* Render answers in the order the server sent them. B-04 sorts accepted-first,
  then votes, then oldest — re-sorting client-side will disagree with it eventually.
* Own-post vote arrows are **disabled**, not hidden. A user should see why they can't
  vote, not wonder where the buttons went.
* The moderation banner is author-facing only. You never need a "this post was rejected"
  state for other viewers, because they never receive the post.
* Use the `api` wrapper; `Question`, `Answer`, `Comment` types are frozen in
  `lib/types.ts`.

**Files you will probably touch:**
* `frontend/src/pages/QuestionDetailPage.tsx` — replace the `<Placeholder>`.
* `frontend/src/components/{VoteArrows,MarkdownBody,AttachmentList,Avatar}.tsx` — the
  first two are yours from B-14; the last two are read-only.

**Suggested approach:**
1. Read-only first: fetch the payload and render question, answers, comments. No actions
   at all. That's half the ticket and it's where the layout work is.
2. Then voting, since `<VoteArrows>` already handles its own optimism (B-14) — you just
   pass `total`, `myVote`, and `disabled`.
3. Then the composers. Post → refetch the question → re-render. Simple and correct;
   optimise later if it feels slow.
4. Then accept, then the banners.
5. The AI prefill last: `useLocation().state`, guarded for `null`, feeding the composer's
   initial value. Test it by navigating with `navigate(url, { state: {...} })` from a
   scratch button before D-05 exists.

**Words you'll meet in this ticket:**
* **Router state** — data passed through a navigation without putting it in the URL. How
  D-05 hands you a draft answer.
* **Optimistic update** — changing the UI before the server confirms. `<VoteArrows>` does
  this internally.
* **Server-sorted** — the order is decided by the API; the client renders it as given.

## Verify it yourself

Use **three** accounts: the asker, an answerer, and an uninvolved stranger.

1. As the stranger: the question renders with answers accepted-first, comments in both
   places, vote arrows enabled, and **no** accept control.
2. As the answerer: the arrows on **your own** answer are disabled with a tooltip; the
   arrows on the question are enabled.
3. As the asker: an Accept control on each approved answer. Accept one → it floats to the
   top and is marked. Accept another → the mark moves. Clear it → gone.
4. Post an answer to **your own** question → allowed.
5. Post a comment on the question and on an answer → each lands in the right place after
   the reload.
6. Vote on an answer → the number moves immediately, then settles on the server's value.
   Stop the backend and vote → it reverts and toasts.
7. Edit an answer, reload → the "edited" marker appears.
8. Set a post to `pending` in `psql` → the **author** sees the held banner; the stranger
   gets a page without that post at all.
9. Navigate in with router state (hand-rolled until D-05 exists) → the composer is
   prefilled and the submitted answer comes back `is_ai_assisted: true`.
