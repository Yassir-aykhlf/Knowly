# [B-01] There is one place that decides who can see a post, who owns it, and what it scored

**Lane:** B — Q&A Core
**Task ID:** B-01
**Size:** ~1.5–2 days
**Depends on:** nothing. Start here on day 1.
**Blocks:** every other task in your lane — **and three other people.** A-06/A-07,
D-07, D-09 and D-11 all read content through this service (integration milestone 2).

---

## Problem

Four lanes need to answer the same questions about content — *may this person see this
post? do they own it? what's its score? what happens to its comments when it's deleted?*
Right now everyone has a stub that says "approved only, `can_view` → True". If each lane
answers those questions its own way, the app will disagree with itself about what's
visible, which is a privacy bug, not a style difference.

## Proposed outcome

`services/content.py` — the single source of truth for visibility, ownership, vote
aggregation, and the polymorphic cascades. Lane A's profile counts, Lane D's moderation
queue, file rules and search all import it and delete their stubs.

## Acceptance criteria

### Visibility

- [ ] `visible_filter(model, user)` returns a **SQL predicate**: `moderation_status ==
      'approved'`, **OR** (when a user is present) `author_id == user.id`, **OR** (when
      that user is an admin) everything.
- [ ] `can_view(obj, user)` is the in-Python mirror of the same rule for a single loaded
      row.
- [ ] These two are the only definition of "who may see this content" in the codebase.

### Ownership

- [ ] `load_owned(db, Model, id, user, kind)` fetches by id and raises
      **404 `not_found`** when missing, **403 `forbidden`** ("Only the author can modify
      this {kind}") when `author_id != user.id`. Every edit and delete route uses it.

### Votes — never denormalised

- [ ] `vote_totals(db, target_type, ids) -> {id: sum(value)}`.
- [ ] `viewer_votes(db, user, target_type, ids) -> {id: my value}`, empty for anonymous.
- [ ] `apply_vote(db, user, target_type, id, value)`:
  - [ ] `value == 0` deletes the caller's vote row.
  - [ ] `±1` **upserts** one row
        (`INSERT ... ON CONFLICT (voter_id, target_type, target_id) DO UPDATE`).
  - [ ] It **commits**, and returns the `vote_total` and `my_vote` **recomputed from the
        table** — not guessed by adding one to a cached number.

### Context and cascades

- [ ] `question_context(db, parent_type, parent_id) -> (question_id, question_author_id,
      parent_author_id)`. A question's parent-author is itself; an answer's is the
      answer's author. Returns `None` if the parent chain is gone.
- [ ] `delete_comments_for(parent_type, ids)` and `delete_votes_for(target_type, ids)` —
      bulk deletes used when a parent is removed.

## Out of scope

* Any HTTP route. This task is a service module; B-02 onward add the endpoints.
* Moderation *decisions* — D-02 decides what gets held. You only read
  `moderation_status`.
* Attachments cascade — `delete_attachments_for` belongs to D-09. You call it.
* Notifications. C-01 owns those; your delete paths call them later (B-05/B-07).

Three details to take from the file before you write anything:

* **`can_view` is called without `await`** — it is a plain synchronous function on an
  already-loaded object. `apply_vote`, `load_owned` and `question_context` are `async`.
* **`apply_vote` returns something with attributes**, not a dict — the test reads
  `up.vote_total` and `up.my_vote`. A Pydantic model or a dataclass; not `{"vote_total": ...}`.
* **A misleading comment.** Above the second `apply_vote` call the test says
  *"Same direction again == clear"* — but the code passes `0`, not `1`. The assertion is
  what counts: **0 clears**. Sending `1` twice is an explicit set to 1. B-10's test says
  so outright: "click again to clear" is a frontend concept. Read code, not comments.

**Not graded here, but still required:** `visible_filter` as a SQL predicate (only its
Python mirror is tested), `vote_totals` / `viewer_votes` batch helpers, the two cascade
functions, and the "commits" behaviour of `apply_vote`.

## Technical notes

**Constraints (requirements, not suggestions):**
* Vote totals are **always aggregated**, never stored on the question or answer row. The
  schema has no `vote_total` column and won't be getting one.
* `apply_vote` is the one function here that commits — it is a complete user action on
  its own. Everything else in this module stages.
* Comments, votes and attachments use a `parent_type`/`parent_id` pair with **no SQL
  foreign key**, which is why deletion has to cascade in application code. That's what
  the two `delete_*_for` helpers are for.

**Files you will probably touch:**
* `backend/app/services/content.py` — replace the stub bodies.
* `backend/app/models/{question,answer,comment,vote}.py` — read only.

**Suggested approach:**
1. `can_view` and `visible_filter` first — they're the smallest and everything else
   composes them. Write them as a pair so they can't drift.
2. `load_owned` next; it's five lines and two raises.
3. Vote helpers: `vote_totals` as a `GROUP BY` returning a dict, then `apply_vote` on top
   of it. SQLAlchemy's `from sqlalchemy.dialects.postgresql import insert` gives you
   `on_conflict_do_update`.
4. `question_context` and the cascades last.

**Words you'll meet in this ticket:**
* **Seam** — a function another lane imports. This whole module is one.
* **Predicate** — a SQL condition object you can drop into a `.where(...)`. Returning
  one (rather than a bool) is what lets callers filter *queries*, not just rows.
* **Denormalised** — storing a computed value (like a vote total) alongside the source
  data. Fast, and it goes stale. This project deliberately doesn't.
* **Upsert** — "insert, or update if it exists", in one statement.
* **Polymorphic parent** — a row that can point at more than one kind of table, using a
  type-plus-id pair. The database can't enforce it, so your code must.

```bash

```

By hand, in a shell:
1. Build a pending question. Check `can_view` for: anonymous, a stranger, the author, an
   admin → `False, False, True, True`.
2. Run a query with `visible_filter(Question, admin_user)` → it returns pending rows too.
3. Vote +1, then +1 again with the same user → **one** row in `votes`, total still 1.
   Then 0 → the row is gone and the total is 0.
4. Create a comment on an answer, then delete the answer via `delete_comments_for` → the
   comment row is gone.
5. `question_context(db, "comment_parent_that_no_longer_exists")` → `None`, not a crash.
