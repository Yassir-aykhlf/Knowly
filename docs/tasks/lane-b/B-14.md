# [B-14] Post bodies render as formatted text, and votes are one click away

**Lane:** B — Q&A Core
**Task ID:** B-14
**Size:** ~1 day
**Depends on:** nothing (the Launch Pad). **Build `<MarkdownBody>` early** — Lane D's AI
page renders assistant replies with it.
**Blocks:** B-13 (which mounts both), and D-05.

---

## Problem

Every body in the app is stored as Markdown and displayed as raw text, so code blocks,
lists and links all render as literal asterisks and backticks. And there is no vote
control anywhere — B-10's endpoints have no button.

Two small shared components, built once here so B-13, A-12 and D-05 don't each grow their
own.

## Proposed outcome

`<MarkdownBody>` renders post bodies safely, and `<VoteArrows>` handles the whole vote
interaction — optimistic update, reconcile, revert on failure — so pages just pass props.

## Acceptance criteria

### `<MarkdownBody markdown>`

- [ ] Renders Markdown to **sanitized** HTML: no raw HTML injection, and links that are
      safe to click.
- [ ] Used for question, answer and comment bodies, and for AI replies (D-05).
- [ ] Inline images pointing at `/api/files/:id` (attachments) render in place.

### `<VoteArrows targetType targetId total myVote disabled? disabledReason?>`

- [ ] Up and down buttons around the current total.
- [ ] Clicking a direction sets that vote; **clicking the active direction again clears
      it** (sends `value: 0`). This toggle is a frontend concept — the API has no
      "toggle", so translate it here.
- [ ] Updates are **optimistic**: adjust the total and `myVote` immediately, POST, then
      **reconcile** with the server's returned `{ vote_total, my_vote }`.
- [ ] On error: **revert** to the previous state and toast the message.
- [ ] `disabled` (the viewer's own post) greys both arrows and shows `disabledReason` on
      hover.
- [ ] While a vote is in flight, further clicks are **ignored** — no double-submits.
- [ ] Re-syncs when the parent passes fresh `total` / `myVote` (for example after B-13
      reloads the detail payload).

## Out of scope

* The vote endpoints — B-10.
* A Markdown **editor** or preview toolbar — B-12 owns the ask form.
* Rendering attachments as a list — that's `<AttachmentList>` (D-10). You only handle
  inline image links inside a body.
* Comment voting. Not in this project.

## Technical notes

**Constraints (requirements, not suggestions):**
* **Sanitize.** Post bodies are user input rendered into other users' browsers — that is
  the textbook cross-site-scripting path. Use a Markdown renderer with raw HTML disabled,
  or sanitize the output; do not hand-roll either. Check `frontend/package.json` for what
  is already available before adding a dependency.
* Never use `dangerouslySetInnerHTML` on unsanitized output. If you use it at all, the
  string must have been through the sanitizer on the line above.
* Keep `<VoteArrows>` self-contained: it owns its own in-flight state and its own
  revert. Pages pass props and forget about it.

**Files you will probably touch:**
* `frontend/src/components/MarkdownBody.tsx` (new),
  `frontend/src/components/VoteArrows.tsx` (new), `contexts/ToastContext.tsx`.

**Suggested approach:**
1. `<MarkdownBody>` first — it's the one another lane is waiting on.
2. `<VoteArrows>` presentation next: two buttons and a number, driven purely by props.
3. Then the click logic. Save the previous `(total, myVote)` in a local variable, apply
   the optimistic change, POST, and either reconcile with the response or restore the
   saved pair. That saved pair is the entire trick.
4. Then the in-flight guard and the `disabled` state.
5. Re-sync last: a `useEffect` on the incoming props that resets local state when the
   parent hands you new numbers.

**Words you'll meet in this ticket:**
* **XSS (cross-site scripting)** — injecting scripts into a page through content another
  user supplied. What sanitization prevents.
* **Sanitize** — strip anything executable from HTML before rendering it.
* **Optimistic update / reconcile / revert** — change the UI first, replace with the
  server's truth on success, restore the old value on failure.
* **In-flight** — a request that's been sent and hasn't answered. Ignoring clicks while
  one is in flight is how you avoid double-voting.

## Verify it yourself

1. Render a body containing a heading, a list, a fenced code block, a link and
   `**bold**` → all render properly.
2. **The XSS check:** post a question whose body is
   `<img src=x onerror="alert('xss')">` and `<script>alert(1)</script>`, then view it →
   **no alert**, and no live element in the DOM. This must pass before you ship.
3. A body containing `![diagram](/api/files/<some-id>)` renders the image inline.
4. Click the up arrow on someone's answer → the number moves instantly, then settles on
   the server's value (they should agree).
5. Click up **again** → it clears to 0 and `my_vote` is 0.
6. Click up then down fast → one vote lands, the UI matches the server, and no double
   request goes out.
7. Stop the backend, click a vote → the number **reverts** to where it was and a toast
   appears.
8. Render the arrows on your own post → both greyed, tooltip on hover, clicks do nothing.
9. Have the parent reload the detail payload with different totals → the arrows pick up
   the new numbers.
