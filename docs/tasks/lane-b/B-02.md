# [B-02] A user can post a question

**Lane:** B — Q&A Core
**Task ID:** B-02
**Size:** ~1 day
**Depends on:** **B-01**. Calls three seams you don't own — `moderation.screen_and_stage`
(**D-02**), `files.bind_attachments` (**D-09**), notifications (**C-01**). Stubs below.
**Blocks:** everything downstream — you can't answer, comment on, or vote on a question
that can't be created.

---

## Problem

Knowly is a question-and-answer site with no way to ask a question. Every other feature
in the app — answers, votes, comments, search, moderation, attachments — needs question
rows to exist, and today they only appear via `psql`.

## Proposed outcome

`POST /api/questions` — validated, screened by moderation, attachments bound, and
returning the same full detail payload the question page renders.

## Acceptance criteria

- [ ] Auth required (**401** otherwise). Body
      `{ title, body, tags[], attachment_ids[] }`.
- [ ] Validation → **400 `validation_error`** with `fields`:
  - [ ] `title` trimmed, 10–200 characters.
  - [ ] `body` 30–30 000 characters.
  - [ ] at most **5** tags, each trimmed to 2–30 characters; empty tags are dropped
        rather than rejected.
  - [ ] at most **10** `attachment_ids`.
- [ ] The question is owned by the caller.
- [ ] **Screen it** through the moderation hook over the text `"{title}\n\n{body}"`. The
      hook sets `moderation_status` (`approved` or `pending`) and `moderation_note`, and
      stages whatever notifications the verdict implies.
- [ ] Questions have **no owner notification event** — the only person who owns a
      question is the person who just asked it. So approval stages mention notifications
      only; a hold notifies the author that their post is held.
- [ ] Bind the given attachments to this question (D-09's rules apply).
- [ ] Commit, then return **201** with the **full `QuestionOut` detail payload** — the
      same shape B-04 returns, including empty `answers` and `comments` arrays.

## Technical notes

**Constraints (requirements, not suggestions):**
* Screen the title **and** body together as one string — a clean body with an abusive
  title must still be caught.
* Content is born `approved` (the schema's default). Don't write "pending" and wait for
  something to approve it; the hook decides.
* Return the full detail payload. Share one serializer with B-04 rather than writing a
  second one that drifts.

**Files you will probably touch:**
* `backend/app/routers/questions.py`, `backend/app/schemas/question.py`.

**Suggested approach:**
1. Write the `QuestionOut` schema and its serializer first — B-04 and B-05 both reuse it.
2. Validation next. Trim, then check. Collect **all** field errors into one `fields` map
   rather than raising on the first.
3. Insert → `screen_and_stage` (which flushes, so the id exists) → `bind_attachments` →
   commit → serialise.

**Words you'll meet in this ticket:**
* **Screening** — passing text through automated moderation before it becomes public.
* **Staging** — writing rows into the open transaction without committing. The seams you
  call stage; **you** commit.
* **Seam / stub** — a function another lane owns; a fake stand-in with the real signature
  so you can build today.
