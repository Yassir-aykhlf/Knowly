# [C-04] A user can browse their full notification history on a dedicated page

**Lane:** C — Social & Signals
**Task ID:** C-04
**Size:** ~0.5 day — the smallest task in the lane, and a good one to do right after C-03
**Depends on:** **C-02** (the API). Do it **after C-03** so you can reuse
`describeNotification` rather than writing the wording twice.
**Blocks:** nothing.

---

## Problem

The bell dropdown only shows the ten most recent notifications. Anything older is
unreachable — a user who was away for a week can see that something happened but not
what. The route `/notifications` already exists in the router and renders a
placeholder box.

## Proposed outcome

`/notifications` is the full, paginated inbox: every notification the user has ever
received, in the same plain English as the bell, with unread rows standing out and a
one-click way to clear them all.

## Acceptance criteria

- [ ] `NotificationsPage` replaces the placeholder at the `/notifications` route.
- [ ] Lists **all** of the caller's notifications, newest first, paginated via
      `GET /api/notifications?page&limit`.
- [ ] Each row uses the **same** `describeNotification(n)` from C-03 — imported, not
      copy-pasted.
- [ ] Unread rows are **visually distinct** from read ones (background tint, a dot,
      or a weight change — your call, just make it obvious at a glance).
- [ ] Each row shows the actor's avatar and a relative timestamp.
- [ ] Clicking a row marks it read and navigates to `n.link`.
- [ ] A "mark all read" button clears every unread row and updates the page without
      a reload.
- [ ] Empty state: a user with no notifications sees a friendly message, not a blank
      page or a spinner that never stops.
- [ ] Loading and error states exist — a failed fetch says so and offers a retry.

## Out of scope

- Changing the wording function. If a sentence is wrong, fix it in C-03's
  `lib/notifications.ts` so the bell and this page stay in sync.
- Filters, search, tabs ("unread only"), or deleting notifications. Not in this
  project.
- Infinite scroll. Plain pagination is fine and simpler to get right.
- Changing the API.

## Technical notes

**Constraints:**
- Use the `api` wrapper from `lib/api.ts`, not bare `fetch`.
- The response type is `Paginated<AppNotification>` — both already in
  `frontend/src/lib/types.ts`, which is frozen. Don't declare your own.
- `lib/format.ts` already exports `relativeTime(iso)` for the timestamps.

**Files you will probably touch:**
- `frontend/src/pages/NotificationsPage.tsx` — replace the `<Placeholder>`.
- `frontend/src/App.tsx` — the route already exists; you most likely change nothing.

**Suggested approach — a proposal, not a mandate:**
1. Fetch page 1 on mount, render the list, then add the pager.
2. Reuse whatever row markup you wrote for the C-03 dropdown — if it's the same
   three elements (avatar, sentence, time), lift it into a small shared component
   and let both use it. If that turns awkward, duplicating a handful of lines of JSX
   is an acceptable trade; say which you chose in the PR.
3. Empty/loading/error states last, but do not skip them — "it looked broken but was
   just empty" is the single most common bug report on pages like this.

**Words you'll meet in this ticket:**
- **Empty state** — what the screen says when there is legitimately no data. Not an
  error, not a spinner.
- **Pagination** — `page` (starts at 1) and `limit`; the response carries `total` so
  you can work out how many pages there are.

## Verify it yourself

1. Log in as a user with more than one page of notifications (generate them, or
   insert rows with `psql`, or drop `limit` to 5 while testing).
2. Visit `/notifications` → newest first, unread rows obviously different.
3. Page forward and back → the list changes and the URL/state stays sensible.
4. Click a row → it navigates to the right place and no longer looks unread when
   you come back.
5. Click "mark all read" → every row loses its unread styling, and **the header
   bell's badge goes to zero within 30 s** (it re-polls on its own).
6. Log in as a brand-new user → the empty state, not a blank page.
