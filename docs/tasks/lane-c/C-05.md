# [C-05] A user can send someone a friend request, and gets a clear answer when they can't

**Lane:** C — Social & Signals
**Task ID:** C-05
**Size:** ~1 day
**Depends on:** **C-01** (you notify the addressee).
**Blocks:** C-06, C-07 — and, downstream, C-08 and Lane A's profile page.

---

## Problem

The `friendships` table exists and nothing writes to it. There's no way for one user
to connect to another, which blocks the friends list, the online dots, and the friend
button on profiles. The tricky part isn't creating a row — it's all the ways a
request can be *invalid*: friending yourself, friending a deleted account, asking
twice, or asking again after being turned down.

## Proposed outcome

`POST /api/friends/request` creates a pending friendship and notifies the person on
the other end — and returns a precise, correctly-coded error for each of the ways it
can legitimately fail.

## Acceptance criteria

`POST /api/friends/request`, body `{ addressee_id }`, response **201** `{ id, status }`.

- [ ] Requires a logged-in user (**401 `unauthenticated`** otherwise).
- [ ] Friending **yourself** → **400 `invalid_request`**.
- [ ] An `addressee_id` that doesn't exist, **or** belongs to an anonymized
      (deleted) account → **404 `not_found`**.
- [ ] **No row exists for this pair** → create a friendship with `status = 'pending'`
      and `requester_id` = the caller, and stage a `friend_request` notification to
      the addressee with `link = "/users/{caller_id}"`.
- [ ] **A `pending` or `accepted` row already exists** for the pair (in *either*
      direction) → **409 `conflict`**, message "A friend request already exists".
      Nothing is written, no notification.
- [ ] **A `rejected` row exists** → this is a **re-request**: flip that same row back
      to `pending`, set `requester_id` to the caller (they may be the other person
      this time), and notify the addressee again. This notification is deliberately
      **not** deduplicated — a second attempt weeks later should be visible.
- [ ] If `FRIEND_REREQUEST_COOLDOWN_HOURS > 0` and the rejected row was updated
      inside that window → **429 `rate_limited`**. The default is `0`, so
      re-requesting is immediate unless someone changes the env var.
- [ ] **The reverse-pair race:** if B sends A a request at the same moment A sends
      one to B, the database's unique index on `(LEAST(requester, addressee),
      GREATEST(requester, addressee))` lets exactly one insert win. The loser must
      catch the integrity error, **roll the transaction back** (which also discards
      the notification it had staged — no half-notify), re-read the pair, and fall
      through to the "row already exists" logic above.
- [ ] Every error uses the shared envelope with the matching status.

## Out of scope

- Accepting, rejecting, or removing. That's C-06.
- Listing friends or pending requests. That's C-07.
- Any UI. That's C-08.
- Cancelling a request you sent. Not in the spec — the button shows "Requested" and
  that's it. Don't build it.
- Blocking users. Not in this project.

Two details to lift straight out of this file before you write any code:

- **The success status is 201, not 200** — on the first request *and* on the
  re-request after rejection. Easy to get wrong; FastAPI defaults to 200.
- The self-friending test asserts the **error code**, not only the status. That's the
  shared envelope from foundation §4.1 doing its job — if you `raise HTTPException`
  without a `detail={"code": ..., "message": ...}` dict, this test fails even though
  your status is right.

**Not graded here, but still required:** the anonymized-addressee 404, the 409 when

Lane tests deliberately never assert another lane's side effects — but the AC requires

## Technical notes

**Constraints (requirements, not suggestions):**
- One row per **unordered pair**. `(A→B)` and `(B→A)` are the same friendship; the
  database enforces it and your queries must look both ways.
- `status` is constrained by the schema to `'pending' | 'accepted' | 'rejected'`.
  Postgres will reject anything else — don't invent `'cancelled'`.
- A rejected friendship's row is **kept**, not deleted. That's what makes
  re-requesting possible.
- Anonymized users are not deleted rows — they're real users with
  `is_anonymized = true` and a username like `[deleted_ab12]`. Treat them as
  not-found for friending purposes.

**Files you will probably touch:**
- `backend/app/routers/friends.py` — an empty `APIRouter`, already registered under
  `/api/friends`.
- `backend/app/services/friends.py` — currently only the `friendship_state_for` stub
  (that one is C-07's job; leave it alone for now).
- `backend/app/schemas/` — add a `friend.py`.
- `backend/app/models/friendship.py` — read only.

**Suggested approach — a proposal, not a mandate:**
1. Write a small helper that finds the pair row in either direction:
   `WHERE (requester_id = :a AND addressee_id = :b) OR (requester_id = :b AND addressee_id = :a)`.
   You'll use it in C-06 and C-07 too.
2. Guards first (self, unknown, anonymized), then the branch on the existing row:
   none → insert; pending/accepted → 409; rejected → flip.
3. Do the race handling last. Wrap the insert in `try/except IntegrityError`, then
   `await db.rollback()`, then re-run your pair lookup and take the existing-row
   branch. Test it by reading the code carefully — reproducing a real race by hand is
   hard, and it's fine to reason it through rather than orchestrate two clients.

**Words you'll meet in this ticket:**
- **Unordered pair** — {A, B} is the same as {B, A}. The `LEAST/GREATEST` index is
  the database's way of saying so.
- **Race condition** — two requests arriving at the same instant, each thinking it's
  first. You don't prevent it, you let the database referee and handle losing.
- **IntegrityError** — the exception SQLAlchemy raises when the database refuses a
  write because a constraint (like that unique index) was violated.
- **Rollback** — undo everything staged in this transaction. Note *why* the AC
  demands it here: your notification was staged in the same transaction as the failed
  insert, so rolling back is what stops a "friend request" notification for a friend
  request that never existed.
- **Cooldown** — a minimum wait between repeat actions, to stop harassment-by-retry.

## Verify it yourself

```bash
docker-compose exec backend pytest tests/lane_c/test_c05_friend_requests.py -v
```

By hand at `https://localhost/api/docs`, as users A and B:
1. A requests B → **201**, `{ id, status: "pending" }`, and a row appears in
   `friendships`.
2. B's notification list (C-02) contains a `friend_request` pointing at `/users/{A}`.
3. A requests B again → **409**.
4. B requests A (reverse direction, row already exists) → **409**, not a second row.
5. A requests A → **400**.
6. A requests a random UUID → **404**.
7. Set the row's status to `'rejected'` with `psql`, then A requests B again → **201**,
   the **same row id** comes back as `pending`, and B gets a second notification.
