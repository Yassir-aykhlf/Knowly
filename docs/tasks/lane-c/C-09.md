# [C-09] Any user can send a direct message to any other user, and see what's unread

**Lane:** C — Social & Signals
**Task ID:** C-09
**Size:** ~1.5 days
**Depends on:** **A-01** (real auth) — and until that lands, the Launch Pad's auth
stub returns a fixed dev user, so you can start today. **This task does not depend on
C-01 at all.**
**Blocks:** C-10 (the messages UI).

---

## Problem

The `messages` table exists and nothing writes to it. Users can't talk to each other
privately — a friend list is not much use if the only thing you can do with a friend
is look at them.

Note that messaging is a **separate spine** from notifications and friendships. If
the notification work is going slowly, this task is not blocked by it.

## Proposed outcome

Four endpoints under `/api/messages` covering the whole messaging lifecycle: send,
list your conversations with unread counts, read one conversation's history, and mark
a conversation read.

## Acceptance criteria

### `POST /api/messages/{userId}` → **201** `MessageOut`

- [ ] **Open messaging:** any authenticated user may message any other. It is
      **not** friend-gated. Do not add a friendship check.
- [ ] Body `{ body }`, trimmed, **1–4 000 characters** → **400 `validation_error`**
      outside that range (the database has the same constraint as a backstop).
- [ ] Messaging **yourself** → **400 `invalid_request`**.
- [ ] Unknown or **anonymized** recipient → **404 `not_found`**.
- [ ] Messages are **immutable** once sent — there is no edit and no delete endpoint,
      by design.

### `GET /api/messages/conversations`

- [ ] One row per **correspondent** — not one per message. If you've exchanged 40
      messages with one person, they appear once.
- [ ] Each row carries: the other user (`Author` shape), the **latest** message as a
      **100-character preview**, its timestamp, `last_message_from_me` (boolean), and
      `unread_count` — messages sent **to** the caller that are still unread.
- [ ] **Newest conversation first.** Ties broken by message id so the order is
      deterministic and doesn't shuffle between requests.

### `GET /api/messages/{userId}?page&limit`

- [ ] Paginated history of the conversation with that user (both directions), in the
      shared `{ items, total, page, limit }` envelope, **newest first**.
- [ ] A **pure read with no side effects** — fetching a conversation must **not**
      mark anything read. The client does that separately, on purpose.

### `PUT /api/messages/{userId}/read` → **204**

- [ ] Marks every message **received from** `userId` as read. Messages the caller
      *sent* are untouched.
- [ ] **Commits only if rows actually changed.** The conversation screen polls this
      every 5 seconds; an idle open thread must not write to the database 12 times a
      minute. Check first, write only when there's something to write.

### Across all four

- [ ] Logged-out → **401 `unauthenticated`**.
- [ ] A user can only ever read messages they sent or received. There is no way to
      see two other people's conversation.
- [ ] Every error uses the shared envelope with the right status.

## Out of scope

- **Notifications. Direct messages create none — this is deliberate.** The messages
  UI carries its own unread badge instead (C-10). Do not call `create_notification`
  anywhere in this task.
- Any UI (C-10).
- Group chats, attachments in messages, typing indicators, read receipts beyond
  `read_at`, editing or deleting messages.
- Websockets. Polling is the design.

## The tests that grade this task

```bash
docker-compose exec backend pytest tests/lane_c/test_c09_messages_api.py -v
```

Five tests. The file's own docstring states the design in one line: *"open messaging,
no notifications."*

| Test | What it pins down | AC |
|---|---|---|
| `test_send_message_open_to_anyone` | sender and recipient are **not friends** and it still returns **201**, echoing back `body` and `read_at: None` | open messaging |
| `test_cannot_message_yourself` | **400** | self-message |
| `test_message_unknown_user_is_404` | a random UUID → **404** | unknown recipient |
| `test_conversation_list_reports_unread` | two unread messages from one person → `r.json()[0]` has `user.username`, `unread_count == 2`, and `last_message == "unread two"` (the **newest**, not the first) | conversation list |
| `test_mark_read_clears_unread` | `PUT /api/messages/{other}/read` → **204**, and the conversation's `unread_count` becomes 0 | mark read |

Shape facts to take straight from the file:

- `GET /api/messages/conversations` returns a **bare array** — the test indexes
  `r.json()[0]`. No pagination envelope on this one. (`GET /api/messages/{userId}`
  *is* paginated, per the spec.)
- The keys are `user`, `unread_count`, `last_message`. Not `other_user`, not `unread`.
- `last_message` is the **latest** message's text — the test sends "unread one" then
  "unread two" and expects "unread two". Sort direction is being checked here, quietly.
- The `POST` response includes `read_at` and it must be `null` on a fresh message.

**Not graded here, but still required:** the 1–4 000 trim and validation, anonymized
recipients 404-ing, the 100-character preview truncation (every test body is short,
so nothing catches a missing truncate), `last_message_from_me`, newest-conversation-first
ordering with the id tie-break, the `GET /{userId}` history endpoint **in its
entirety** — no test touches it — and the "commit only if rows changed" rule.

That last one deserves a warning: **`test_mark_read_clears_unread` will pass a naive
implementation that writes on every call.** It only ever calls the endpoint once, with
something genuinely unread. The AC exists because C-10 polls this every 5 seconds, and
a version that commits each time hammers the database forever without ever failing a
test. Check it yourself — step 7 of the walkthrough below.

## Technical notes

**Constraints (requirements, not suggestions):**
- Open messaging is a product decision. It's written down here so nobody "fixes" it
  into friends-only later.
- The `messages` table already has `ix_messages_sender_receiver_created` and
  `ix_messages_receiver_read`. The second exists specifically to make unread counts
  and the receiver half of the conversation list fast — you shouldn't need to add
  anything.
- 4 000 characters is enforced in **three** places: your Pydantic schema, your
  handler's trim-then-check, and a database CHECK constraint. Belt and braces, on
  purpose.

**Files you will probably touch:**
- `backend/app/routers/messages.py` — empty `APIRouter`, already registered.
- `backend/app/services/messages.py` — new file, if you want the conversation query
  out of the router.
- `backend/app/schemas/message.py` — new.
- `backend/app/models/message.py` — read only.

**Suggested approach — a proposal, not a mandate:**
1. `POST` first — it's the simplest and it gives you data to test everything else.
2. Then `GET /{userId}` — one query with an OR of the two directions:
   `(sender=me AND receiver=them) OR (sender=them AND receiver=me)`.
3. Then `PUT /{userId}/read`.
4. `GET /conversations` last — it's the hard one. Two workable shapes:
   - **The simple one:** fetch the caller's messages, group by correspondent in
     Python, take the newest per group. Correct, easy to read, fine at this scale.
   - **The SQL one:** a window function (`ROW_NUMBER() OVER (PARTITION BY
     correspondent ORDER BY created_at DESC, id DESC)`) plus an aggregate for the
     unread counts.
   Either passes. Take the first if the second is eating your day, and say so in
   the PR — a working simple version beats a half-finished clever one.
5. For "commit only if rows changed": run the `UPDATE ... WHERE read_at IS NULL`,
   check `result.rowcount`, and only commit when it's non-zero.

**Words you'll meet in this ticket:**
- **Correspondent** — the other person in a conversation. Which column that is
  depends on whether the caller sent or received the message, which is what makes
  the conversation list awkward.
- **Immutable** — once written, never changed. No edit endpoint exists and none is
  wanted.
- **Idempotent / no-op write** — calling mark-read on an already-read conversation
  should do nothing at all, not write the same values back.
- **`rowcount`** — how many rows an `UPDATE` actually touched. Your cheapest way to
  answer "did anything change?".
- **Spine** — a chain of tasks that only depend on each other. Messages (C-09 →
  C-10) is independent of notifications and friends.

## Verify it yourself

```bash
docker-compose exec backend pytest tests/lane_c/test_c09_messages_api.py -v
```

By hand at `https://localhost/api/docs`, as A and B (who are **not** friends — that's
the point):
1. A messages B → **201**, and the row lands in `messages`.
2. A messages themselves → **400**. A messages a random UUID → **404**.
3. A sends a 4 001-character body → **400** with the envelope; 4 000 → 201.
4. As B, `GET /api/messages/conversations` → one row for A, `unread_count: 1`,
   preview truncated to 100 characters, `last_message_from_me: false`.
5. As B, `GET /api/messages/{A}` → the history. Re-fetch `conversations` →
   `unread_count` is **still 1**. (Reading history must not mark read.)
6. As B, `PUT /api/messages/{A}/read` → 204, and `unread_count` drops to 0.
7. **The idle-poll check:** with nothing unread, call `PUT /{A}/read` five times in a
   row. Confirm no `read_at` value changed — add a temporary log line, or watch the
   database. This is the AC most often shipped broken.
8. As a third user C, try `GET /api/messages/{A}` → you see **your** (empty)
   conversation with A, never A and B's.
