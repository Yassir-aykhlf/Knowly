# [C-10] A user can read and hold a conversation from inside the app

**Lane:** C — Social & Signals
**Task ID:** C-10
**Size:** ~1.5 days
**Depends on:** **C-09** (all four endpoints).
**Blocks:** nothing — this is the last task in the messages spine.

---

## Problem

Messaging works entirely through `curl`. `/messages` and `/messages/:userId` both
render placeholder boxes, so no user can actually reach a feature that is otherwise
finished.

## Proposed outcome

Two screens: an inbox listing every conversation with unread badges, and a thread
view that reads like a chat — history above, composer below, new messages arriving on
their own while you're looking at it.

## Acceptance criteria

### `MessagesPage` at `/messages`

- [ ] Lists conversations from `GET /api/messages/conversations`: the other person's
      avatar and username, the message preview, a relative timestamp, and an
      **unread badge** when `unread_count > 0`.
- [ ] Polls every **30 seconds** via `usePolling` (so it pauses on a hidden tab and
      refreshes once on refocus).
- [ ] Clicking a conversation opens `/messages/{userId}`.
- [ ] Empty state when there are no conversations.

### `ConversationPage` at `/messages/:userId`

- [ ] Loads history from `GET /api/messages/{userId}` (paginated) and renders it
      **oldest at the top, newest at the bottom** — the API returns newest-first, so
      you reverse for display. Reading order is not storage order.
- [ ] Your own messages are visually distinguishable from theirs.
- [ ] A composer: 1–4 000 characters, send button **disabled while empty or while a
      send is in flight** (this is what stops double-sends).
- [ ] After history is displayed, calls `PUT /api/messages/{userId}/read` — the
      screen owns marking read, because the API deliberately doesn't.
- [ ] Polls `GET /api/messages/{userId}` every **5 seconds** while the tab is
      visible, appends anything new, and marks newly-arrived inbound messages read.
- [ ] Sending appends the message **optimistically**, then reconciles with the real
      row the server returns. On failure it removes/marks the pending message and
      toasts — it must never leave a message looking sent when it wasn't.
- [ ] The 5-second poll must not fight the composer: typing, scrolling, and an
      in-flight send all survive a poll tick.
- [ ] Empty state for a conversation with no messages yet (you can open a thread with
      someone you've never messaged — messaging is open, not friend-gated).

## Out of scope

- Any backend change. If a screen needs data the API doesn't give you, that's a C-09
  conversation, not a quiet endpoint edit.
- Notifications for messages — **there are none by design**; the unread badge on this
  screen is the entire mechanism.
- Typing indicators, delivery receipts, message editing/deleting, attachments, group
  chats, emoji pickers.
- Websockets. Polling at 5 s / 30 s is the design.
- Infinite scroll in the thread. Paginated "load older" is enough.

## The tests that grade this task

No `test_c10_*.py` — it's UI. `tests/lane_c/test_c09_messages_api.py` is the contract
for everything these two screens render:

| Test | What it guarantees for you |
|---|---|
| `test_conversation_list_reports_unread` | The `/conversations` response is a **bare array** (the test indexes `r.json()[0]`) whose entries carry `user`, `unread_count`, and `last_message` — and `last_message` is the **newest** one. That is the whole of `MessagesPage`'s data. |
| `test_mark_read_clears_unread` | `PUT /{userId}/read` returns **204** and really does zero the count, so your badge clearing after a thread opens is safe to trust. |
| `test_send_message_open_to_anyone` | `POST` returns **201** with the full message including its real `id` and `read_at: null`. That server row is what your optimistic message reconciles **against** — it's the object you swap your temporary one for. |
| `test_cannot_message_yourself` / `test_message_unknown_user_is_404` | The two failures you can hit by typing a URL by hand: **400** and **404**. Show a real message, don't render an empty thread that silently never sends. |

## Technical notes

**Constraints (requirements, not suggestions):**
- Use `usePolling` for both intervals; it already handles tab visibility.
- Use `api` from `lib/api.ts`, never bare `fetch`.
- `Message` and `Conversation` types are in `lib/types.ts` — frozen.
- `lib/format.ts` already exports `relativeTime(iso)` for the timestamps.
- Marking read is the **client's** job here. That split is intentional: it's what
  lets a user glance at a thread from the list without silently clearing their
  unread state.

**Files you will probably touch:**
- `frontend/src/pages/MessagesPage.tsx`, `frontend/src/pages/ConversationPage.tsx` —
  replace the `<Placeholder>`s.
- `frontend/src/App.tsx` — routes already exist; you probably change nothing.

**Suggested approach — a proposal, not a mandate:**
1. `MessagesPage` first. It's a list — you've written two already (C-04, C-08).
2. Then the thread, read-only: fetch page 1, reverse for display, render bubbles.
3. Then the composer, non-optimistically: send → await → re-fetch. Get it *correct*
   before you make it *feel fast*.
4. Then the 5 s poll. Keep messages in state keyed by id and merge by id — that way
   a poll that returns a message you already have is harmless, which matters a lot
   once optimistic sends are in.
5. Optimism last: append a temporary message with a client-side id and a "sending"
   look, swap it for the server's row on success, remove it and toast on failure.
   If merge-by-id is in place from step 4, this stays small.
6. Scroll position is the classic trap: auto-scroll to the bottom on first load and
   when a message arrives while you're already at the bottom — but **not** when the
   user has scrolled up to read history. Getting this wrong is very visible.

**Words you'll meet in this ticket:**
- **Optimistic send** — show the message immediately, before the server confirms.
- **Reconcile** — replace your temporary local message with the real one the server
  returned (which has the real id and timestamp).
- **Merge by id** — combining server data with local state so duplicates collapse
  instead of stacking up. The single most useful habit in polling UIs.
- **In-flight** — a request that has been sent and hasn't answered yet. Disabling the
  send button while a send is in-flight is how you prevent double-posting.

## Verify it yourself

Two accounts, two windows, side by side. That's the whole test.

1. As A, open `/messages` → empty state.
2. As A, open `/messages/{B}` directly (you've never messaged B) → empty thread, not
   an error.
3. Send a message → it appears immediately, and settles (no duplicate) once the
   server answers.
4. In B's window, **without touching anything**, the thread updates within ~5 s and
   `/messages` shows an unread badge within ~30 s.
5. B opens the thread → the badge clears; A's copy of the conversation list shows
   nothing unread for themselves.
6. Scroll up into old history in B's window, then have A send a message → the view
   must **not** yank B to the bottom mid-read.
7. Send while empty → the button is disabled. Click send twice fast → **one**
   message is created (check the API, not just the screen).
8. Stop the backend, send a message → it does not linger looking successfully sent; a
   toast appears.
9. Switch tabs for two minutes → on return, one immediate refresh, and in the network
   tab no evidence the polls kept firing while hidden.
10. Send a 4 001-character message → rejected in the UI before or after the API says
    so, but with a message the user can understand.
