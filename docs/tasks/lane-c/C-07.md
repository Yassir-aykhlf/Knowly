# [C-07] A user can see who their friends are, who's waiting on them, and who's online right now

**Lane:** C — Social & Signals
**Task ID:** C-07
**Size:** ~1 day
**Depends on:** **C-05** (rows to list). Reads the `users.last_seen` column, which
Lane A's A-10 writes — **the column exists from day 1**, so you are not blocked; it
will simply be `NULL` for everyone until A-10 ships, and everyone reads as offline.
**Blocks:** C-08 (the friends page) and **Lane A's profile page** (A-06 is currently
using a stub that always says "not friends" — your `friendship_state_for` replaces it).

---

## Problem

Friendships can be created and accepted, but nothing can read them back. A user
can't see their friends list, can't see requests waiting for a decision, and Lane A's
profile page has no way to know whether the person you're looking at is already your
friend — so its friend button is hardcoded to "not friends" for everybody.

## Proposed outcome

Two list endpoints and one shared helper function. The helper is a **seam**: Lane A
imports it into the profile payload, which is why its return shape is fixed and must
not drift.

## Acceptance criteria

### `GET /api/friends`

- [ ] Returns a **plain JSON array**, not the `{ items, total, page, limit }`
      envelope. Friends lists aren't paginated in this project — the same goes for
      `/api/friends/pending`.
- [ ] Returns the caller's **accepted** friends only.
- [ ] Each entry: `{ friendship_id, user, online, last_seen, since }` where `user`
      is the public `Author` shape and `since` is when the friendship was created.
- [ ] Sorted by username, **case-insensitively** (so `alice`, `Bob`, `carol` — not
      `Bob`, `alice`, `carol`).
- [ ] **`online` is computed on the server**: true when that user's `last_seen` is
      within the last **2 minutes**. The client is never allowed to recompute this —
      you send a boolean, they render a dot.
- [ ] `last_seen` of `NULL` (a user who has never sent a heartbeat) → `online: false`.
      No crash, no error.
- [ ] Works in both directions: a friendship where the caller is the *requester* and
      one where they're the *addressee* both appear, showing the **other** person.

### `GET /api/friends/pending`

- [ ] Returns **incoming** pending requests only — ones addressed to the caller.
      Requests the caller *sent* must not appear here.
- [ ] Each entry: `{ friendship_id, requester, created_at }`, `requester` being the
      `Author` shape.
- [ ] Newest first.

### `friendship_state_for(db, viewer, other_id) -> (state, friendship_id | None)`

- [ ] Returns one of `none | request_sent | incoming_pending | friends | rejected`.
- [ ] `friends` for an accepted row; `rejected` for a rejected row.
- [ ] For a pending row: `request_sent` if the **viewer** is the requester, otherwise
      `incoming_pending`.
- [ ] `("none", None)` when there is no row for the pair.
- [ ] Keeps the **exact signature** already in `services/friends.py` — Lane A is
      calling it today through the stub.

### Both endpoints

- [ ] Logged-out → **401 `unauthenticated`**.
- [ ] Authors are batch-loaded, not fetched one query per friend.

## Out of scope

- Writing `last_seen`. That's Lane A's A-10 heartbeat. You only read the column.
- Any UI, including the online dot itself (C-08).
- Outgoing pending requests as a list endpoint — the spec only calls for incoming.
  (`friendship_state_for` covers the outgoing case for a single profile.)
- Editing Lane A's profile endpoint to use your helper. **They** do that swap when
  you announce it; you just ship the function.
- Pagination. Friends lists in this project are small enough to return whole.

| Test | What it pins down | AC |
|---|---|---|
| `test_friends_list_derives_online_from_last_seen` | sets one friend's `last_seen` to now and another's to 10 minutes ago, then builds `{f["user"]["username"]: f["online"] for f in r.json()}` and asserts `True` / `False`. | `test_pending_lists_incoming_only` | creates one incoming and one outgoing pending request, then asserts `/api/friends/pending` lists **exactly** `["incoming_req"]` | incoming only |
| `test_friendship_state_for_seam` | calls your service function directly: no row → `("none", None)`; after an accepted friendship → `("friends", <not None>)` | the seam |

Three shape facts the tests hand you for free — get these wrong and nothing passes:

- `r.json()` is **iterated directly**, so both list endpoints return a **bare array**,
  not a pagination envelope.
- A friend entry nests the person under `user`: `f["user"]["username"]`, and carries
  `f["online"]` as a **top-level boolean** on the entry.
- A pending entry nests the person under `requester`: `p["requester"]["username"]`.
- The online test's comment says it outright: *"Online window is 2 minutes."*

**Not graded here, but still required:** case-insensitive username sorting,
`last_seen` of `NULL` reading as offline, `pending` newest-first, batch-loaded
authors, 401 when logged out, and the three `friendship_state_for` states the test
never exercises — `request_sent`, `incoming_pending`, and `rejected`. That last gap
matters: **the test only checks `none` and `friends`**, but C-08's button has five
branches and Lane A's profile shows all of them. Verify the other three by hand.

**The milestone test that proves this seam landed:**
`tests/milestones/test_m5_friendship.py` has Alice request Bob, then checks that
`GET /api/users/{id}` reports `friendship.state` as `"request_sent"` for Alice and
`"incoming_pending"` for Bob — the two states your own test file skips. It stays red
until **Lane A** deletes their `("none", None)` stub and embeds your function. Run it

## Technical notes

**Constraints:**
- Server-derived `online` is a deliberate design choice: two clients with skewed
  clocks would otherwise disagree about who's online. Send the boolean.
- Never leak `email`, `role`, or OAuth fields into these payloads. The `Author` shape
  in foundation §4.4 is the whole of what's public.

**Files you will probably touch:**
- `backend/app/routers/friends.py`, `backend/app/services/friends.py`,
  `backend/app/schemas/friend.py`.

**Suggested approach — a proposal, not a mandate:**
1. `friendship_state_for` first — it's the smallest piece, it reuses C-05's
   find-the-pair helper, and it's the thing another person is waiting on.
2. Then `/pending`: one filtered query, join the requester, sort by `created_at DESC`.
3. Then `/friends`: select accepted rows where the caller is on either side, work out
   "the other id" per row, batch-load those users in one query, then compute `online`
   in Python (`user.last_seen is not None and now - last_seen < 2 minutes`) and sort
   by `username.lower()`.
4. Careful with time zones: compare `last_seen` against the same kind of "now" the
   heartbeat writes. Mixing naive and aware datetimes raises a `TypeError` — if you
   hit that, look at how `created_at` is stored in the models first.

**Words you'll meet in this ticket:**
- **Seam** — a function one lane owns and another imports. `friendship_state_for` is
  one, which is why its signature is frozen and its return values are a fixed set.
- **Heartbeat** — a small periodic request the frontend makes so the server can keep
  `last_seen` fresh. Someone else builds it; you consume the column.
- **Server-derived field** — a value computed on the server and sent as a plain
  answer, precisely so clients can't disagree.
- **Batch-load** — one query for all the users on the page, not one per row.

## Verify it yourself

```bash
docker-compose exec backend pytest tests/lane_c/test_c07_friend_listings_state.py -v
```

By hand, as A, B, C:
1. A and B become friends; C sends A a request and leaves it pending.
2. `GET /api/friends` as A → exactly B, with `friendship_id`, `since`, and
   `online: false` (nobody's heartbeat has run yet).
3. Set B's `last_seen` to `now()` in `psql` → re-fetch → `online: true`. Set it to
   ten minutes ago → `online: false`. Set it to `NULL` → `online: false`, no error.
4. `GET /api/friends/pending` as A → exactly C's request. As **C** → **empty** (the
   request they sent is not incoming for them).
5. Add friends with usernames `zoe`, `Adam`, `mike` → the list comes back
   `Adam, mike, zoe`, not `Adam, mike, zoe` re-ordered by ASCII capitals.
6. Call `friendship_state_for` from a shell for each situation: strangers → `none`;
   you sent → `request_sent`; they sent → `incoming_pending`; accepted → `friends`;
   rejected → `rejected`.
