# [C-02] A user can fetch their notifications, see how many are unread, and mark them read

**Lane:** C — Social & Signals
**Task ID:** C-02
**Size:** ~1 day
**Depends on:** **C-01** (you need rows in the table before you can list them).
**Blocks:** C-03 (the bell) and C-04 (the inbox page) — both are pure consumers of
these four endpoints.

---

## Problem

C-01 fills the `notifications` table, but nothing can read it. The frontend has no
way to ask "what happened while I was away?" or "how many unread do I have?", and no
way to mark anything as read — which means the unread count would only ever grow.

## Proposed outcome

Four read/update endpoints under `/api/notifications` that the bell and the inbox
page can be built on: a paginated list, an unread count, mark-one-read, and
mark-all-read. Nothing in this task ever *creates* a notification.

## Acceptance criteria

- [ ] `GET /api/notifications?page&limit` returns the caller's notifications,
      **newest first**, in the shared pagination envelope
      `{ items, total, page, limit }` (foundation §4.3).
  - [ ] Ties are broken by `id DESC`, so several rows written in one transaction
        (identical `created_at`) always come back in the same order. Without this
        the list visibly shuffles between refreshes.
  - [ ] Each item is
        `{ id, event_type, subject_type, subject_id, link, actor, actor_count, read_at, created_at }`.
  - [ ] `actor` is the public `Author` shape
        `{ id, username, avatar_url, is_anonymized }` — or `null` for system events
        (moderation) and for anonymized users.
  - [ ] Actors are **batch-loaded**: one query for all the actors on the page, not
        one query per row.
- [ ] `GET /api/notifications/unread-count` returns `{ count }` — rows where
      `read_at IS NULL`.
- [ ] `PUT /api/notifications/{id}/read` marks one notification read and returns **204**.
  - [ ] A notification belonging to **someone else** returns **404 `not_found`** —
        the same response as a row that doesn't exist. Never confirm that another
        user's notification exists.
  - [ ] Calling it on an already-read row is fine: still **204**, and `read_at` is
        **not** overwritten with a new timestamp.
- [ ] `PUT /api/notifications/read-all` marks all of the caller's unread rows read
      and returns **204**.
- [ ] All four endpoints require a logged-in user and return **401 `unauthenticated`**
      without one.
- [ ] Every error response uses the shared envelope with the right status.

## Out of scope

- Creating notifications. That is C-01 and it stays the only write path.
- Deleting notifications — the API has no delete, and we're not adding one.
- Any UI. C-03 (bell) and C-04 (page) consume these endpoints.
- Filtering by `event_type`, or a "notification settings" screen. Not in this
  project.

## Technical notes

**Constraints (requirements, not suggestions):**
- 404, never 403, for someone else's notification. Returning 403 would tell an
  attacker "this ID is real, it's just not yours" — that's an information leak.
- Read endpoints only. If you find yourself writing an `INSERT` into
  `notifications` in this task, you're in the wrong ticket.

**Files you will probably touch:**
- `backend/app/routers/notifications.py` — currently an empty `APIRouter`, already
  registered in `main.py` under `/api/notifications`.
- `backend/app/schemas/` — add a `notification.py` for the response models.
- `backend/app/services/notifications.py` — if you want read helpers next to the
  write ones. Optional.

**Suggested approach — a proposal, not a mandate:**
1. `unread-count` first. It's a one-line `SELECT count(*)`, and it proves your
   router registration and auth dependency work before you write anything hard.
2. Then the list endpoint. Query the page of notifications, collect the non-null
   `actor_id`s into a set, run **one** `SELECT ... WHERE users.id IN (...)`, build a
   `{id: Author}` dict, and map over your rows. That's the batch-load.
3. Then the two mark-read endpoints.
4. For "already-read → don't rewrite", the simplest form is a conditional update:
   `UPDATE ... SET read_at = now() WHERE id = :id AND recipient_id = :me AND read_at IS NULL`.

**Words you'll meet in this ticket:**
- **N+1 query** — the bug where listing 20 rows runs 21 queries (one for the list,
  one per row to fetch its author). Batch-loading is how you avoid it. It's the most
  common performance mistake in code like this, which is why it's an AC.
- **Pagination envelope** — every list endpoint in Knowly returns
  `{ items, total, page, limit }`. `page` starts at 1.
- **Idempotent** — calling it twice is the same as calling it once. Mark-read is
  idempotent; that's what lets the UI fire it optimistically without worrying.
- **204 No Content** — success, and there is deliberately no response body.

## Verify it yourself

```bash
docker-compose exec backend pytest tests/lane_c/test_c02_inbox_api.py -v
```

By hand, with the stack running and logged in as two different users (two browsers
or a normal + private window), using `https://localhost/api/docs`:
1. Create a couple of notifications for user A (easiest: have A send B a friend
   request once C-05 exists; before then, insert rows directly with `psql`).
2. `GET /api/notifications` as A → they're there, newest first.
3. `GET /api/notifications/unread-count` → matches.
4. `PUT /api/notifications/{id}/read` as **B** → 404, and the envelope says
   `not_found`.
5. Same call as A → 204, and the count drops by one. Call it again → still 204,
   and `read_at` in the database is unchanged.
