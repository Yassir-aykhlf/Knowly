# [C-06] A user can accept or reject a friend request, and either friend can undo a friendship

**Lane:** C — Social & Signals
**Task ID:** C-06
**Size:** ~0.5–1 day
**Depends on:** **C-05** (there must be requests to respond to).
**Blocks:** C-08's buttons have nothing to call without this.

---

## Problem

Friend requests can be sent but never answered. Every friendship in the database is
stuck at `pending` forever, so nobody is ever actually friends and nobody can get out
of a connection they no longer want.

## Proposed outcome

Three endpoints that close the loop: the addressee can accept or reject; either
person can remove an existing friendship. Accepting tells the requester; rejecting
says nothing at all.

## Acceptance criteria

### `PUT /api/friends/{id}/accept` and `PUT /api/friends/{id}/reject` → `{ id, status }`

- [ ] **Only the addressee** may accept or reject. The requester trying to accept
      their own request → **403 `forbidden`**. An unrelated user → **403** too.
- [ ] Unknown `{id}` → **404 `not_found`**.
- [ ] A row that isn't `pending` (already accepted, already rejected) → **409 `conflict`**.
- [ ] **Accept** sets `status = 'accepted'` and stages a `friend_accepted`
      notification to the **requester**.
- [ ] **Reject is silent.** It sets `status = 'rejected'` and sends **no
      notification** — being turned down should not generate a message. The row
      **stays** so the pair can re-request later (C-05).

### `DELETE /api/friends/{id}` → **204**

- [ ] **Either party** may remove the friendship. Anyone else → **403 `forbidden`**.
- [ ] Unknown `{id}` → **404 `not_found`**.
- [ ] Stages a `friend_removed` notification to **the other person** — then
      **deletes the row entirely**, so the pair is free to start over from scratch.
- [ ] Order matters: read the other party's id **before** you delete the row.
- [ ] Returns **204** with no body.

### Across all three

- [ ] Logged-out → **401 `unauthenticated`**.
- [ ] Every error uses the shared envelope with the right status.

## Out of scope

- Sending or re-sending requests (C-05).
- Listing friends or pending requests (C-07).
- UI (C-08).
- "Unfriend and block". Blocking isn't in this project.
- Soft-deleting friendships. Remove means `DELETE FROM friendships`; the spec is
  explicit that the row goes away, unlike reject.

Details to take from the file:

- Accept and reject return **200 with a body** (`{ id, status }`); remove returns
  **204 with no body**. Three endpoints, two different conventions — that's
  deliberate, and it's the kind of thing you only notice by reading the test.
- The remove test calls `db.expire_all()` before counting. That's a test-harness
  detail (forcing a re-read after the app mutated the row), not something you need in
  your code — but if you ever write a test yourself and a row looks stale, that's why.
- Read the test names as a pair: *"reject is silent **and keeps row**"* versus
  *"either party can **remove**"* which ends at zero rows. The two behaviours are
  opposite on purpose.

**Not graded here, but still required:** 404 for an unknown id, 409 for a non-pending
row, 403 for an unrelated third party, and the notifications — `friend_accepted` on
accept, `friend_removed` on remove, and **nothing at all** on reject. As in C-05, no
test in this file looks at the `notifications` table; the AC still does. Check it
yourself with `psql`, especially the "reject writes zero rows" case.

## Technical notes

**Constraints (requirements, not suggestions):**
- Reject vs remove behave differently **on purpose**: reject keeps the row (status
  `rejected`, no notification), remove deletes it (with a notification). If that
  feels inconsistent, the reasoning is: rejection is a state the pair should remember
  so re-requests are traceable; removal is a reset.
- 403 vs 404: use **404** when the friendship doesn't exist, **403** when it exists
  but the caller isn't allowed to touch it. Unlike C-02's notifications, a friendship
  id isn't sensitive — the caller either is or isn't part of the pair.
- Notification staging goes through C-01's `create_notification`; still no commits
  inside the service layer.

**Files you will probably touch:**
- `backend/app/routers/friends.py` — add three routes next to C-05's.
- `backend/app/services/friends.py`, `backend/app/schemas/friend.py`.

**Suggested approach — a proposal, not a mandate:**
1. Accept and reject share almost everything: load row → 404 → check caller is
   addressee → 403 → check status is pending → 409 → set status. Write one helper
   with the target status as an argument, then two thin routes.
2. Remove is separate: load row → 404 → check caller is *either* party → 403 →
   compute "the other person" → notify → delete.
3. Watch the ordering trap in remove. If you delete first, you no longer know who to
   notify; if you commit the delete before staging the notification, a failure
   halfway leaves an inconsistent state. Stage the notification, then delete, then
   let the request handler commit both together.

**Words you'll meet in this ticket:**
- **Addressee** — the person a request was sent *to*. **Requester** — the person who
  sent it. Only the addressee gets to answer.
- **403 vs 404** — "you may not" vs "there is nothing here". Which one you return
  is a design decision about what you're willing to reveal.
- **Silent action** — an action that deliberately produces no notification. Rejection
  is one. This is a product decision, not an oversight; don't "improve" it.

## Verify it yourself

```bash
docker-compose exec backend pytest tests/lane_c/test_c06_friend_respond_remove.py -v
```

By hand, as A and B:
1. A requests B (C-05). As **A**, try `PUT /api/friends/{id}/accept` → **403**.
2. As **B**, accept → 200, `status: "accepted"`, and **A** gets a `friend_accepted`
   notification.
3. Accept again → **409**.
4. New pair, A requests B, B rejects → 200, `status: "rejected"`, **B's reject
   produced no notification row for A** (check the table). The row still exists.
5. A re-requests (C-05) → back to `pending`. Good: reject didn't burn the pair.
6. Accept it, then as **A** `DELETE /api/friends/{id}` → **204**, B has a
   `friend_removed` notification, and the row is **gone** from `friendships`.
7. As an unrelated user C, try to delete a friendship between A and B → **403**.
