# [C-08] A user can manage friendships from the Friends page and from anyone's profile

**Lane:** C — Social & Signals
**Task ID:** C-08
**Size:** ~1.5 days — two deliverables that ship together because they'd each be
useless alone (the page can't create friendships, the button can't show a list)
**Depends on:** **C-07** (listings + state), and C-05/C-06 for the actions.
**Blocks:** integration milestone 5 — Lane A's profile page mounts your button.

---

## Problem

Every friendship endpoint now works and none of them are reachable from the app.
`/friends` renders a placeholder box, and the profile page mounts an
`<AddFriendButton>` that deliberately renders nothing — so the only way to make a
friend in Knowly today is to POST JSON by hand.

## Proposed outcome

A Friends page where requests can be answered and friends can be seen (with a live
online dot), plus a single button on user profiles that always shows the right
control for your current relationship with that person.

## Acceptance criteria

### `FriendsPage` + `FriendsList` at `/friends`

- [ ] **Requests section** — incoming pending requests from `GET /api/friends/pending`,
      each with the requester's avatar, username, when it arrived, and **Accept** /
      **Reject** actions wired to C-06.
- [ ] **Friends section** — accepted friends from `GET /api/friends`, each with:
  - [ ] an **online dot** driven by the server's `online` boolean — never recomputed
        from `last_seen` in the browser;
  - [ ] a link to their profile (`/users/{id}`);
  - [ ] a link to their conversation (`/messages/{id}`);
  - [ ] a **Remove** action wired to C-06's `DELETE`.
- [ ] Both lists refresh on a modest poll (30 s is fine) via `usePolling`, so an
      accepted request and a friend coming online appear without a reload.
- [ ] Acting on a request moves it out of Requests and (for Accept) into Friends.
- [ ] Separate empty states for both sections — "no pending requests" and "no friends
      yet" say different things.
- [ ] Errors surface as a toast (`ToastContext`), and the row returns to its previous
      state rather than lying about what happened.

### `<AddFriendButton userId>` — rendered on another user's profile

- [ ] Drives entirely off the `friendship` object the profile payload provides
      (Lane A embeds C-07's `friendship_state_for` output there). It does **not**
      fetch friendship state itself.
- [ ] Renders the right control for each state:
  - [ ] `none` → **"Add friend"** → `POST /api/friends/request`
  - [ ] `request_sent` → **"Requested"**, disabled (or offering cancel — pick one and
        keep it consistent)
  - [ ] `incoming_pending` → **"Accept" / "Reject"**
  - [ ] `friends` → **"Friends ✓"** with a Remove option
  - [ ] `rejected` → **"Add friend"** again (this is the re-request path)
- [ ] Updates **optimistically**: the button changes state immediately, and on error
      it **reverts** and shows a toast.
- [ ] Renders **nothing at all** on your own profile, or for an anonymized user.
- [ ] Until Lane A ships the real profile payload, the button may be exercised
      against a locally-faked `friendship` prop — leave a
      `// STUB: swap for A-06 profile payload` comment if you do.

## Out of scope

- Building or restyling Lane A's profile page. You own the button; they mount it.

No `test_c08_*.py` — this is UI. But three test files define every response your two
components render, and one milestone test defines the data your button reads:

| Test file / test | What it guarantees for you |
|---|---|
| `test_c07_friend_listings_state.py` → `test_friends_list_derives_online_from_last_seen` | Each friend entry looks like `{ user: {username, ...}, online: bool, ... }` and the list is a **bare array**, not a paginated envelope. **`online` arrives as a server-computed boolean** — this test is the reason your dot must render `friend.online` and never do date maths in the browser. |
| `test_c07_friend_listings_state.py` → `test_pending_lists_incoming_only` | `/api/friends/pending` gives you **only** incoming requests, nested under `requester`. You never have to filter out your own outgoing requests in the UI. |
| `test_c05_friend_requests.py` | "Add friend" gets **201** on success, **409** on a duplicate, **400** with `error.code == "invalid_request"` for self. Those are the failures your optimistic revert has to handle. |
| `test_c06_friend_respond_remove.py` | Accept and reject return **200** with `{ id, status }`; remove returns **204 with no body**. If your handler tries to parse JSON from the remove response, it will break — the test is where you find that out. |

## Technical notes

**Constraints (requirements, not suggestions):**
- The online dot renders `friend.online`. Do not compare `last_seen` to
  `Date.now()` in the browser — the server already decided, and a client with a
  wrong clock would disagree with everyone else.
- Use `api` from `lib/api.ts` (never bare `fetch`) and `usePolling` for refreshes.
- `Friend` and `PendingRequest` types already exist in `lib/types.ts` — frozen; use
  them rather than declaring your own.

**Files you will probably touch:**
- `frontend/src/pages/FriendsPage.tsx` — replace the `<Placeholder>`.
- `frontend/src/components/FriendsList.tsx` — new file.
- `frontend/src/components/AddFriendButton.tsx` — replace the "returns null" stub.

**Suggested approach — a proposal, not a mandate:**
1. Get both lists rendering read-only first. No buttons, no polling. Confirm the data
   looks right.
2. Add the actions, and re-fetch both lists after each one. Simple and correct.
3. Add polling.
4. Then the button. Its five states are just a `switch` on
   `friendship.state` — write the switch before you write any handlers, and screenshot
   all five.
5. Optimistic updates last: set the new state locally, fire the call, and on
   `catch` restore the state you saved and toast the error. Keep the old value in a
   local variable before you overwrite it — that's the whole trick.

**Words you'll meet in this ticket:**
- **Optimistic update** — change the UI before the server answers, assuming success.
  Feels instant; costs you a revert path when it fails. The revert is not optional.
- **Toast** — the small transient message box. `ToastContext` already exists.
- **Empty state** — the message shown when a list is legitimately empty.
- **Mount** — when another page renders your component inside itself. Lane A mounts
  `<AddFriendButton>`; you never edit their page to make it happen.

## Verify it yourself

You need **two** logged-in accounts — a normal window and a private window.

1. As A, visit B's profile → **"Add friend"**. Click it → it flips to **"Requested"**
   immediately (optimistic), and stays that way after a refresh.
2. As B, visit `/friends` → A is in **Requests** with Accept / Reject.
3. As B, visit A's profile → the button shows **Accept / Reject**
   (`incoming_pending`), not "Add friend".
4. B accepts → A moves into **Friends** on B's page, and A's page shows B within
   30 s without a reload.
5. Both profiles now show **"Friends ✓"** with a Remove option.
6. In `psql`, set B's `users.last_seen` to `now()` → A's friends list shows B's dot
   as online within one poll. Set it ten minutes back → the dot goes out.
7. Click a friend's message link → lands on `/messages/{id}`.
8. Remove the friendship → both sides drop to "Add friend" and the row disappears.
9. Stop the backend and click Accept → the row reverts and a toast appears. The UI
   must not claim success.
10. Visit **your own** profile → the button renders nothing.
