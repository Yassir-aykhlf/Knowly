# [C-01] Any action in the app can record a notification for the person it affects

**Lane:** C — Social & Signals
**Task ID:** C-01
**Size:** ~2–3 days — the biggest and most important task in the lane
**Depends on:** nothing. You can start on day 1 against the Launch Pad stubs.
**Blocks:** C-02, C-05, and **two other people** — Lane B (answers, comments, votes,
edits) and Lane D (moderation verdicts) all call the functions you write here.

---

## Problem

Knowly users have no way of finding out that anything happened to their content.
Someone answers your question, votes on your answer, mentions you by name, or a
moderator holds your post — and you only discover it if you happen to reload the
right page. Every one of those events is produced by a different part of the app
owned by a different person, so if each one writes its own notification row we get
four slightly different behaviours, duplicate rows, and users notified about their
own actions. This is the first thing to build in Lane C, because Lane B and Lane D
are currently calling do-nothing stubs where your functions will go, and they can't
finish their features until the real ones exist.

## Proposed outcome

There is exactly **one** way to create a notification in Knowly —
`services/notifications.py` — and it is smart enough that callers don't have to be.
It refuses to notify you about your own actions, folds a storm of votes into a
single "12 people voted on your answer" row, and never notifies twice about the
same answer or mention. Lane B and Lane D delete their no-op stubs and import it.

## Acceptance criteria

### `create_notification(db, *, recipient_id, actor_id, event_type, link, subject_type=None, subject_id=None, coalesce_key=None)`

- [ ] It **stages** the notification in the caller's transaction and **never calls
      `db.commit()`**. (If the action that caused the notification fails and rolls
      back, the notification must disappear with it.)
- [ ] **Self no-op:** when `actor_id == recipient_id`, nothing is written at all.
- [ ] **Vote coalescing** — only when `coalesce_key` is given:
  - [ ] The first vote on a target inserts one row with `actor_count = 1`.
  - [ ] Each later vote on that same target **updates the existing unread row**
        instead of inserting: `actor_id` becomes the newest actor, `actor_count`
        increases by 1, and `created_at` is refreshed so it floats back to the top.
  - [ ] Once that row has been read (`read_at` is set), the next vote starts a
        **fresh** row rather than reviving the old one.
- [ ] **Insert-once events:** for `event_type` in `answer_created`,
      `comment_created`, `mentioned`, at most one row may ever exist per
      `(recipient_id, event_type, subject_type, subject_id)` — whether the existing
      row is read or unread. A second call with the same four values writes nothing.
- [ ] Every other `event_type` inserts a plain row, no deduplication.

### `emit_content_approved(db, *, kind, obj, question_id, parent_author_id=None)`

- [ ] Does nothing unless `obj.moderation_status == "approved"`.
- [ ] For `kind` of `answer` or `comment` **with** a `parent_author_id`, stages the
      owner's event (`answer_created` / `comment_created`). Questions have no owner
      event (nobody owns a question but its author, who is the actor).
- [ ] Parses `@mentions` out of `obj.body` and stages one `mentioned` notification
      per mentioned user, skipping usernames that don't exist and skipping
      anonymized users.
- [ ] Everything goes through `create_notification`, so self-no-op and insert-once
      apply automatically.
- [ ] `link` is `/questions/{question_id}` for all of them.

### `notify_vote_if_new(db, *, actor, target_type, target_id, target_author_id, question_id, value)`

- [ ] Silent when `value == 0` (that's a vote being retracted).
- [ ] Silent when this actor already has a vote row on this target — **only a
      user's first vote on a target notifies**, so toggling up→down→up doesn't spam.
- [ ] Otherwise stages a coalesced `vote_cast` with
      `coalesce_key = f"vote:{target_type}:{target_id}"`.
- [ ] The notification is **direction-neutral**: nothing stored anywhere reveals
      whether it was an upvote or a downvote.

### `notify_content_edited(db, *, kind, obj, question_id, question_author_id, actor_id)`

- [ ] Does nothing if the edit happened within `EDIT_NOTIFICATION_GRACE_SECONDS`
      (300 s, already in `config.py`) of the object's creation — fixing your own
      typo ten seconds later must stay silent.
- [ ] Otherwise stages a `content_edited` notification to the question author.
- [ ] Deliberately **not** deduplicated: three real edits produce three rows.

### `extract_mentions(body) -> set[str]` in `services/mentions.py`

- [ ] Returns the unique set of `@username` mentions found in the text, where a
      username is 3–30 characters of `[A-Za-z0-9_-]`.
- [ ] Ignores anything inside a fenced code block (```` ``` ````) — **including an
      unterminated fence that runs to the end of the text**.
- [ ] Ignores anything inside `inline code` backticks.
- [ ] `bob@example.com` must **not** produce a mention of `example`.
- [ ] A token longer than 30 characters is rejected outright, not truncated to 30.

## Out of scope

- **Reading** notifications — the list, the unread count, marking read. That's C-02.
- Any UI at all (bell, inbox page). C-03 / C-04.
- Actually calling these functions from answers, comments, or votes. Lane B does
  that when you tell them you're done (integration milestone 3).
- Direct messages. **Messages create no notifications in Knowly** — by design. The
  messages UI carries its own unread badge instead (C-09 / C-10).
- Email, push, or web-socket delivery. Notifications are database rows, full stop.

| `test_extract_mentions_ignores_code_spans` | `"hey @alice and @bob_ here"` → `{"alice", "bob_"}`; `` "`@alice` in code" `` → empty set; `"email bob@example.com"` → empty set | mention parsing |

Two things worth noticing:

- The mention test is a plain `def`, not `async` — no database at all. That's your
  proof that `extract_mentions` can be built and driven green before anything else in
  this ticket exists. Start there.
- `test_only_first_vote_notifies` records the vote with `factory.vote(...)` between
  the two calls. That's the test telling you *how* you're expected to detect "already
  voted": by looking for a row in `votes`, not by remembering anything.

**These five are a floor, not the whole spec.** The acceptance criteria they do *not*
check — and a reviewer will — include: never committing, the unterminated-code-fence
case, rejecting over-long mention tokens, a read row starting a fresh coalesce row,
the `EDIT_NOTIFICATION_GRACE_SECONDS` window, and all of `emit_content_approved`.
Green tests mean you haven't broken the contract; they don't mean you're finished.

## Technical notes

**Constraints (requirements, not suggestions):**
- Never commit. Not once, not "just to be safe". The caller owns the transaction.
- The signatures in `backend/app/services/notifications.py` are frozen — they were
  written into the Launch Pad stub precisely so B and D could code against them
  before you shipped.
- The complete event vocabulary you must support (owners in brackets):
  `answer_created`, `comment_created`, `mentioned`, `vote_cast` [B/D],
  `content_edited`, `content_deleted` [B], `friend_request`, `friend_accepted`,
  `friend_removed` [you, C-05/C-06], `moderation_pending`, `moderation_approved`,
  `moderation_rejected` [D].
- `link` is stored as a plain string path. You never import anything from Lane B to
  build it — that's deliberate, it keeps you two uncoupled.

**Files you will probably touch:**
- `backend/app/services/notifications.py` — replace the stub bodies.
- `backend/app/services/mentions.py` — replace the stub `extract_mentions`.
- `backend/app/models/notification.py` — **read only.** The columns you have are
  `recipient_id, actor_id, event_type, subject_type, subject_id, link,
  coalesce_key, actor_count, read_at, created_at`.

**Suggested approach — a proposal, not a mandate:**
1. Build `extract_mentions` first. It's pure string work, no database, and it has
   its own test. Strip fenced blocks, then inline code, then regex the rest.
2. Then `create_notification`, in three steps: self no-op → insert-once check →
   plain insert. Get those green before you attempt coalescing.
3. Coalescing last. Postgres can do it in one statement: an
   `INSERT ... ON CONFLICT (recipient_id, coalesce_key) WHERE <index predicate> DO
   UPDATE SET ...`. SQLAlchemy exposes this as
   `from sqlalchemy.dialects.postgresql import insert`. If the upsert fights you,
   a SELECT-then-INSERT-or-UPDATE also passes the tests — write the simple version,
   note the trade-off in your PR, and move on. Shipping beats elegance here.
4. `emit_content_approved`, `notify_vote_if_new`, `notify_content_edited` are thin
   wrappers once `create_notification` is solid.

**Words you'll meet in this ticket:**
- **Seam** — a place where one person's code calls another person's code. Yours is
  the app's single write-seam for notifications.
- **Stub** — a fake function with the real signature and an empty body, so people
  can call it before it exists. You are replacing stubs; B and D are still on theirs.
- **Stage vs commit** — *staging* adds a row to the open transaction (`db.add`,
  `db.flush`); *committing* makes it permanent. You stage; whoever called you commits.
- **Idempotent** — doing it twice has the same effect as doing it once.
- **Coalesce** — collapse many events into one row that carries a count.
- **Upsert** — "insert, or update if it's already there", in one database statement.
- **Partial unique index** — a uniqueness rule that only applies to *some* rows.
  Yours: `(recipient_id, coalesce_key)` must be unique, but **only** while
  `coalesce_key IS NOT NULL AND read_at IS NULL`. That single line of schema is what
  makes "unread vote rows merge, read ones don't" work.

## Verify it yourself

```bash
docker-compose up --build
docker-compose exec backend pytest tests/lane_c/test_c01_notification_seam.py -v
```

Then, in a Python shell or a scratch test, confirm the two behaviours that bite
people most often:
- Call `create_notification` twice with identical `answer_created` arguments →
  exactly one row in `notifications`.
- Call it three times with the same `coalesce_key` → **one** row with
  `actor_count = 3`. Set `read_at` on it, call a fourth time → now **two** rows.
