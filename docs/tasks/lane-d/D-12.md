# [D-12] A user can search from the app, and share the search they ran

**Lane:** D — AI & Trust
**Task ID:** D-12
**Size:** ~1–1.5 days
**Depends on:** **D-11**.
**Blocks:** nothing — it's the end of the search spine.

---

## Problem

`/search` renders a placeholder, so the search API has no consumer and users can only
browse. And the highlight the API returns arrives as a string containing `<mark>` tags —
rendering that carelessly is the fastest way to put a cross-site-scripting hole in the app.

## Proposed outcome

`SearchPage` — a query box and filters that all live in the URL, results with the matched
words highlighted safely, and pagination.

## Acceptance criteria

- [ ] A query box plus filter controls (tags, author, status, date range) and a sort
      selector.
- [ ] **All of them reflected in the URL query string**, so a search is shareable and the
      back button works.
- [ ] Changing any control refetches **from page 1**.
- [ ] Results render the card fields (title, excerpt/highlight, tags, author, vote total,
      answer count) and link to `/questions/:id`.
- [ ] The `highlight` is rendered by **splitting on the `<mark>` / `</mark>` markers and
      styling the matched spans** — **never** by injecting it as raw HTML.
- [ ] Paginated, with a visible total count.
- [ ] Two **distinct** empty states: "No questions match your search" after a search that
      found nothing, versus the initial state before any query has been entered.

## Out of scope

* Any backend change (D-11 owns it).
* Search suggestions, autocomplete, or recent-search history.
* Searching anything but questions.
* Replacing the home feed. `/search` is its own screen (B-11 owns `/home`).

## The tests that grade this task

## Technical notes

**Constraints (requirements, not suggestions):**
* **Never `dangerouslySetInnerHTML` the highlight.** Split the string on `<mark>` and
  `</mark>` and render the pieces as React nodes — plain text in between, a styled
  `<mark>` element for the matched parts. React escapes text nodes for you, so the
  question body can contain anything and stay inert. Injecting the raw string means any
  question body is executable in every searcher's browser.
* Filters live in the URL (`useSearchParams`), not only in component state. That's what
  makes a search shareable and the back button meaningful.
* Reset to page 1 when a filter changes — otherwise you land on page 4 of a 2-page result
  set and see nothing.
* Use the `api` wrapper; `SearchResult` and `Paginated<T>` are already in `lib/types.ts`.

**Files you will probably touch:**
* `frontend/src/pages/SearchPage.tsx` — replace the `<Placeholder>`.
* Reuse Lane B's question-card component if it exists by the time you get here.

**Suggested approach:**
1. Query box and results list first, with `q` in the URL. Nothing else.
2. Then the highlight renderer — a small pure function
   `(highlight: string) => ReactNode[]`. Write it early; everything else is ordinary form
   work, and this is the bit that has to be right.
3. Then the filters one at a time, each reading and writing `useSearchParams`.
4. Then the sort selector and pagination.
5. Both empty states last, and keep them genuinely different — "you haven't searched yet"
   and "we found nothing" are different messages to a user.

**Words you'll meet in this ticket:**
* **XSS (cross-site scripting)** — running attacker-supplied script in another user's
  browser. Injecting server HTML into the DOM is the classic route in.
* **`dangerouslySetInnerHTML`** — React's escape hatch for raw HTML. Named that way on
  purpose. Not needed here.
* **Query string as state** — storing view state in the URL so it's shareable and
  navigable.
* **Marker parsing** — turning `a <mark>b</mark> c` into three React nodes instead of
  trusting it as HTML.

## Verify it yourself

1. Search for a word → results appear with the word highlighted, and **the URL contains
   the query**. Paste that URL into a new tab → the same results.
2. Add a tag filter and a sort → both appear in the URL; back button undoes them one at a
   time.
3. Go to page 3, then change a filter → you land on **page 1**, not an empty page 3.
4. Search for something with no matches → "No questions match your search". Clear the box
   → the *initial* state, with a different message.
5. Search with an empty query → results appear with plain excerpts and no highlighting,
   not an error.
6. **The XSS check:** post a question whose body contains
   `<img src=x onerror="alert('xss')">`, then search for a word in that body → the result
   renders as **visible text**, no alert fires, and no element is created. Do this before
   you open the PR.
7. Type an awkward query — `"quoted phrase"`, `cats OR dogs`, a lone `'` → results or an
   empty state, never a crash.
