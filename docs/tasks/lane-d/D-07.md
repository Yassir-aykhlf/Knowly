# [D-07] An admin can review held content and decide whether it goes public

**Lane:** D — AI & Trust
**Task ID:** D-07
**Size:** ~1.5 days
**Depends on:** **D-02**, **D-06**. Stages notifications via **C-01** (stub).
**Blocks:** D-08 (the queue UI).

---

## Problem

D-02 can hold content, and nothing can un-hold it. Anything the automated screen flags is
invisible forever, with no human in the loop — which makes the moderation feature worse
than useless: it silently eats legitimate posts.

## Proposed outcome

Three admin-only endpoints: a unified queue of everything awaiting review, and approve /
reject verdicts that notify the author and correctly release the notifications that were
queued behind the hold.

## Acceptance criteria

**Every route requires the admin role** (`require_admin`, A-01).

### `GET /api/moderation/pending?limit`

- [ ] Held (`pending`) items across **all three** content types, unified as
      `{ type, id, title (questions only), body, author, moderation_note, question_id,
      created_at }`.
- [ ] **Oldest first** — reviewed in arrival order, so nothing rots at the bottom.
- [ ] Capped by `limit`.
- [ ] `question_id` always points at the page where the content lives — resolve a
      comment → answer → question chain **in a single batch**, not per row.

### `PUT /api/moderation/{type}/{id}/approve`

- [ ] Unknown `type` → **404**; missing content → **404**.
- [ ] **Lock the row (`FOR UPDATE`)** so two admins clicking at once serialize.
- [ ] Content not in `pending` **or** `rejected` → **409**. (Rejected content **is**
      re-approvable — an admin can reverse their own call.)
- [ ] Set `approved`, clear the note, and notify the author (`moderation_approved` — a
      system event with **no actor**).
- [ ] Then run the **on-approval flush**: emit the owner notification and queued mentions
      through the **same idempotent helper used at creation**. That is what makes
      held-then-approved content notify the owner **exactly once** — never twice, never
      zero.
- [ ] Return `{ type, id, moderation_status: "approved" }`.

### `PUT /api/moderation/{type}/{id}/reject { note }`

- [ ] `note` trimmed, 1–1 000, **required** → **400** if empty.
- [ ] Lock the row. Only `pending` content is rejectable → **409** otherwise.
- [ ] Set `rejected`, store the note, notify the author (`moderation_rejected`).
- [ ] **No** owner notification and **no** mention flush — the post never became visible,
      and mentions are derived at approval time only.
- [ ] Return `{ type, id, moderation_status: "rejected" }`.

## Out of scope

* The queue UI — D-08.
* Deciding what gets flagged — D-02.
* Deleting content. Moderators reject; authors delete (B-05/B-07/B-09).
* Banning users, or a moderation audit log. Not in this project.

## Technical notes

**Constraints (requirements, not suggestions):**
* Approve accepts `pending` **and** `rejected`; reject accepts only `pending`. That
  asymmetry is deliberate — reversing a rejection is a legitimate admin action, "rejecting"
  a live post is not (it would silently unpublish something people have already read).
* `SELECT ... FOR UPDATE` before you check the status. Without the lock, two admins can
  both read `pending` and both act.
* The on-approval flush must go through the **same** idempotent helper creation uses
  (C-01's `emit_content_approved`). Writing a second "notify the owner" path here is how
  you get double notifications.
* `moderation_approved` and `moderation_rejected` carry **no actor** — the author never
  learns which moderator acted.

**Files you will probably touch:**
* `backend/app/routers/moderation.py`, `backend/app/schemas/moderation.py`.

**Suggested approach:**
1. A `{type: Model}` map so all three types share one code path, with the unknown-type 404
   falling out of the lookup.
2. The queue: three `SELECT`s (one per type) filtered to `pending`, merged and sorted by
   `created_at`, capped by `limit`. Then one batch pass to resolve `question_id` for the
   answers and comments.
3. Approve and reject as one helper each, both starting with load-locked → 404 → status
   check → 409.
4. Notifications last, and write the four cases out explicitly before you code them.

**Words you'll meet in this ticket:**
* **`SELECT ... FOR UPDATE`** — takes a row lock, so a second transaction touching the
  same row waits. How you serialize two admins.
* **Idempotent emission** — safe to call twice; the notification appears once.
* **State machine** — the legal transitions between `pending`, `approved` and `rejected`.
  Every 409 in this ticket is an illegal transition.
* **Unified queue** — one list built from three tables, presented in one shape.

## Verify it yourself

```bash
docker-compose exec backend pytest tests/lane_d/test_d07_moderation_queue.py -v
```

By hand, as an admin:
1. Hold a question, an answer **and** a comment (set `moderation_status='pending'` in
   `psql`) → all three appear in the queue, oldest first, each with a `question_id` that
   actually opens the right page — including the **comment**, whose id has to be resolved
   through its answer.
2. Approve the question → 200; a stranger can now see it in the feed.
3. Approve it again → 409.
4. Reject the answer with an empty note → 400. With a real note → 200, and its author sees
   the note.
5. Approve the **rejected** answer → 200 (reversal is allowed).
6. Once C-01 has shipped, the important one: post an answer that gets **held**, then
   approve it → the question's author gets **exactly one** `answer_created` notification.
   Approve it again → still exactly one.
7. Reject a held answer that contained an `@mention` → the mentioned user gets **nothing**.
8. As a normal user, call any of these → 403 (once A-01 is wired).
