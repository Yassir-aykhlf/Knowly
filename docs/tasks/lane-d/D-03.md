# [D-03] A user can keep separate AI conversations, and nobody can read anyone else's

**Lane:** D — AI & Trust
**Task ID:** D-03
**Size:** ~1 day
**Depends on:** **A-01** (auth — the stub covers you until then). Reads
`content.can_view` (**B-01**, stub).
**Blocks:** D-04, D-05.

---

## Problem

The `ai_conversations` and `ai_messages` tables exist and nothing writes to them. Before
anything can stream a reply, there has to be somewhere to keep the thread — and a strict
rule about who can open it.

## Proposed outcome

Four owner-scoped endpoints under `/api/ai/conversations`: create (optionally linked to a
question), list, read with messages, delete.

## Acceptance criteria

- [ ] **Every route is scoped to the caller.** Another user's conversation is a **404** —
      never a 403, because the existence of a conversation is itself private.
- [ ] `POST /conversations { question_id? }` → creates a conversation owned by the caller.
      **201**, returning `{ id, title, question, created_at, updated_at }`.
  - [ ] If `question_id` is given it must be **viewable** (else **404**); store the link
        and seed the title `"Help with: {question.title}"`, capped at 80 characters.
- [ ] `GET /conversations` → the caller's conversations, **most-recently-updated first**.
- [ ] `GET /conversations/{id}` → the conversation plus its `messages[]`
      (`{ id, role, content, created_at }`) in **chronological** order.
- [ ] `DELETE /conversations/{id}` → deletes it; `ai_messages` cascade in the database.
      **204**.

## Out of scope

* Sending a message and streaming a reply — **D-04**. This task creates the container,
  not the conversation content.
* The AI pages — D-05.
* Renaming a conversation by hand. Titles are derived (here, or from the first message in
  D-04).
* Sharing a conversation with another user. Not in this project.

## Technical notes

**Constraints (requirements, not suggestions):**
* 404, never 403, for someone else's conversation — and apply it uniformly across all
  three by-id routes. One route returning 403 undoes the other two.
* Scope by owner in the **query** (`WHERE user_id = :me`), not with a load-then-check.
  It's harder to forget.
* `ai_messages` cascade at the database level — you don't delete them yourself.

**Files you will probably touch:**
* `backend/app/routers/ai.py`, `backend/app/schemas/ai.py`,
  `backend/app/models/ai.py` (read only).

**Suggested approach:**
1. A `load_own_conversation(db, id, user)` helper that raises the 404 — all three by-id
   routes go through it, so the rule can't drift.
2. Create, then list, then get, then delete. Each is a handful of lines.
3. The question link last: fetch, `can_view`, 404, then build the title with a slice
   at 80.

**Words you'll meet in this ticket:**
* **Owner-scoped** — every query is filtered to the caller. The default posture for
  private data.
* **404 vs 403** — "nothing here" vs "not allowed". For private resources, 404 for both,
  so an attacker can't map what exists.
* **Cascade delete (in-DB)** — the database removes children automatically when the
  parent goes, declared in the schema.

## Verify it yourself

```bash
docker-compose exec backend pytest tests/lane_d/test_d03_ai_crud.py -v
```

By hand, as two users:
1. Create a conversation → 201; list → it's there; get it → `messages: []`.
2. As the **other** user, GET and DELETE that id → **404** both times.
3. Create one with a `question_id` → the title starts `Help with:` and `question` is
   nested. Try a very long question title → the stored title is capped at 80 characters.
4. Create with a `question_id` that doesn't exist → 404.
5. Create three conversations, touch the `updated_at` of the oldest in `psql` → it moves
   to the top of the list.
6. Delete a conversation that has messages → 204, and `ai_messages` for it are gone too.
