# [D-01] The app can talk to a language model through one function, and fails predictably when it can't

**Lane:** D — AI & Trust
**Task ID:** D-01
**Size:** ~1 day
**Depends on:** nothing. Start here (it's the head of the AI spine).
**Blocks:** D-04 (streaming), and therefore D-05.

---

## Problem

Nothing in the app can reach a language model. And the naive version of this — calling
the provider's HTTP API from the endpoint that needs it — spreads provider-specific
details and, worse, provider-specific *failures* across the codebase. A streaming
endpoint needs to tell "you're rate-limited" apart from "the key is missing" apart from
"it timed out", and a raw `httpx` exception can't express that.

## Proposed outcome

`services/llm.py` — one streaming function, one message type, and a small hierarchy of
exceptions that the streaming endpoint can translate into clean events for the user.

## Acceptance criteria

- [ ] `chat_stream(messages: list[ChatMessage]) -> AsyncIterator[str]` streams the
      assistant's reply **token by token**.
- [ ] `ChatMessage = { role: "system" | "user" | "assistant", content }`.
- [ ] Default provider is **OpenAI** (`/v1/chat/completions`, `stream: true`,
      `settings.LLM_MODEL`).
- [ ] A **provider registry**: adding a provider means adding one
      "async generator (messages) → tokens" function, with no changes at any call site.
- [ ] Structured errors, all subclassing a base `LLMError`:
  - [ ] `LLMUnavailable` — missing key, unknown provider, HTTP ≥ 400, network failure.
  - [ ] `LLMRateLimited` — HTTP 429.
  - [ ] `LLMTimeout` — read or connect timeout.
- [ ] A missing `LLM_API_KEY` or an unknown `LLM_PROVIDER` raises `LLMUnavailable`
      **immediately**, at call time — not on the first iteration.
- [ ] Provider errors surface **while iterating**.
- [ ] The API key is read at call time, and is **never logged and never included in any
      exception message**. Don't echo the provider's response body either — it can quote
      the key back at you.
- [ ] A generous read timeout: a model can pause mid-stream and that's normal.

## Out of scope

* The HTTP endpoint and SSE translation — D-04.
* Conversation storage and history — D-03.
* Rate limiting the *user* — D-04. This module doesn't know about users.
* Prompt construction. D-04 builds the message list; you send it.
* Moderation. Different sub-spine entirely (D-02).

## The tests that grade this task

```bash
docker-compose exec backend pytest tests/lane_d/test_d01_llm_client.py -v
```

Three tests, all synchronous, no network.

| Test | What it pins down | AC |
|---|---|---|
| `test_missing_key_raises_unavailable` | with `LLM_API_KEY = ""`, `llm.chat_stream([...])` raises `LLMUnavailable` | fail fast |
| `test_unknown_provider_raises_unavailable` | with a nonsense `LLM_PROVIDER`, same | fail fast |
| `test_error_hierarchy_is_catchable_as_llmerror` | `LLMTimeout`, `LLMRateLimited` and `LLMUnavailable` are all `issubclass(..., LLMError)` | the hierarchy |

**Read the first two tests very carefully — they encode a Python trap that will cost you
an afternoon.** They call `llm.chat_stream([...])` and expect it to raise *there*, inside
`pytest.raises`. They never `await` it and never iterate it. If you write `chat_stream`
as a plain `async def ... yield` async generator, **calling it does nothing at all** — the
body doesn't run until something iterates it, so no exception is raised and the test
fails. You need a regular `def chat_stream(...)` that validates config, then returns an
async iterator. (The other tests also monkeypatch `llm.settings.*`, so read settings
inside the function, not at import.)

**Not graded here, but still required:** the actual OpenAI call, token-by-token
streaming, the registry, mapping 429 → `LLMRateLimited` and timeouts → `LLMTimeout`, and
the key-never-leaks rule. Verify those by hand.

## Technical notes

**Constraints (requirements, not suggestions):**
* Fail fast on configuration, lazily on the network. Config errors are knowable before
  you open a socket; provider errors aren't.
* Never put the provider's raw response body into an exception message. Error bodies
  routinely include the request that caused them.
* Read `settings` at call time. The tests monkeypatch it, and so does anyone changing
  `.env` without a rebuild.

**Files you will probably touch:**
* `backend/app/services/llm.py` — replace the stub.
* `LLM_PROVIDER`, `LLM_API_KEY`, `LLM_MODEL` are already in `config.py`.

**Suggested approach:**
1. Define `LLMError` and its three subclasses, plus `ChatMessage` (a dataclass or
   `NamedTuple` — it must accept positional args). That's one test green already.
2. Write `chat_stream` as a **regular function**: validate the key and look up the
   provider in the registry, raising `LLMUnavailable` on either — then return the
   provider's async generator. That's the other two tests.
3. Then the OpenAI generator itself: `httpx.AsyncClient.stream(...)`, parse
   `data: ` lines, yield the content deltas, stop at `[DONE]`.
4. Map the error cases as you go: 429 → `LLMRateLimited`, timeout exceptions →
   `LLMTimeout`, everything else → `LLMUnavailable`.

**Words you'll meet in this ticket:**
* **Async generator** — an `async def` containing `yield`. Calling it returns an
  iterator; **the body doesn't run until you iterate**. That's the trap above.
* **Structured errors** — a small class hierarchy instead of one generic exception, so
  callers can react differently to different failures.
* **Provider registry** — a dict from provider name to implementation, so adding one
  doesn't mean editing call sites.
* **Fail fast** — detect a broken configuration at the earliest possible moment.

## Verify it yourself

```bash
docker-compose exec backend pytest tests/lane_d/test_d01_llm_client.py -v
```

By hand, in a Python shell inside the container:
1. With a real key set, iterate `chat_stream([ChatMessage("user", "Say hi")])` → tokens
   arrive **progressively**, not as one lump at the end. (Print each with a timestamp.)
2. Blank the key → `LLMUnavailable` raised **on the call**, before any iteration.
3. Set `LLM_PROVIDER=banana` → `LLMUnavailable`, same.
4. Point the base URL at a dead host → `LLMUnavailable` while iterating, and the message
   contains no key material.
5. Set a 1-millisecond timeout → `LLMTimeout`.
6. `try: ... except llm.LLMError:` catches every one of them.
