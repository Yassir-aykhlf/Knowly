# [D-09] A user can attach files to a post, and only people who can see the post can open them

**Lane:** D — AI & Trust
**Task ID:** D-09
**Size:** ~2 days
**Depends on:** **A-01** (auth stub covers you). Reads `content.can_view` (**B-01**, stub).
**Blocks:** D-10, and **Lane B** — their ask and answer forms bind attachments through
your seam (integration milestone 6).

---

## Problem

The `attachments` table exists and nothing writes to it. Nobody can post a screenshot of
the error they're asking about. And the naive fix — a public uploads folder — would mean
every file ever attached to a held or private post is readable by anyone who guesses a URL.

## Proposed outcome

Upload, serve and delete endpoints backed by a **private** volume with an auth-gated read
rule, plus the binding seam Lane B calls to attach files to a post.

## Acceptance criteria

### Upload — `POST /api/files` (multipart)

- [ ] Reject > 5 MB → **400 `validation_error`** with `fields.file`.
- [ ] **Validate by content** (magic bytes), allowlisting PNG / JPEG / WebP / GIF / PDF /
      text / Markdown → **400** otherwise.
- [ ] Store under a UUID filename in the **private** uploads volume — never web-exposed.
- [ ] Optional at-upload association `{ parent_type, parent_id }` — **both or neither**
      (→ **400**). The parent must exist (**404**) and be **owned by the caller** (**403**).
- [ ] **201** `AttachmentOut { id, original_filename, mime_type, size_bytes,
      url: "/api/files/{id}", parent_type, parent_id, created_at }`.

### Serve — `GET /api/files/{id}`

- [ ] Auth required. The **read rule** (`can_read`): allowed if the caller is the
      **uploader**, **or** an **admin**, **or** the file is attached to content the caller
      may see.
- [ ] **Unattached files are private to their uploader.**
- [ ] Any disallowed read → **404**, never 403 — existence is not leaked.
- [ ] Serve inline for images, as an attachment otherwise, with a correct (UTF-8-safe)
      filename.

### Delete — `DELETE /api/files/{id}`

- [ ] Missing → **404**. A **non-uploader → 403** — this endpoint deliberately
      distinguishes them, unlike the read path.
- [ ] Delete the row, then best-effort remove the file. **204**.

### The binding seam (for Lane B)

- [ ] `bind_attachments(db, *, attachment_ids, parent_type, parent_id, user)` — attach the
      caller's own, currently-unbound (or already-bound-to-this-same-post) files to a post.
  - [ ] Enforce **≤ 10 per post**, counted against what's already attached.
  - [ ] Reject unknown or other-owner files (**400**), and files bound to another post
        (**400**).
  - [ ] Binding is **additive** — removal goes through `DELETE /api/files/:id`, never by
        omission from a later edit.
  - [ ] Staged; the caller commits.
- [ ] `attachments_for(parent_type, ids) -> {parent_id: [Attachment]}`, oldest first.
- [ ] `delete_attachments_for(parent_type, ids) -> [stored_path]` — deletes rows in the
      caller's transaction and returns paths for post-commit file removal.

## Out of scope

* The upload UI and the attachment list — D-10.
* Avatars — that's **A-09**, a different volume with different rules (public, image-only,
  normalised). Don't merge the two.
* Virus scanning, image resizing, thumbnails. Not in this project.
* Calling `bind_attachments` from question creation — **Lane B** does that.

## The tests that grade this task

```bash
docker-compose exec backend pytest tests/lane_d/test_d09_files_api.py -v
```

Four tests. They build real PNG bytes with Pillow.

| Test | What it pins down | AC |
|---|---|---|
| `test_upload_returns_authgated_url` | **201**, `body["url"] == f"/api/files/{body['id']}"`, and `mime_type == "image/png"` | upload + URL shape |
| `test_upload_disallowed_type_is_rejected` | bytes `b"\x00\x01\x02BOGUS"` sent as `("evil.png", ..., "image/png")` → **400** with `"file"` in `fields`. The filename and the declared MIME both say PNG; **the content doesn't** | content sniffing |
| `test_uploader_can_read_unattached_file_but_others_cannot` | the uploader gets **200**; a different user gets **404** — with the comment "existence not leaked" | the read rule |
| `test_only_uploader_can_delete` | a non-uploader `DELETE` → **403**; the uploader → **204** | delete |

Read the last two together: **the same file gives 404 on an unauthorized read and 403 on
an unauthorized delete.** That looks inconsistent and is deliberate — a read probe would
let someone enumerate file ids, while a delete already requires knowing an id you were
given. The spec calls it out explicitly, and both tests exist to stop you "fixing" it.

**Not graded here, but still required:** the 5 MB cap, the full allowlist, at-upload
association and its three error cases, admin read access, attached-content read access
(the interesting half of `can_read`), inline-vs-download serving, and **the entire binding
seam** — all three functions, which is the part Lane B depends on.

**The milestone test that grades the seam:**
`tests/milestones/test_m6_files.py` uploads a file, creates a question through **Lane B's**
endpoint with `attachment_ids: [id]`, and asserts the question detail's `attachments`
array contains it with the right `url`. Red until B swaps their empty stub for your
functions. It is the only automated check of `bind_attachments` anywhere.

## Technical notes

**Constraints (requirements, not suggestions):**
* Private volume. Avatars are served as static files by nginx; **uploads are not** — every
  read goes through your endpoint so the rule can run. Check `nginx.conf` and confirm.
* Validate by magic bytes. The filename and `Content-Type` are both attacker-controlled.
* 404 on read, 403 on delete. Both tests assert it; don't unify them.
* Binding is additive. An edit that omits an id must not silently detach a file — Lane B
  re-binds on every edit, and detach-by-omission would delete attachments on every save.

**Files you will probably touch:**
* `backend/app/routers/files.py`, `backend/app/services/files.py` (replace the stubs),
  `backend/app/schemas/attachment.py`.
* `UPLOAD_MAX_BYTES` and `UPLOAD_DIR` are already in `config.py`.

**Suggested approach:**
1. Upload without the optional association first — size check, sniff, store, insert. Two
   tests green.
2. Then the serve endpoint with only the uploader-or-admin half of `can_read`. Third test.
3. Then delete. Fourth test.
4. Then the attached-content half of `can_read` (via `content.can_view`), and the
   at-upload association.
5. The seam functions last. `bind_attachments` is the fiddly one: load the requested rows,
   reject anything not owned / bound elsewhere, count existing attachments for the cap,
   then set `parent_type`/`parent_id` and flush.

**Words you'll meet in this ticket:**
* **Magic bytes** — the leading bytes identifying a file's real format.
* **Content sniffing** — determining a type from content instead of metadata.
* **Auth-gated URL** — a file URL that runs a permission check on every request, as
  opposed to a static path anyone can fetch.
* **Binding** — attaching an uploaded file to a post after the fact, which is why uploads
  can exist unattached at all.
* **Additive** — binding only ever adds; nothing is removed by leaving it out.

## Verify it yourself

```bash
docker-compose exec backend pytest tests/lane_d/test_d09_files_api.py -v
```

By hand, as two users plus an admin:
1. Upload a PNG → 201 with an `/api/files/{id}` URL that renders **inline** in a browser
   tab. Upload a PDF → it downloads with its original filename intact (try a filename with
   an accent in it).
2. Upload a 6 MB file → 400. Upload a `.exe` renamed to `.png` → 400.
3. As another user, GET the unattached file → **404**. As an **admin** → 200.
4. Attach the file to a question (via Lane B, or by setting `parent_type`/`parent_id` at
   upload) → now any user who can see that question can read it. Set the question to
   `pending` → strangers get 404 again.
5. Try to fetch the file directly from the uploads volume path over HTTP (e.g.
   `https://localhost/uploads/<uuid>`) → it must **not** be served.
6. As a non-uploader, DELETE → **403**. As the uploader → 204, and the file is gone from
   disk.
7. Bind 10 files to one post, then try an 11th → 400. Bind a file already attached to
   another post → 400.
