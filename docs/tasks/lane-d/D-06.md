# [D-06] The first admin exists, whether they registered before or after the server booted

**Lane:** D — AI & Trust

**Size:** ~0.5 day
**Depends on:** nothing (the Launch Pad). Lane A's registration (**A-02**) applies the same

## Problem

`users.role` exists, `require_admin` checks it, and no code path ever sets it to
`"admin"`. There is a bootstrapping problem: the moderation queue needs an admin, and the
only way to become one is to already be one.

## Proposed outcome

The dual-path first-admin mechanism — promote at startup if the account already exists,
set the role at creation if it doesn't — plus a CLI for promoting anyone later.

## Acceptance criteria

- [ ] The user whose email equals `INITIAL_ADMIN_EMAIL` becomes an admin **two ways**:
  1. [ ] at **backend startup**, promote them if the account already exists;
  2. [ ] at **account creation**, set `role = "admin"` when the email matches — A-02 and
         A-13's OAuth first-login both call the same helper.
- [ ] Both paths are needed so it works whether the admin registers **before** or **after**
      first boot.
- [ ] `promote_to_admin(email)` is **idempotent** (promoting twice is fine) and returns the
      user, or `None` if no such account exists.
- [ ] Exposed as `python -m app.cli promote-admin <email>`.
- [ ] Publish the `is_initial_admin(email)` helper so **Lane A** can delete their local
      stub.

## Out of scope

* The moderation queue itself — D-07.
* An admin UI for managing roles. The CLI is the whole admin-management story.
* Demoting an admin. Not in this project.
* Anything about `require_admin` — that's A-01's dependency; you only set the column it
  reads.

## Technical notes

**Constraints (requirements, not suggestions):**
* Case-insensitive email comparison, both directions. `Boss@Example.com` in `.env` and
  `boss@example.com` in the database must match.
* Idempotent: promoting an existing admin is a no-op that still returns the user.
* Startup promotion must not crash the app when `INITIAL_ADMIN_EMAIL` is empty or the
  account doesn't exist. That's the normal case on a fresh database.

**Files you will probably touch:**
* `backend/app/services/admin.py` — replace the stub.
* `backend/app/cli.py`, `backend/app/main.py` (the startup hook).
* `INITIAL_ADMIN_EMAIL` is already in `config.py`.

**Suggested approach:**
1. `promote_to_admin(db, email)` first — `SELECT ... WHERE lower(email) = lower(:email)`,
   set the role, return the user or `None`. Both tests green.
2. `is_initial_admin(email)` — a two-line pure function. This is the one Lane A imports.
3. The startup hook: call `promote_to_admin` on boot, wrapped so an empty setting or a
   missing account is a quiet no-op.
4. The CLI last: `python -m app.cli promote-admin <email>` opening its own session.

**Words you'll meet in this ticket:**
* **Bootstrapping problem** — needing an admin to create an admin. Solved by a path that
  doesn't require one.
* **Idempotent** — running it twice changes nothing beyond running it once.
* **Startup hook** — code that runs when the app boots, before it serves requests.

## Verify it yourself

```bash
docker-compose exec backend pytest tests/lane_d/test_d06_admin_bootstrap.py -v
```

By hand — **both orders matter**:
1. **Register first, then boot:** create an account with `boss@example.com`, set
   `INITIAL_ADMIN_EMAIL=boss@example.com` in `.env`, restart the backend → that user's
   `role` is now `admin`.
2. **Boot first, then register:** with the setting already in place and no such account,
   restart (no crash), then register `boss@example.com` → the new user is created as
   `admin`.
3. Set the email in a different case than the account's → still promoted.
4. Leave `INITIAL_ADMIN_EMAIL` empty and restart → the app boots normally and nobody is
   promoted.
5. `docker-compose exec backend python -m app.cli promote-admin someone@example.com` →
   they become an admin. Run it again → no error. Run it for an unknown address → a clean
   "no such user" message, not a traceback.
6. Once D-07 exists: the admin gets 200 from `/api/moderation/pending`, a normal user 403.
