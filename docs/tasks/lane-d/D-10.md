# [D-10] A user can attach a file while writing a post, and see attachments under posts

**Lane:** D — AI & Trust
**Task ID:** D-10
**Size:** ~1–1.5 days
**Depends on:** **D-09**.
**Blocks:** integration milestone 6 — **Lane B** mounts both of these components in their
ask/answer forms and on the question page.

---

## Problem

The files API works and nothing in the app can reach it. `<FileUpload>` and
`<AttachmentList>` are Launch Pad stubs that render nothing, so Lane B's forms have a slot
where attachments should be and every post displays without them.

## Proposed outcome

Two components Lane B drops in: an uploader that hands back attachment ids for the parent
form to submit, and a list that renders a post's attachments with previews and a delete
for the owner.

## Acceptance criteria

### `<FileUpload onUploaded>`

- [ ] Lets the user pick **or drag** files.
- [ ] Uploads each via `POST /api/files`, showing progress.
- [ ] Shows **per-file** validation errors, surfacing the server's `fields.file` message —
      one bad file must not sink the others.
- [ ] Calls `onUploaded(attachment)` with the returned metadata, so the parent form can
      collect ids.
- [ ] Enforces the **≤ 10** hint client-side.
- [ ] Lets the user remove a not-yet-submitted upload.

### `<AttachmentList items onDelete?>`

- [ ] Renders a post's attachments: **inline preview for images**, and a download
      affordance (filename + size) for everything else.
- [ ] Every link points at the **auth-gated** `url` from the API.
- [ ] When the viewer is the uploader, offer delete → `DELETE /api/files/:id`, with an
      **optimistic** removal and a revert on error.

## Out of scope

* Any backend change (D-09 owns it).
* Mounting these into the ask form or the question page — **Lane B** does that (B-12,
  B-13). You build and export; they mount.
* Avatars (A-09) — different component, different endpoint.
* Image editing, cropping, or reordering attachments.

## Technical notes

**Constraints (requirements, not suggestions):**
* `onUploaded(attachment)` is the whole contract with Lane B — one call per successful
  upload, carrying the full metadata object. Don't change its shape; their forms are
  written against it.
* Files are uploaded **immediately**, before the post exists, and bound later by id. That's
  why an unattached file is private to its uploader (D-09) and why the parent form only
  ever handles ids.
* Use `postForm` from `lib/api.ts` for multipart — it's already there for this.
* Attachment URLs are auth-gated: an `<img src>` works because the browser sends the
  session cookie, but only for a user who's allowed to see it. Handle a broken image
  gracefully rather than showing a broken-icon.

**Files you will probably touch:**
* `frontend/src/components/FileUpload.tsx`, `frontend/src/components/AttachmentList.tsx` —
  replace the stubs.
* `Attachment` already exists in `lib/types.ts` — frozen.

**Suggested approach:**
1. `<AttachmentList>` first — it's presentational and it gives you something to look at.
2. Then `<FileUpload>` with a plain file input, one file at a time, no progress.
3. Then multiple files with per-file state (`queued / uploading / done / error`) — a small
   array of objects, each rendering its own row and its own error.
4. Then drag-and-drop (`onDragOver` / `onDrop`), the 10-file cap, and removal.
5. Delete + optimistic revert in `<AttachmentList>` last.
6. Build a scratch route mounting both so you can exercise them before Lane B is ready.

**Words you'll meet in this ticket:**
* **Per-file state** — each upload tracks its own progress and error, so one failure
  doesn't blank the batch.
* **Multipart form data** — the encoding used for file uploads. `postForm` handles it.
* **Optimistic removal** — take it out of the list immediately, put it back if the server
  says no.
* **Auth-gated URL** — a URL that runs a permission check per request, unlike a static
  file path.

## Verify it yourself

Mount both components on a scratch page.

1. Pick a PNG → progress shows, then `onUploaded` fires with the metadata (log it).
2. Drag three files in at once → all three upload, each with its own row.
3. Include a `.exe` renamed to `.png` in a batch → **that row** shows the server's error;
   the others still succeed.
4. Include a 6 MB file → its row shows the size error.
5. Try to add an 11th file → blocked client-side with a clear message.
6. Remove a not-yet-submitted upload → its row disappears and its id is no longer reported
   to the parent.
7. `<AttachmentList>` with a mix of PNG and PDF → the image previews inline, the PDF shows
   a filename and size with a download link that works.
8. As the uploader, delete an attachment → it disappears immediately. Stop the backend and
   delete another → it comes **back** and a toast appears.
9. Log in as a different user and view the same list → no delete controls, and images that
   they aren't allowed to see fail gracefully rather than showing a broken icon.
