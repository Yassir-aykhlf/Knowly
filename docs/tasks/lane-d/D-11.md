# [D-11] A user can find questions by words, tags, author, status or date

**Lane:** D — AI & Trust
**Task ID:** D-11
**Size:** ~2 days
**Depends on:** nothing (the Launch Pad). Reads `content.visible_filter` (**B-01**, stub).
The `search_vector` trigger already exists in the initial migration.
**Blocks:** D-12.

---

## Problem

The only way to find a question is to scroll the feed. `questions.search_vector` is
maintained by a Postgres trigger on every insert and update, with a GIN index over it, and
nothing queries it — the whole search infrastructure is sitting there unused.

## Proposed outcome

`GET /api/search` — full-text search over questions with combinable filters, sensible
ranking, and a highlighted snippet showing why each result matched.

## Acceptance criteria

- [ ] Query params, all optional: `q` (≤ 200), `tag` (**repeatable**), `author` (≤ 30),
      `status ∈ unanswered | answered | accepted`, `from` / `to` (dates),
      `sort ∈ relevance | newest | votes | answers`, `page`, `limit`.
- [ ] Anonymous-friendly, and visibility-filtered.
- [ ] Free text goes through **`websearch_to_tsquery('english', ...)`** against
      `questions.search_vector`. It must tolerate spaces, quotes, `OR`, and a leading `-`
      **without erroring**. Empty or whitespace-only `q` means no text filter at all.
- [ ] Filters:
  - [ ] `tag` uses **AND** semantics — the question's tags must contain **all** requested.
  - [ ] `author` matches username case-insensitively.
  - [ ] `status`: `unanswered` = no approved answer; `answered` = has an approved answer
        **and** no accepted answer; `accepted` = has an accepted answer.
  - [ ] `from` / `to` filter `created_at`, with the end day **inclusive**.
- [ ] Sort: default `relevance` when `q` is present (by `ts_rank_cd`, then newest),
      otherwise `newest`. `votes` and `answers` sort by their aggregated totals then
      newest. **`relevance` without a query falls back to newest.**
- [ ] Each result is a home-feed-style card **plus** a `highlight` string: with `q`, a
      `ts_headline` wrapping matches in `<mark>…</mark>` (2 fragments); without `q`, a plain
      240-character excerpt. **The `highlight` field is always present.**
- [ ] Response `{ items, total, page, limit }`, with `total` respecting **all** filters.

## Out of scope

* The search page — D-12.
* Searching answers, comments, or users. Questions only — that's what the trigger indexes.
* Maintaining `search_vector`. The database trigger does it; never compute it in Python.
* Typo tolerance, synonyms, "did you mean". Not in this project.

## Technical notes

**Constraints (requirements, not suggestions):**
* Use **`websearch_to_tsquery`**, not `to_tsquery`. The latter raises a syntax error on
  input like `foo bar` or an unmatched quote — that is, on ordinary human typing. The
  former is designed for user input and never throws.
* `total` respects the filters. Same rule as B-03, and the most commonly-shipped bug in
  search endpoints.
* Never compute `search_vector` in Python. The trigger owns it; a Python-computed vector
  would silently disagree with the index.
* `highlight` is **always** present, even with no query. A conditional field means the UI
  needs a branch for nothing.

**Files you will probably touch:**
* `backend/app/routers/search.py`, `backend/app/schemas/search.py`.

**Suggested approach:**
1. Build one base query with `visible_filter` applied, and derive `total` from it.
2. Add the filters one at a time, each as a conditional `.where(...)`. Tags first (it's
   the odd one — `@>` array containment gives you the AND semantics), then author, status,
   dates.
3. Add `q` last of the filters, and `highlight` right after it — `ts_headline` with
   `MaxFragments=2` and the default `<mark>` markers (check the option names against the
   Postgres docs rather than guessing).
4. Then the sorts, with the relevance fallback.
5. Try the awkward queries from step 3 below **as you go**, not at the end.

**Words you'll meet in this ticket:**
* **`tsvector` / `tsquery`** — Postgres's full-text types: the indexed document, and the
  parsed query run against it.
* **GIN index** — the index type that makes `tsvector` matching fast.
* **`websearch_to_tsquery`** — a parser that accepts search-engine-style input (quotes,
  `OR`, leading `-`) and never errors on nonsense.
* **`ts_rank_cd`** — a relevance score for a match.
* **`ts_headline`** — Postgres generating a snippet with the matched words wrapped in
  markers.

## Verify it yourself

```bash
docker-compose exec backend pytest tests/lane_d/test_d11_search_api.py -v
```

By hand:
1. `?q=docker` → only matching questions, each with `<mark>` around the match in
   `highlight`.
2. No `q` at all → everything visible, newest first, and `highlight` is a **plain
   240-character excerpt** with no `<mark>`.
3. **The robustness pass** — every one of these must return 200 with sensible results:
   `?q=hello world`, `?q="exact phrase"`, `?q=cats OR dogs`, `?q=-excluded`, `?q='`,
   `?q=%20%20`, and a 200-character `q`.
4. `?tag=python&tag=django` → only questions with **both**.
5. `?author=ALICE` → matches the user `alice`.
6. `?status=unanswered`, `?status=answered`, `?status=accepted` → three disjoint sets that
   add up to the whole corpus.
7. `?from=2026-01-01&to=2026-01-31` → includes a question created on the 31st.
8. `?sort=relevance` **without** `q` → newest order, not an error.
9. Set a matching question to `pending` → it vanishes from results **and** from `total`.
