# [D-04] A user sees the assistant's reply appear word by word, and never loses what it wrote

**Lane:** D — AI & Trust
**Task ID:** D-04
**Size:** ~2 days — the hardest task in the lane
**Depends on:** **D-01**, **D-03**.
**Blocks:** D-05.

---

## Problem

Conversations exist and can't be talked to. A plain request/response endpoint would leave
the user staring at a spinner for ten seconds, and if they navigated away mid-generation
the reply — which the model already produced and which already cost money — would be lost.

## Proposed outcome

`POST /api/ai/conversations/{id}/messages` — a Server-Sent Events stream that delivers
tokens as they arrive, persists both turns, enforces a per-user hourly cap, and keeps a
partial reply when the user hits stop.

## Acceptance criteria

- [ ] Owner-scoped (**404** otherwise). Body `{ content }`, trimmed, non-empty, ≤ 8 000.
- [ ] **Rate limit:** a rolling-hour cap of `LLM_RATE_LIMIT_PER_HOUR` (30) **user**
      messages across all of the caller's conversations. Exceeded → **429 `rate_limited`**
      with a **`Retry-After`** header set to when the oldest in-window message ages out.
- [ ] **Persist the user's turn BEFORE streaming** — so it counts toward the rate limit
      and survives a mid-stream failure or disconnect.
- [ ] If the conversation has no title yet, derive one from the first line of the message
      (≤ 80 characters).
- [ ] Build the model input from the **full persisted history** (the client sends only the
      new message) plus a system prompt. When the conversation is linked to a question,
      ground that system prompt in the question's title and body.
- [ ] Stream `data: {"delta": "..."}` per token; end with `event: done`.
- [ ] Translate LLM failures into a **final** `event: error` carrying a **sanitized**
      message (rate-limited / timed out / unavailable) — **never** the provider's raw body.
- [ ] **Cancellation:** poll for client disconnection between tokens. On disconnect, close
      the upstream stream (cancelling the provider call) and **persist the partial
      assistant reply**, shielding that write so task cancellation can't lose it.
- [ ] A full completion likewise persists the assistant turn and bumps the conversation's
      `updated_at`.
- [ ] Response headers: `Content-Type: text/event-stream`, `Cache-Control: no-cache`,
      `X-Accel-Buffering: no`. (Nginx SSE pass-through is already configured.)

## Out of scope

* The chat UI, the Stop button, the countdown — D-05.
* Provider specifics — D-01 owns those; you catch its exception types.
* Conversation creation, listing, deletion — D-03.
* Editing or regenerating a past turn. Not in this project.

## The tests that grade this task

```bash
docker-compose exec backend pytest tests/lane_d/test_d04_ai_streaming.py -v
```

Three tests. The provider is replaced by the `fake_llm` fixture, so the suite is hermetic
(set `fake_llm.tokens` for output, `fake_llm.raise_` to make it fail).

| Test | What it pins down | AC |
|---|---|---|
| `test_stream_emits_tokens_and_persists_turns` | **200**; the response text contains **`'"delta": "Hel"'`** and `"event: done"`; and afterwards `ai_messages` for that conversation contains both a `user` and an `assistant` row, with the user's content stored verbatim | streaming + persistence |
| `test_rate_limit_returns_429_with_retry_after` | patches the cap to 1; the first message → 200, the second → **429** with `error.code == "rate_limited"` and a **`Retry-After` header present** | rate limit |
| `test_llm_failure_becomes_sse_error_event` | with `fake_llm.raise_` set, the response is still **200** (the stream opens, *then* reports) and its text contains `"event: error"` | error translation |

Three details from this file that will otherwise bite you:

* The delta assertion is the **exact substring** `"delta": "Hel"` — with a space after the
  colon. That's what `json.dumps({"delta": tok})` produces by default. Use compact
  separators (`separators=(",", ":")`) and the test fails.
* The rate-limit test monkeypatches **`app.routers.ai.settings.LLM_RATE_LIMIT_PER_HOUR`**.
  So the endpoint must live in `app/routers/ai.py` and read the value off `settings` **at
  request time** — a module-level `LIMIT = settings...` captured at import won't see the
  patch.
* An LLM failure is **200 plus an error event**, not a 5xx. By the time the model fails,
  headers are already sent; the error has to travel inside the stream.

**Not graded here, but still required:** the `Retry-After` *value* (only its presence is
checked), the ≤ 8 000 validation, title derivation, building history from the database,
grounding the prompt in a linked question, the SSE headers, and **the entire cancellation
and partial-persistence path** — which is the hardest part of the ticket and completely
untested. Verify it by hand.

## Technical notes

**Constraints (requirements, not suggestions):**
* Persist the user turn first. Everything else — the rate limit being honest, the
  conversation surviving a crash — follows from that ordering.
* Sanitize error messages. D-01 already promises not to leak the key into its exceptions;
  don't undo that by streaming `str(exc)` from an unexpected error type.
* Shield the partial-reply write. When a client disconnects, your task is being cancelled;
  an unshielded `await` inside the cleanup will be cancelled too, and the partial reply
  disappears. `asyncio.shield` is the tool.
* `X-Accel-Buffering: no` is not optional — without it nginx buffers the whole stream and
  the user waits for the full reply anyway.

**Files you will probably touch:**
* `backend/app/routers/ai.py`, `backend/app/schemas/ai.py`,
  `backend/app/services/llm.py` (read only — D-01's).

**Suggested approach:**
1. Rate limit first: `COUNT` of the caller's `user` messages in the last hour; if at the
   cap, compute `Retry-After` from the oldest one and raise the 429. That's one test.
2. Persist the user turn, load history, build the message list.
3. Return a `StreamingResponse` over an async generator that yields SSE blocks. Get
   `delta` and `done` working — that's the second test.
4. Wrap the iteration in `try/except llm.LLMError` and yield an `event: error` block —
   third test.
5. Cancellation last, once everything else is green. Check `await request.is_disconnected()`
   between tokens, break out, and write the accumulated text under `asyncio.shield`.

**Words you'll meet in this ticket:**
* **SSE (Server-Sent Events)** — a one-way stream of text over a normal HTTP response.
  Blocks are separated by a blank line; `data:` carries payload, `event:` names a type.
* **Rolling window** — "in the last hour", measured continuously, not per calendar hour.
* **Backpressure / buffering** — a proxy holding your output until it has a lot of it.
  What `X-Accel-Buffering: no` disables.
* **`asyncio.shield`** — protects an await from being cancelled along with its parent
  task. The one thing standing between a disconnect and a lost reply.

## Verify it yourself

```bash
docker-compose exec backend pytest tests/lane_d/test_d04_ai_streaming.py -v
```

By hand, with a real key configured:
1. `curl -kN https://localhost/api/ai/conversations/<id>/messages -d '{"content":"count to twenty"}'`
   → tokens appear **progressively** (the `-N` disables curl's buffering). If they arrive
   all at once, check `X-Accel-Buffering`.
2. Check `ai_messages` in `psql` → one `user` row and one `assistant` row, complete.
3. Send 31 messages in an hour → the 31st is a 429 with a sensible `Retry-After`. Wait it
   out (or backdate the oldest row) → it works again.
4. **The cancellation test:** start a long generation and kill curl halfway (Ctrl-C).
   Then look at `ai_messages` → there is an `assistant` row containing the **partial**
   text produced so far. This is the acceptance criterion no test covers.
5. Blank `LLM_API_KEY` and send a message → the stream opens, then an `event: error` with
   a human-readable message, and **no key material anywhere** in the output.
6. Create a conversation linked to a question and ask "what is this about?" → the reply
   shows the model was given the question's content.
