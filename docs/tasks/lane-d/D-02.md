# [D-02] Content is screened before it becomes public, and an outage never blocks posting

**Lane:** D — AI & Trust
**Task ID:** D-02
**Size:** ~1.5 days
**Depends on:** nothing (the Launch Pad). Stages notifications through **C-01** (stub).
**Blocks:** D-07 (the admin queue), and **Lane B** — five of their endpoints call this
(integration milestone 4).

---

## Problem

Anything anyone posts is public the instant they hit submit. There's no screening, no way
to hold something for review, and no admin queue to review it into. Lane B currently calls
a stub that approves everything.

## Proposed outcome

`services/moderation.py` — screen text, write the verdict onto the content object, and
stage exactly the notifications that the visibility transition implies. Lane B swaps its
approve-everything stub for this and content can finally be held.

## Acceptance criteria

### `moderate(text) -> { flagged, categories, reason }`

- [ ] When `MODERATION_ENABLED` is false → `flagged = False`, and **never call the API**.
- [ ] Otherwise call the provider's moderation endpoint, and **cache by SHA-256 of the
      text** in a bounded LRU, so identical content is screened once per worker lifetime.
- [ ] **Flagging rule:** flagged when **any** category score ≥ its threshold — the scalar
      `MODERATION_THRESHOLD` by default, or the per-category value from the
      `MODERATION_THRESHOLD_OVERRIDES` JSON map. `reason` names the top offending
      categories.
- [ ] **Fail open:** on **any** API error, return `flagged = False` and log it. A provider
      outage must never block posting. **Don't cache a failure** — it's transient, not a
      verdict.

### `screen(text) -> (status, note)`

- [ ] `("pending", reason)` when flagged, `("approved", None)` otherwise.

### `screen_and_stage(db, *, kind, obj, text, question_id=None, parent_author_id=None, editing=False, question_author_id=None)`

- [ ] The single owner of the create/edit moderation sequence for all three content types.
- [ ] Screen `text`, write `moderation_status` and `moderation_note` onto `obj`, and
      **flush** so ids and defaults exist.
- [ ] Then stage exactly the notifications the visibility transition implies:
  - [ ] Newly **held** content notifies its author once (`moderation_pending`). An edit
        that leaves a post still pending stays silent.
  - [ ] **Approved** content runs `emit_content_approved` (owner event + mentions). It's
        idempotent, so the admin-approval path can safely re-emit.
  - [ ] An edit of content that was **already approved** additionally notifies the
        question author of a post-grace edit (`notify_content_edited`). A
        pending→approved transition reads as "new", not "edited", so it does **not**.
- [ ] **Stages only** — the caller owns the transaction and the commit.

* The moderation UI — D-08.
* Calling this from question/answer/comment creation — **Lane B** does that at milestone 4.

| Test | What it pins down | AC |
|---|---|---|
| `test_evaluate_scores_threshold_rule` | `evaluate_scores({"harassment": 0.9, "hate": 0.1})` → `(True, reason)` with `"harassment"` in the reason; `evaluate_scores({"harassment": 0.2})` → `(False, None)` | the threshold rule |
| `test_screen_maps_flagged_to_pending` | clean text → `("approved", None)`; text containing the fixture's sentinel → `("pending", <truthy note>)` | `screen` |
| `test_screen_and_stage_writes_verdict_onto_content` | builds a real `Question`, calls `screen_and_stage(db, kind="question", obj=q, text=q.body)` → `q.moderation_status == "pending"` and `q.moderation_note` is set; a clean one → `"approved"` | the write |

**The first test requires a function the spec doesn't name.** The spec describes
`moderate(text)`; the test calls **`moderation.evaluate_scores(scores_dict)`** — a
**synchronous** function taking an already-fetched score map and returning
`(flagged, reason)`. Factor the threshold logic out into that function and have
`moderate` call it. It's better design anyway: the rule becomes testable without a
network call, which is exactly why the test was written that way.

The `moderation_flags` fixture (in `conftest.py`) forces a flag for any text containing
its `@@FLAG@@` sentinel and approves everything else — that's how the suite gets a
deterministic verdict with no provider.

**Not graded here, but still required:** the `MODERATION_ENABLED` short-circuit, the
SHA-256 LRU cache, **fail-open on provider errors and not caching them**, the
`MODERATION_THRESHOLD_OVERRIDES` map, and every one of the notification-staging rules.
That last group is most of the ticket and none of it is tested here.

**The milestone test that grades the rest:**
`tests/milestones/test_m4_moderation.py` posts a flagged question through **Lane B's**
endpoint and asserts three things: the response is `moderation_status == "pending"`, a
**stranger gets 404** for it, and the author's inbox contains `moderation_pending`. It's
red until Lane B swaps their stub for yours. Run it the day after you announce.

## Technical notes

**Constraints (requirements, not suggestions):**
* **Fail open.** If the moderation provider is down, posts go through. A Q&A site that
  stops accepting content because a third party is having a bad day is broken; one that
  briefly under-moderates is not.
* Never cache a failure. A cached `False` from an outage would suppress screening for
  that text forever.
* Stage, never commit. The caller owns the transaction — that's what makes the verdict
  and the content land atomically.
* Cache on the **hash** of the text, not the text: bounded keys, and no user content
  sitting in an in-memory dict.

**Files you will probably touch:**
* `backend/app/services/moderation.py` — replace the stub.
* `MODERATION_ENABLED`, `MODERATION_THRESHOLD`, `MODERATION_THRESHOLD_OVERRIDES` are in
  `config.py`.

**Suggested approach:**
1. `evaluate_scores(scores) -> (flagged, reason)` first — pure, synchronous, no I/O. One
   test green.
2. `moderate(text)`: the enabled check, the cache lookup, the API call in a broad
   `try/except` that returns not-flagged, then `evaluate_scores`.
3. `screen(text)` is three lines on top.
4. `screen_and_stage` last, and write the notification branches as an explicit
   decision table — the four cases (newly held / still held / newly approved / edit of
   already-approved) are easy to conflate and only `m4` will catch you.

**Words you'll meet in this ticket:**
* **Fail open vs fail closed** — when a check breaks, do you allow or deny? Security
  checks usually fail closed; this one deliberately fails open.
* **LRU cache** — a bounded cache that evicts the least-recently-used entry.
* **Visibility transition** — the change from held to public (or the reverse). The
  notifications follow the transition, not the verdict.
* **Idempotent emission** — safe to call twice; C-01 guarantees the row appears once.

## Verify it yourself

```bash
docker-compose exec backend pytest tests/lane_d/test_d02_moderation_service.py -v
```

By hand:
1. `MODERATION_ENABLED=false` → `moderate()` returns not-flagged and makes **no** HTTP
   call (watch the network, or log it).
2. Screen the same text twice with the cache on → **one** provider call.
3. Set `MODERATION_THRESHOLD_OVERRIDES='{"harassment": 0.1}'` → text scoring 0.2 for
   harassment is now flagged, though the scalar default of 0.5 would have let it through.
4. **Fail open:** point the moderation URL at a dead host → `moderate()` returns
   not-flagged, the error is logged, and screening the same text again **still calls out**
   (the failure wasn't cached).
5. Call `screen_and_stage` on a flagged object → the object is `pending` with a note, and
   nothing is committed (roll back and check the table is untouched).
